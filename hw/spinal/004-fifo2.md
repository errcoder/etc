# 1. 왜 `write A`가 실제로 수행되지 않았는가?

로그를 다시 보면:

```text
Initial              empty=true full=false readData=0x00
After write A        empty=true full=false readData=0x00
```

`A`를 썼다면 최소한:

```text
empty = false
```

가 되어야 합니다.

그런데 그대로:

```text
empty = true
```

입니다.

즉 FIFO 내부에서 실제로:

```scala
doWrite
```

가 `true`가 되지 않았습니다.

---

# 2. 문제의 핵심은 이 순서입니다

우리가 작성한 테스트벤치는:

```scala
dut.io.write #= true

dut.clockDomain.waitSampling()

dut.io.write #= false
```

였습니다.

여기서 제가 놓친 것이 있습니다.

SpinalSim은 일반적인 "Scala 코드가 clock edge를 정확히 지나간 다음 다음 줄을 실행한다"라고 단순하게 생각하면 안 됩니다.

SpinalSim의 simulation engine은 event-driven 방식으로 동작하고, DUT에 대한 `#=` write도 simulation command buffer를 통해 처리됩니다. 따라서 clock sampling 시점과 testbench의 signal assignment 사이의 **delta-cycle/event ordering**을 고려해야 합니다. [spinalhdl.github.io](https://spinalhdl.github.io/SpinalDoc-RTD/master/SpinalHDL/Simulation/engine.html?utm_source=chatgpt.com)

---

# 3. 특히 `#=`는 즉시 HDL signal을 물리적으로 바꾸는 것처럼 생각하면 안 됩니다

예를 들어:

```scala
dut.io.write #= true
```

를 했다고 해서 Scala 코드 관점에서 즉시 DUT의 `write`가 확정적으로 `1`이 되어 clock edge를 통과했다고 생각하면 위험합니다.

그리고:

```scala
dut.clockDomain.waitSampling()
```

은 문서상 **ClockDomain이 sampling을 수행할 때까지 기다리는 것**입니다. [spinalhdl.github.io](https://spinalhdl.github.io/SpinalDoc-RTD/master/SpinalHDL/Simulation/clock.html?utm_source=chatgpt.com)

문제는 그 sampling event 주변에서:

```scala
dut.io.write #= false
```

를 바로 실행하는 것입니다.

즉 제가 테스트벤치에서:

```text
write = 1
   ↓
waitSampling()
   ↓
write = 0
```

를 너무 낙관적으로 작성했습니다.

---

# 4. 이게 왜 치명적인가?

FIFO의 실제 하드웨어 코드는:

```scala
val doWrite =
  io.write && !io.full

when(doWrite) {
  mem(writePtr) := io.writeData
  ...
}
```

입니다.

우리가 원하는 것은 clock edge에서:

```text
write = 1
full  = 0
```

을 보는 것입니다.

그러면:

```text
doWrite = 1
```

이 되고:

```text
count = count + 1
```

이 되어야 합니다.

그런데 testbench scheduling 때문에 DUT가 해당 sampling에서 `write = 0`을 보게 되면:

```text
doWrite = 0
```

이고:

```text
count = 0
```

그대로입니다.

그러니:

```text
empty = true
```

가 유지됩니다.

---

# 5. 어떻게 고쳐야 하는가?

가장 간단하고 명확한 방법은 **입력 stimulus와 clock edge를 분리해서 생각하는 것**입니다.

예를 들어:

```text
        falling edge
             │
             ▼
write = 1 ──────────────
             │
             │
             ▼
        rising edge
             │
             ▼
        FIFO samples
             │
             ▼
        write 처리
             │
             ▼
        falling edge
             │
             ▼
write = 0
```

즉 **write를 sampling edge까지 확실하게 유지한 후 내려야 합니다.**

핵심은:

```scala

```

직후에 바로:

```scala
#= false
```

하지 않는 것입니다.

# 9. 수정된 기본 FIFO Simulation

이제 처음부터 다시 작성하겠습니다.

```scala
import spinal.core._
import spinal.core.sim._

object SimpleFifoSim extends App {

  SimConfig
    .withWave
    .doSim(
      SimpleFifo(
        dataWidth = 8,
        depth = 4
      )
    ) { dut =>

      // --------------------------------------------------------
      // Initial stimulus
      // --------------------------------------------------------

      dut.io.write     #= false
      dut.io.writeData #= 0
      dut.io.read      #= false

      dut.clockDomain.forkStimulus(10)

      // --------------------------------------------------------
      // Helper functions
      // --------------------------------------------------------

      def printStatus(name: String): Unit = {

        println(
          f"$name%-20s " +
          f"empty=${dut.io.empty.toBoolean} " +
          f"full=${dut.io.full.toBoolean} " +
          f"readData=0x${dut.io.readData.toBigInt}%02X"
        )
      }

      def writeOne(data: Int): Unit = {

        dut.io.writeData #= data
        dut.io.write     #= true

        // Write request is sampled here.
        dut.clockDomain.waitSampling()

        // Allow the sequential logic and
        // combinational outputs to settle.
        dut.clockDomain.waitFallingEdge()

        dut.io.write #= false
      }

      def readOne(): Unit = {

        dut.io.read #= true

        // Read request is sampled here.
        dut.clockDomain.waitSampling()

        // Allow state changes to settle.
        dut.clockDomain.waitFallingEdge()

        dut.io.read #= false
      }

      // --------------------------------------------------------
      // Initial state
      // --------------------------------------------------------

      dut.clockDomain.waitSampling()
      dut.clockDomain.waitFallingEdge()

      printStatus("Initial")

      assert(
        dut.io.empty.toBoolean,
        "FIFO must be empty initially"
      )

      assert(
        !dut.io.full.toBoolean,
        "FIFO must not be full initially"
      )

      // --------------------------------------------------------
      // Write A
      // --------------------------------------------------------

      writeOne(0x41)

      printStatus("After write A")

      assert(
        !dut.io.empty.toBoolean,
        "FIFO should not be empty after writing A"
      )

      // --------------------------------------------------------
      // Write B
      // --------------------------------------------------------

      writeOne(0x42)

      printStatus("After write B")

      // --------------------------------------------------------
      // Write C
      // --------------------------------------------------------

      writeOne(0x43)

      printStatus("After write C")

      // --------------------------------------------------------
      // Read A
      // --------------------------------------------------------

      assert(
        dut.io.readData.toBigInt == 0x41,
        "First FIFO data must be A"
      )

      readOne()

      printStatus("After read A")

      // --------------------------------------------------------
      // Read B
      // --------------------------------------------------------

      assert(
        dut.io.readData.toBigInt == 0x42,
        "Second FIFO data must be B"
      )

      readOne()

      printStatus("After read B")

      // --------------------------------------------------------
      // Read C
      // --------------------------------------------------------

      assert(
        dut.io.readData.toBigInt == 0x43,
        "Third FIFO data must be C"
      )

      readOne()

      printStatus("After read C")

      // --------------------------------------------------------
      // FIFO should be empty
      // --------------------------------------------------------

      assert(
        dut.io.empty.toBoolean,
        "FIFO must be empty after reading all data"
      )

      assert(
        !dut.io.full.toBoolean,
        "FIFO must not be full"
      )

      println()
      println("Basic FIFO test passed.")
    }
}
```

맞습니다. **시뮬레이션 검증 통과한 것이 중요합니다.** 이제 `waitSampling()`과 `waitFallingEdge()`의 차이를 정확히 잡고 넘어가면 FIFO 테스트벤치 작성이 훨씬 편해집니다.

# 1. 먼저 한 줄로 정리

| 함수 | 무엇을 기다리나? | 주 용도 |
|---|---|---|
| `waitSampling()` | **ClockDomain의 sampling 이벤트** | DUT가 입력을 샘플링하는 시점 기준으로 테스트 |
| `waitFallingEdge()` | **클럭의 실제 Falling Edge(↓)** | 입력을 바꾸거나 다음 동작을 준비하는 시점 확보 |

즉,

> **`waitSampling()` = "DUT가 이 클럭에서 샘플링할 때까지 기다려라"**

> **`waitFallingEdge()` = "클럭이 1 → 0으로 떨어질 때까지 기다려라"**

입니다.

SpinalHDL 문서에서도 `waitSampling()`은 ClockDomain의 sampling event를 기다리는 동작으로 설명하고, `waitFallingEdge()`는 실제 falling edge를 기다리는 동작으로 구분합니다. 

---

# 2. 클럭을 그림으로 보면 바로 이해됩니다

우리 FIFO의 클럭을 단순하게 그려보면:

```text
        ↑             ↑             ↑
        │             │             │
CLK ____/‾‾‾‾‾‾‾‾‾‾‾‾\____/‾‾‾‾‾‾‾‾‾‾‾‾\____
        ↑             ↑
     Rising        Rising
      Edge          Edge

              ↓             ↓
           Falling       Falling
             Edge          Edge
```

일반적인 synchronous RTL에서는 `Reg`가 **Rising Edge에서 업데이트**됩니다.

예를 들어:

```scala
when(io.write) {
  mem(writePtr) := io.writeData
}
```

이것은 하드웨어적으로 대략:

```text
Rising Edge
    │
    ├── write가 1인가?
    │
    └── 그렇다면 memory에 write
```

입니다.

# 3. `waitSampling()`은 무엇인가?

예를 들어:

```scala
dut.io.write #= true

dut.clockDomain.waitSampling()

dut.io.write #= false
```

라고 하면,

```text
write = 1
        │
        │
        ▼
       ↑
    Sampling
        │
        ▼
write = 0
```

라는 의도입니다.

즉,

> "write를 1로 만들어 놓고, DUT가 한 번 샘플링할 때까지 기다린다."

입니다.

그래서 일반적인 DUT 테스트에서는 아주 자연스럽게:

```scala
dut.io.valid #= true
dut.clockDomain.waitSampling()
```

처럼 사용할 수 있습니다.

# 4. 그런데 왜 `waitFallingEdge()`를 추가했을까?

여기서 우리가 방금 수정한 FIFO 테스트를 다시 보겠습니다.

```scala
def writeOne(data: Int): Unit = {
  dut.io.writeData #= data
  dut.io.write     #= true

  dut.clockDomain.waitSampling()

  dut.clockDomain.waitFallingEdge()

  dut.io.write #= false
}
```

핵심은 이 부분입니다.

```scala
waitSampling()
waitFallingEdge()
```

이 두 개를 연속으로 사용했습니다.

시간축으로 보면:

```text
             DUT가 write를 샘플링
                     │
                     ▼
CLK          ↑               ↓
             │               │
             │               │
write  ──────1───────────────0──────
             │               │
             │               │
        waitSampling()   waitFallingEdge()
```

즉:

### `waitSampling()`

```text
"일단 DUT가 write=1을 볼 수 있는 sampling 시점까지 가자."
```

### `waitFallingEdge()`

```text
"그리고 그 sampling edge가 지나간 뒤,
클럭이 떨어질 때까지 기다리자."
```

그 다음에:

```scala
dut.io.write #= false
```

를 합니다.

# 5. 왜 굳이 Falling Edge에서 `write=false`로 만들까?

이게 이번 FIFO 테스트에서 **가장 중요한 포인트**입니다.

우리가 처음 작성했던 테스트는:

```scala
dut.io.write #= true

dut.clockDomain.waitSampling()

dut.io.write #= false
```

였습니다.

겉으로 보면 완전히 맞아 보입니다.

그런데 SpinalSim은 단순히:

```text
waitSampling()
↓
즉시 다음 Scala 코드 실행
```

처럼 생각하면 안 됩니다.

SpinalSim은 event-driven simulation이고, DUT의 sampling/update와 simulation thread의 signal access 사이에 이벤트 순서가 존재합니다. 공식 문서에서도 simulation event ordering 때문에 값 접근이 한 cycle 늦어질 수 있는 경우 등을 설명하고 있습니다. 

그래서 테스트벤치에서는 **DUT가 입력을 확실히 본 뒤 입력을 변경하는 것**이 안전합니다.

우리가:

```scala
waitSampling()
waitFallingEdge()
```

를 넣은 이유가 바로 이것입니다.

---

# 6. 실제 하드웨어 관점에서는 이렇게 생각하면 됩니다

FIFO에:

```text
write = 1
writeData = 0x41
```

를 넣었다고 합시다.

### Rising Edge

```text
          Rising Edge
              ↑
              │
write = 1 ────┤
data  = 41 ───┤
              │
              ▼
        FIFO가 write 수행
```

이 순간 FIFO 내부에서:

```text
mem[writePtr] = 0x41
```

가 수행됩니다.

그런데 테스트벤치가 바로:

```scala
write = false
```

로 바꾸는 것보다,

```text
          Rising Edge
              ↑
              │
        FIFO가 write
              │
              │
              ↓
          Falling Edge
              ↓
       write = false
```

처럼 **write를 해당 cycle 동안 유지**하는 것이 훨씬 명확합니다.

# 7. 그렇다면 `waitFallingEdge()`가 DUT 동작에 필요한가?

**아닙니다.**

이것도 매우 중요합니다.

`waitFallingEdge()`가 FIFO RTL을 동작시키는 것이 아닙니다.

```scala
dut.clockDomain.waitFallingEdge()
```

는 **테스트벤치의 시간 진행을 위한 것**입니다.

즉:

```text
                    DUT
                     │
                     │
       ┌─────────────┴─────────────┐
       │                           │
   write=1                     write=0
       │                           │
       ▼                           ▼
    Rising                     Falling
       │                           │
       └────── FIFO write ─────────┘
```

FIFO 자체는 Rising Edge에서 동작합니다.

`waitFallingEdge()`는 단지:

> "이제 FIFO가 방금 처리한 cycle이 끝났으니, 여기서 입력을 내려놓자."

라는 **testbench synchronization 방법**입니다.

---

# 8. `waitSampling()`과 `waitRisingEdge()`는 또 다릅니다

여기서 하나 더 알아두면 좋습니다.

SpinalHDL에는:

```scala
waitSampling()
```

뿐만 아니라:

```scala
waitRisingEdge()
```

도 있습니다.

둘을 단순화하면:

```text
waitRisingEdge()
    ↓
실제 Clock의 ↑ Edge를 기다림


waitSampling()
    ↓
ClockDomain의 Sampling Event를 기다림
```

따라서 **Clock Enable, Reset 등의 ClockDomain 조건**까지 고려하면 `waitSampling()`이 더 DUT 중심적인 개념입니다. SpinalHDL의 `waitSampling()`은 ClockDomain의 active sampling edge를 기준으로 동작합니다. 

일반적인 단일 클럭 synchronous RTL을 학습하는 단계에서는:

```scala
waitSampling()
```

을 주로 사용한다고 생각해도 좋습니다.

---

# 9. 이번 FIFO 테스트를 다시 해석하면

우리가 작성한:

```scala
def writeOne(data: Int): Unit = {
  dut.io.writeData #= data
  dut.io.write     #= true

  dut.clockDomain.waitSampling()

  dut.clockDomain.waitFallingEdge()

  dut.io.write #= false
}
```

는 사실 다음 의미입니다.

### Step 1

```scala
dut.io.writeData #= data
dut.io.write     #= true
```

테스트벤치가 FIFO에:

```text
WRITE 요청
DATA = data
```

를 걸어놓습니다.

### Step 2

```scala
waitSampling()
```

FIFO가 그 요청을 **sampling edge에서 받아들일 때까지 기다립니다.**

### Step 3

```scala
waitFallingEdge()
```

방금 처리한 clock cycle을 확실히 끝냅니다.

### Step 4

```scala
dut.io.write #= false
```

다음 cycle에서는 WRITE 요청을 제거합니다.

# 11. 실전에서는 어떻게 사용하면 좋을까?

앞으로 SpinalHDL 테스트벤치를 만들 때 저는 다음 패턴을 추천합니다.

## 입력을 한 clock 동안 넣는 경우


또는 조금 더 복잡한 handshake라면 상황에 맞춰:

# 12. 그런데 여기서 중요한 것 하나

우리 FIFO 코드에서:

```scala
io.readData := mem(readPtr)
```

이기 때문에 `readData`는 **현재 `readPtr`가 가리키는 데이터**입니다.

그래서:

```text
write A
write B
write C

readData = A
```

그리고:

```text
read A
```

를 수행한 다음:

```text
readPtr → B
```

가 되면서:

```text
readData = B
```

가 됩니다.

실제로 이번 결과가:

```text
After write A    readData=0x41
After write B    readData=0x41
After write C    readData=0x41

After read A     readData=0x42
After read B     readData=0x43
After read C     readData=0x00
```

로 나온 것이 바로 이 구조 때문입니다.

즉, **이번 시뮬레이션 결과는 FIFO의 write/read pointer와 `waitSampling()`/`waitFallingEdge()`의 타이밍이 의도대로 맞물려 동작했다는 좋은 검증 결과**입니다.

```text
waitSampling()
    ↓
"DUT가 이 ClockDomain의 sampling 시점을 지날 때까지 기다림"


waitFallingEdge()
    ↓
"실제 Clock이 1 → 0으로 떨어질 때까지 기다림"
```

그리고 우리의 FIFO 테스트에서는:

```scala
write = true

waitSampling()       // FIFO가 write를 처리

waitFallingEdge()    // 그 cycle을 확실히 끝냄

write = false        // 다음 cycle에 write 제거
```

라는 목적으로 사용했습니다.

**다음 FIFO 단계에서는 `FULL`, `EMPTY`, `동시 read/write`를 테스트해보는 게 좋습니다.** 특히 `FULL + read + write`를 넣어보면 FIFO 설계에서 왜 `doWrite = io.write && !io.full` 같은 정책을 정해야 하는지가 확실히 보입니다.

 (2) 에서 테스트 벤치가 dut.io.write 에 false 를 true 로 바꿨다. 이 사실은 (3) 지점에서 DUT에 반영될 것인데
 (3) 에서는 SpinalSim 은 (2) 만 dut 에 반영할 것이다. 왜냐하면 (1) 은 이미 (2) 에 의하여 덮어졌으니까.
 따라서, (1) 은 현재의 시뮬레이션 시나리오에서는 필요없는 코드이다. 너의 생각은?

 네. **지적하신 논리가 맞습니다.** 그리고 제가 앞에서 `waitFallingEdge()`를 넣은 이유를 잘못 설명했습니다.

특히 지금처럼 **같은 simulation thread에서 순차적으로**

```scala
dut.io.write #= false

// 바로 다음
dut.io.write #= true

dut.clockDomain.waitSampling()
```

가 실행되는 구조라면, `(1)`의 `false`를 DUT가 관찰할 별도의 clock/sampling 이벤트가 없습니다.

# 1. 지금 코드를 정확히 시간 순서로 보면

사용자께서 지적한 코드:

```scala
// Write A
dut.io.writeData #= 0x41
dut.io.write     #= true

dut.clockDomain.waitSampling()
dut.clockDomain.waitFallingEdge()

dut.io.write #= false          // (1)

// 관찰 코드
...

// Write B
dut.io.writeData #= 0x42
dut.io.write     #= true       // (2)

dut.clockDomain.waitSampling() // (3)
```

여기서 중요한 건 `(1) → (2)` 사이입니다.

```text
(1) write = false
       │
       │  ← clock wait 없음
       │
(2) write = true
       │
       │
(3) waitSampling()
       │
       ▼
    sampling
```

따라서 DUT가 `(1)`의 `write=false`를 **sampling할 기회가 없습니다.**

결국 다음 sampling 시점 `(3)`에서 DUT가 보는 것은:

```text
write = true
writeData = 0x42
```

입니다.

즉, 말씀하신:

> "(1)은 (2)에 의하여 덮어졌다."

라는 해석이 **이 테스트 구조에서는 맞습니다.**

---

# 2. 그러면 `waitFallingEdge()` 뒤의 `write=false`는 필요한가?

**현재 테스트 코드에서는 필요 없습니다.**

즉 이 부분:

```scala
dut.clockDomain.waitSampling()
dut.clockDomain.waitFallingEdge()

dut.io.write #= false
```

에서

```scala
dut.io.write #= false
```

는 다음 `waitSampling()` 전에 다시 `true`로 덮어쓰기 때문에 FIFO DUT의 동작에는 아무런 영향을 주지 않습니다.

그리고 더 중요한 것은:

```scala
waitFallingEdge()
```

자체도 이 경우에는 **`write=false`를 안전하게 반영하기 위해 필요한 것이 아닙니다.**

제가 앞에서:

> "Falling Edge에서 write=false로 만들어서 다음 cycle에는 write를 제거한다."

라고 설명한 것은 정확하지 않았습니다.

---

# 3. 실제로는 훨씬 간단하게 작성할 수 있습니다

현재 FIFO 테스트에서는:

```scala
// Write A
dut.io.writeData #= 0x41
dut.io.write     #= true

dut.clockDomain.waitSampling()

// 관찰

// Write B
dut.io.writeData #= 0x42
dut.io.write     #= true

dut.clockDomain.waitSampling()
```

이렇게 해도 됩니다.

각 `waitSampling()`에서 DUT가 다음과 같이 봅니다.

```text
             Sampling #1
                 ↓
write = true
data  = 41
                 │
                 ▼
              WRITE A


             Sampling #2
                 ↓
write = true
data  = 42
                 │
                 ▼
              WRITE B
```

이게 훨씬 자연스럽습니다.

# 4. 그렇다면 `write=false`는 언제 필요한가?

**WRITE를 한 번만 발생시키고 싶을 때** 필요합니다.

예를 들어:

```scala
dut.io.writeData #= 0x41
dut.io.write     #= true

dut.clockDomain.waitSampling()

dut.io.write #= false

dut.clockDomain.waitSampling()
```

이렇게 하면:

```text
             Sampling #1
                 ↓
write = true
data  = 41
                 │
                 ▼
              WRITE A


             Sampling #2
                 ↓
write = false
                 │
                 ▼
             아무것도 안 함
```

이제 `write=false`가 실제로 의미가 있습니다.

**왜냐하면 `write=false`를 설정한 뒤 다음 sampling event가 있기 때문입니다.**

---

# 5. 이것이 핵심입니다

테스트벤치에서 signal 값을 바꿨다고 해서 DUT가 즉시 그 값을 "clocked logic 관점에서 처리"하는 것은 아닙니다.

예를 들어:

```scala
dut.io.write #= false
```

를 했다고 해서 FIFO의

```scala
when(doWrite) {
    ...
}
```

가 실행되는 것은 아닙니다.

FIFO의 `Reg`와 memory write는 결국 sampling/clock edge에 의해 동작합니다.

그래서 중요한 것은:

```text
signal 변경
    ↓
다음 sampling edge
    ↓
DUT가 그 값을 관찰
```

이라는 관계입니다.

---

# 6. 따라서 우리가 처음 했던 코드의 진짜 의미

현재 코드:

```scala
dut.io.write #= true

dut.clockDomain.waitSampling()
dut.clockDomain.waitFallingEdge()

dut.io.write #= false

// 바로 다음
dut.io.write #= true

dut.clockDomain.waitSampling()
```

을 하드웨어 관점에서 보면 사실상:

```text
             Rising       Falling       Rising
               ↑             ↓             ↑
               │             │             │
write ─────────1──────────────1──────────────1────
               │                           │
               │                           │
             WRITE A                     WRITE B
```

와 동일한 효과입니다.

`false` 구간이 **clock edge 사이에 존재하지 않기 때문**입니다.

정확히 말하면:

```text
(1) false
   ↓
   같은 simulation time 안에서
(2) true
   ↓
(3) 다음 sampling
```

이므로 DUT 입장에서는 `false`를 sampling하지 않습니다.

---

# 7. 그러면 `waitFallingEdge()`는 완전히 쓸모없는가?

**아닙니다.**

`waitFallingEdge()` 자체는 유용합니다.

예를 들어 testbench에서 **clock phase를 명확하게 분리하고 싶을 때**:

```scala
dut.io.write #= true

dut.clockDomain.waitSampling()

dut.clockDomain.waitFallingEdge()

dut.io.write #= false
```

그리고 그 뒤에 다른 코드가 충분히 실행되는 구조라면 의미가 있습니다.

또는 입력을 **falling edge에서 변경하고 다음 rising edge에서 DUT가 샘플링하도록** 만들 수도 있습니다.

예:

```scala
dut.io.write #= false

dut.clockDomain.waitFallingEdge()

dut.io.writeData #= 0x42
dut.io.write     #= true

dut.clockDomain.waitSampling()
```

그러면 아주 명확합니다.

```text
CLK       ↑────────↓────────↑────────↓────────
          │        │        │
          │        │        │
DUT       sample            sample
                   │
                   ↓
             testbench가
             다음 입력 준비
```

이런 식의 **phase separation**이 목적이라면 `waitFallingEdge()`가 유용합니다.

---

# 8. SpinalHDL 문서상 의미도 이 해석과 일치합니다

SpinalHDL 문서에서:

```scala
waitSampling()
```

은 ClockDomain이 **sampling**하는 시점을 기다리는 것이고,

```scala
waitFallingEdge()
```

는 **falling edge 자체**를 기다리는 API입니다. [spinalhdl.github.io](https://spinalhdl.github.io/SpinalDoc-RTD/master/SpinalHDL/Simulation/clock.html?utm_source=chatgpt.com)

즉 `waitFallingEdge()`가 자동으로 "이전 `#=` 값을 DUT에 반영해 준다"는 의미는 아닙니다.

# 9. 이번 FIFO 테스트는 이렇게 고치는 게 더 좋겠습니다

제가 추천하는 현재 학습 단계의 `writeOne()`은 오히려:

```scala
def writeOne(data: Int): Unit = {
  dut.io.writeData #= data
  dut.io.write     #= true

  dut.clockDomain.waitSampling()
}
```

입니다.

그리고 한 번 write하고 끝난 뒤 write를 내려야 하는 테스트라면:

```scala
def writeOne(data: Int): Unit = {
  dut.io.writeData #= data
  dut.io.write     #= true

  dut.clockDomain.waitSampling()

  dut.io.write #= false
}
```

도 가능합니다.

다만 **이 함수가 끝난 직후 바로 다음 `writeOne()`을 호출한다면**:

```scala
writeOne(0x41)
writeOne(0x42)
writeOne(0x43)
```

내부적으로

```text
write=true
waitSampling()   ← A 처리

write=false
write=true       ← 바로 덮음
waitSampling()   ← B 처리
```

가 되므로, 중간의 `false`는 역시 DUT 관점에서 필요하지 않습니다.

따라서 현재 목적이라면 더 간결하게:

```scala
def writeOne(data: Int): Unit = {
  dut.io.writeData #= data
  dut.io.write     #= true

  dut.clockDomain.waitSampling()
}
```

하고 마지막에만:

```scala
dut.io.write #= false
```

하는 방식도 가능합니다.

# 10. 그런데 여기서 한 단계 더 중요한 것이 있습니다

이번 질문은 사실 **SpinalSim 테스트벤치를 제대로 이해하고 있다는 증거**입니다.

우리가 앞으로 테스트벤치를 작성할 때는 항상 이 질문을 해야 합니다.

> **"내가 signal을 변경한 뒤, DUT가 그 변경된 값을 관찰할 simulation event가 실제로 존재하는가?"**

예를 들어:

### ❌ 의미 없는 패턴

```scala
dut.io.write #= false
dut.io.write #= true
dut.clockDomain.waitSampling()
```

DUT가 보는 것:

```text
false → true
           ↑
        sampling
```

실제로는 `true`만 관찰.

### ✅ 의미 있는 패턴

```scala
dut.io.write #= false
dut.clockDomain.waitSampling()

dut.io.write #= true
dut.clockDomain.waitSampling()
```

DUT가 보는 것:

```text
false
  ↑
sampling #1

true
  ↑
sampling #2
```

이 차이가 굉장히 중요합니다.

# 결론

**사용자님의 분석에 동의합니다.**

제가 앞서 제시했던:

```scala
waitSampling()
waitFallingEdge()
write = false
```

패턴은 **현재 FIFO 테스트 시나리오에서는 불필요하게 복잡했습니다.**

특히:

```scala
write = false   // (1)
...
write = true    // (2)
waitSampling() // (3)
```

라면 `(1)`의 `false`를 DUT가 sampling할 기회가 없으므로 **DUT의 동작에는 영향을 주지 않습니다.**

따라서 이번 FIFO 테스트에서는 `waitFallingEdge()`를 제거하는 방향이 맞습니다.

그리고 이 부분은 제가 처음부터 더 정확하게 분석했어야 합니다. 특히 우리가 지금 **SpinalHDL v1.15.0의 simulation semantics를 배우는 과정**이므로, 앞으로는 "일단 동작하는 코드"보다 **각 signal 변경이 어느 simulation event에서 DUT에 관찰되는지까지 확인한 코드**를 기준으로 설명하겠습니다. 

다음에는 이걸 이용해서 **`FULL + READ + WRITE` 동시 발생 시 FIFO가 정확히 어떻게 동작하는지**를 waveform 기준으로 분석해보면 아주 좋은 다음 단계입니다.
