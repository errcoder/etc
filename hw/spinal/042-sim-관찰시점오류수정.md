 **이번 로그는 CPU datapath 자체의 `R2 = 0x65` 계산은 정상**입니다. 실제 문제는 **WB 관찰 시점과 실제 register write 시점이 한 cycle 어긋난 것**입니다.

로그가 결정적인 증거입니다.

```text
Cycle 4 : WB #1 : R1 <= 0x55
Cycle 6 : WB #2 : R2 <= 0x65

Final R1 = 0x55
Final R2 = 0x00
```

### 원인

현재 순차 로직은 같은 clock edge에서:

```scala
when(memWbValid && memWbWriteEnable) {
  registers(memWbRd) := memWbResult
}

memWbResult := ...
```

를 수행합니다.

SpinalHDL의 `Reg`는 clock edge에서 이전 값을 읽고 새로운 값을 저장합니다.

따라서 Cycle 6에서:

```text
기존 memWbResult = 0x00
새로운 memWbResult = 0x65
```

입니다.

그래서 **Cycle 6의 WB debug 출력은 새로 들어온 `0x65`를 보여주지만, 실제 register write는 이전 `memWbResult`인 `0x00`을 사용**합니다.

즉:

```text
Cycle 6
        MEM/WB에 0x65 도착
              │
              ├── debug → "WB #2 : R2 <= 0x65"
              │
              └── 실제 register write → 이전 memWbResult = 0x00
```

그리고 CPU를 바로 `run = false`로 만들어 버렸기 때문에 다음 WB clock이 실행되지 않습니다.

# 수정은 Simulation 쪽에서 하면 된다

CPU 자체의 pipeline 계산은 현재 로그상 정상입니다.

Simulation의 이 부분:

```scala
while (wbCount < 2 && cycle < 20) {
    ...
}
```

뒤에서 바로:

```scala
dut.io.run #= false
dut.clockDomain.waitSampling()
sleep(1)
```

하는 것이 문제입니다.

**두 번째 WB가 관찰된 뒤 실제 register write가 반영될 clock을 하나 더 줘야 합니다.**

다음처럼 수정하십시오.

```scala
// ------------------------------------------------------
// Stop condition
//
// WB #2 is visible in MEM/WB at this point,
// but the actual register write occurs on the
// following clock edge.
// ------------------------------------------------------

dut.clockDomain.waitSampling()
sleep(1)

// Now the final WB has actually been committed.

dut.io.run #= false

dut.clockDomain.waitSampling()
sleep(1)
```

즉 전체 마지막 부분은:

```scala
// ------------------------------------------------------
// Stop CPU
// ------------------------------------------------------

dut.clockDomain.waitSampling()
sleep(1)

dut.io.run #= false

dut.clockDomain.waitSampling()
sleep(1)

// ------------------------------------------------------
// Final register values
// ------------------------------------------------------

val r0 = dut.io.reg0.toInt
val r1 = dut.io.reg1.toInt
val r2 = dut.io.reg2.toInt
val r3 = dut.io.reg3.toInt
```

로 바꾸면 됩니다.

## 그런데 더 중요한 점

이번 로그를 보면 CPU의 핵심 동작은 정확합니다.

```text
Cycle 3 : STALL
Cycle 4 : WB #1 : R1 <= 0x55
Cycle 6 : WB #2 : R2 <= 0x65
```

그리고:

```text
R1 = 0x55
```

까지 실제로 반영되었습니다.

즉 다음 사항은 모두 정상입니다.

```text
LOAD address        → MEM[2]
MEM[2]              → 0x55
LOAD result         → R1
load-use hazard     → 1 cycle stall
MEM/WB forwarding   → ADD operand
ADD                  → 0x55 + 0x10
ADD result           → 0x65
```

문제는 **마지막 WB commit을 기다리지 않고 simulation을 종료한 것**입니다.

### 기대되는 수정 후 결과

```text

Cycle  4 : WB #1 : R1 <= 0x55
Cycle  6 : WB #2 : R2 <= 0x65

Final R0 = 0x02
Final R1 = 0x55
Final R2 = 0x65
Final R3 = 0x10

Stall count = 1
WB count    = 2

Load-use hazard / stall test passed.
```

따라서 **`FiveStageLoadCpu.scala`를 다시 뜯어고칠 필요는 없습니다.** 이번 실패는 CPU 연산 오류가 아니라 **testbench의 마지막 clock 관찰/commit 타이밍 문제**입니다.
