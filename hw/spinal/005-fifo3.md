
---

좋습니다. 👍  
그럼 **FIFO의 다음 핵심 단계: `FULL + READ + WRITE` 동시 발생**으로 넘어가겠습니다.

이번 단계는 단순히 코드를 추가하는 것보다 **FIFO 설계 정책을 이해하는 것**이 목적입니다.

# 1. 먼저 현재 FIFO의 정책 확인

현재 RTL에는:

```scala
val doWrite =
  io.write && !io.full

val doRead =
  io.read && !io.empty
```

가 있습니다.

즉,

```text
write 요청 + full 아님 → write 수행
read 요청  + empty 아님 → read 수행
```

입니다.

그런데 FIFO가 `FULL`인 상태에서:

```text
write = 1
read  = 1
```

이면 어떻게 될까요?

현재 로직에서는:

```text
full = true

doWrite = write && !full
       = true  && false
       = false

doRead  = read && !empty
       = true && true
       = true
```

따라서:

```text
READ  → 수행
WRITE → 수행하지 않음
```

입니다.

---

# 2. 이것이 이번 실험의 핵심

예를 들어 depth=4이고 FIFO가:

```text
[A][B][C][D]
 ↑           ↑
read        write
```

처럼 FULL이라고 해봅시다.

그리고 동시에:

```text
read  = 1
write = 1
writeData = E
```

를 넣습니다.

현재 설계에서는:

```text
           현재
       ┌───────────┐
       │ A B C D   │
       └───────────┘
         ↑       ↑
       READ    WRITE

       동시에

       read  = 1
       write = 1
```

하지만:

```scala
doWrite = io.write && !io.full
```

이므로:

```text
READ  A
WRITE E → 거부
```

결과:

```text
[B][C][D]
```

가 됩니다.

`E`는 FIFO에 들어가지 않습니다.

---

# 3. 그런데 다른 설계도 가능합니다

FIFO에 따라서는 FULL 상태에서:

```text
READ A
WRITE E
```

가 동시에 들어오면,

```text
A를 빼는 동시에
E를 넣는다
```

라고 정의할 수도 있습니다.

그러면:

```text
Before

[A][B][C][D]
 ↑           ↑
read        write


After

[B][C][D][E]
```

가 됩니다.

FIFO의 occupancy는:

```text
4 → 4
```

로 그대로입니다.

이 방식은 고성능 FIFO에서 상당히 중요한 정책입니다.

---

# 4. 두 정책 비교

| 상황 | 현재 FIFO | 동시 처리 FIFO |
|---|---|---|
| EMPTY + READ | READ 거부 | READ 거부 |
| EMPTY + WRITE | WRITE 수행 | WRITE 수행 |
| 일반 상태 READ | 수행 | 수행 |
| 일반 상태 WRITE | 수행 | 수행 |
| FULL + WRITE | 거부 | 거부 |
| **FULL + READ + WRITE** | **READ만 수행** | **READ + WRITE 수행** |

우리가 지금까지 만든 FIFO는 **첫 번째 정책**입니다.

---

# 5. 오늘은 먼저 RTL을 바꾸지 말자

여기서 바로:

```scala
doWrite = io.write && (!io.full || io.read)
```

같이 바꾸는 것은 잠시 보류하겠습니다.

먼저 **현재 FIFO가 실제로 어떤 동작을 하는지 시뮬레이션으로 증명**해보겠습니다.

이 과정이 중요합니다.

---

# 6. 첫 번째 실험: FULL 만들기

현재 depth가 4이므로:

```scala
writeOne(0x41) // A
writeOne(0x42) // B
writeOne(0x43) // C
writeOne(0x44) // D
```

하면:

```text
FIFO

┌────┬────┬────┬────┐
│ 41 │ 42 │ 43 │ 44 │
└────┴────┴────┴────┘
 ↑                  ↑
readPtr          writePtr
```

그리고:

```text
count = 4
empty = false
full  = true
```

가 되어야 합니다.

---

# 7. FULL 상태에서 WRITE만 해보기

그 다음:

```scala
dut.io.writeData #= 0x45
dut.io.write     #= true

dut.clockDomain.waitSampling()

dut.io.write     #= false
```

하면 어떻게 되어야 할까요?

현재 RTL에서는:

```scala
val doWrite =
  io.write && !io.full
```

이므로:

```text
write = true
full  = true

doWrite = false
```

입니다.

따라서:

```text
[A][B][C][D]
```

그대로여야 합니다.

`E`가 들어가면 안 됩니다.

---

# 8. 이것을 코드로 검증

기존 시뮬레이션에 다음 부분을 추가해봅시다.

```scala
// Fill FIFO: A, B, C, D
writeOne(0x41)
writeOne(0x42)
writeOne(0x43)
writeOne(0x44)

assert(
  dut.io.full.toBoolean,
  "FIFO must be full after four writes"
)

assert(
  dut.io.readData.toBigInt == 0x41,
  "FIFO head must be A"
)

printStatus("FIFO full")

// Try to write E while FIFO is full
dut.io.writeData #= 0x45
dut.io.write     #= true

dut.clockDomain.waitSampling()

dut.io.write     #= false

assert(
  dut.io.full.toBoolean,
  "FIFO must remain full"
)

assert(
  dut.io.readData.toBigInt == 0x41,
  "Write while full must not change FIFO head"
)

printStatus("After write E")
```

예상 결과:

```text
FIFO full          empty=false full=true  readData=0x41
After write E      empty=false full=true  readData=0x41
```

# 9. 그리고 진짜 중요한 실험

이제:

```text
FULL
```

상태에서:

```text
read  = 1
write = 1
writeData = 0x45
```

를 동시에 넣어봅니다.

코드는:

```scala
dut.io.writeData #= 0x45
dut.io.write     #= true
dut.io.read      #= true

dut.clockDomain.waitSampling()

dut.io.write     #= false
dut.io.read      #= false
```

현재 RTL에서는:

```text
full = true
empty = false

doWrite = true && !true
        = false

doRead = true && !false
       = true
```

따라서:

```text
READ A       → 수행
WRITE E      → 거부
```

가 되어야 합니다.

---

# 10. 결과는 이렇게 되어야 합니다

처음:

```text
[A][B][C][D]
```

동시:

```text
READ A
WRITE E
```

현재 FIFO 정책에서는:

```text
[B][C][D]
```

입니다.

따라서 `readData`는:

```text
0x42
```

가 되어야 합니다.

그리고 FIFO는:

```text
empty = false
full  = false
```

가 됩니다.

즉:

```text
count

4
↓
READ
↓
3
```

입니다.

`WRITE`가 막혔기 때문에 다시 4가 되지 않습니다.

---

# 11. 이 부분도 assertion으로 잡아보자

```scala
assert(
  !dut.io.full.toBoolean,
  "FIFO should no longer be full after reading one item"
)

assert(
  !dut.io.empty.toBoolean,
  "FIFO should still contain data"
)

assert(
  dut.io.readData.toBigInt == 0x42,
  "After simultaneous read/write while full, head must be B"
)

printStatus("After full read+write")
```

# 12. 여기서 아주 중요한 하드웨어 개념

현재 FIFO의 `count` 로직을 다시 보겠습니다.

```scala
when(doWrite && !doRead) {
  count := count + 1
} elsewhen(!doWrite && doRead) {
  count := count - 1
}
```

동시 read/write가 실제로 허용되는 일반적인 상황에서는:

```text
doWrite = true
doRead  = true
```

가 됩니다.

그러면:

```text
doWrite && !doRead
= true && false
= false

!doWrite && doRead
= false && true
= false
```

따라서 `count`에는 새로운 assignment가 없습니다.

결과:

```text
count = 그대로
```

입니다.

예:

```text
count = 3

READ + WRITE

count = 3
```

이게 정확합니다.

---

# 13. 그런데 FULL에서는 현재 설계가 다릅니다

현재:

```text
count = 4
```

에서:

```text
read  = 1
write = 1
```

이지만:

```text
doWrite = false
doRead  = true
```

이므로:

```text
count = 4 - 1
      = 3
```

입니다.

그래서 이번 실험은 단순히 `readData`만 보는 것이 아니라:

```text
FULL
 ↓
READ + WRITE
 ↓
doWrite = ?
doRead  = ?
 ↓
count 변화
 ↓
full 변화
```

를 확인하는 실험입니다.

# 14. 다음 단계에서 우리가 만들 것은

이번 실험을 통과시키면 다음으로 **FIFO를 조금 더 좋은 구조로 개선**하겠습니다.

순서는:

### Step 1 — 현재 정책 검증

```text
FULL + WRITE
FULL + READ
FULL + READ + WRITE
```

### Step 2 — pointer wrap-around 검증

```text
A B C D
↑     ↑

READ A
READ B

WRITE E
WRITE F

→ pointer가 다시 처음으로 돌아가는지 확인
```

### Step 3 — 내부 상태를 waveform에서 보기

```scala
writePtr.simPublic()
readPtr.simPublic()
count.simPublic()
```

를 이용해서 GTKWave에서:

```text
write
read
writePtr
readPtr
count
full
empty
readData
```

를 동시에 관찰합니다.

### Step 4 — FIFO 정책 개선

그 다음에야:

```scala
val doWrite =
  io.write && (!io.full || io.read)
```

같은 형태로 **FULL에서도 READ+WRITE 동시 처리를 허용하는 FIFO**를 만들어봅니다.

이때는 단순히 한 줄을 바꾸는 것으로 끝나지 않고, `count`, pointer, memory 동작까지 함께 검증해야 합니다.

---

## 지금은 여기까지

우선 **현재 FIFO RTL을 수정하지 않고**, 아래 세 가지를 시뮬레이션으로 확인하는 것이 첫 번째 과제입니다.

```text
① A B C D → FULL

② FULL + WRITE(E)
   → E는 들어가지 않는다

③ FULL + READ(A) + WRITE(E)
   → 현재 설계에서는 A만 빠지고 E는 들어가지 않는다
   → count: 4 → 3
   → readData: B
   → full: false
```

이걸 직접 실행해서 결과를 보여주시면, 그 결과를 기준으로 **pointer와 count까지 같이 추적하면서 다음 단계로 진행하겠습니다.**
