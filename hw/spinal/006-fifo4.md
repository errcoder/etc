맞습니다. **이번 실패는 FIFO RTL의 동작이 잘못된 것이 아니라, 이번에는 반대로 `readPtr`의 갱신을 관찰하기 전에 assertion을 해버린 것이 원인입니다.**

그리고 이 결과가 아주 좋은 학습 포인트입니다. 앞에서 우리가 이야기했던 **SpinalSim의 event ordering**이 실제로 다시 나타났습니다.

# 1. 지금 결과를 보면

실제 출력:

```text
FIFO full
    empty=false full=true readData=0x41

After write E
    empty=false full=true readData=0x41

After full read+write
    empty=false full=true readData=0x41
```

그리고:

```text
assertion failed:
After reading A, FIFO head must be B
```

입니다.

우리는 `B = 0x42`를 기대했는데 `readData`가 여전히 `0x41`로 보였습니다.

그런데 여기서 중요한 것이 있습니다.

---

# 2. `read` 자체가 실행되지 않았다는 뜻은 아닙니다

현재 FIFO RTL:

```scala
when(doRead) {
  when(readPtr === depth - 1) {
    readPtr := 0
  } otherwise {
    readPtr := readPtr + 1
  }
}
```

`FULL + READ + WRITE` 상황에서는:

```text
full  = true
empty = false
write = true
read  = true
```

이므로:

```text
doWrite = true && !true
        = false

doRead  = true && !false
        = true
```

입니다.

따라서 clock edge에서:

```text
doRead = true
```

이고,

```text
readPtr: 0 → 1
```

이 되어야 합니다.

즉 **A를 읽는 동작 자체는 발생해야 합니다.**

---

# 3. 문제는 바로 다음 줄의 assertion

우리가 작성한 테스트는 대략:

```scala
dut.io.writeData #= 0x45
dut.io.write     #= true
dut.io.read      #= true

dut.clockDomain.waitSampling()

dut.io.write     #= false
dut.io.read      #= false

printStatus("After full read+write")

assert(
  dut.io.readData.toBigInt == 0x42,
  "After reading A, FIFO head must be B"
)
```

입니다.

시간 순서를 그리면:

```text
             sampling edge
                  ↑
                  │
read = true ──────┤
                  │
                  └── readPtr := readPtr + 1
                           │
                           │
                           ▼
                    simulation update
```

그런데:

```scala
waitSampling()
```

직후에 바로 값을 읽었습니다.

즉:

```text
waitSampling()
    ↓
바로 readData 관찰
    ↓
readPtr 변경 결과가 아직 관찰 측에 반영되기 전일 가능성
```

이 생길 수 있습니다.

SpinalSim의 event ordering 때문에 이런 식으로 **DUT의 sequential update와 testbench의 signal read 사이에 타이밍 차이**가 발생할 수 있습니다.

---

# 4. 여기서 `waitFallingEdge()`가 드디어 제대로 쓰입니다

앞에서 제가 `waitFallingEdge()`를 잘못된 목적으로 사용했던 것을 지적하셨죠.

이번에는 **정확한 용도**입니다.

```scala
dut.clockDomain.waitSampling()

dut.clockDomain.waitFallingEdge()

printStatus("After full read+write")
```

이렇게 하면:

```text
             Rising Edge
                 ↑
                 │
                 │ DUT가 read 처리
                 │
                 ▼
             readPtr 갱신
                 │
                 │
                 ▼
             Falling Edge
                 ↓
                 │
                 ▼
          testbench가 관찰
```

이 됩니다.

즉 이번 `waitFallingEdge()`의 목적은:

> **입력을 변경하기 위한 것이 아니라, DUT의 clocked state update가 진행된 뒤 안정된 값을 관찰하기 위한 것**

입니다.

이 차이가 매우 중요합니다.

# 6. 그런데 여기서 한 가지 더 발견됩니다

사용자님의 출력:

```text
After full read+write
empty=false full=true readData=0x41
```

에서 `full=true`도 아직 그대로입니다.

이것 역시 같은 이유로 설명할 수 있습니다.

현재:

```scala
io.full := count === depth
```

이고 `count`는:

```scala
when(doWrite && !doRead) {
  count := count + 1
} elsewhen(!doWrite && doRead) {
  count := count - 1
}
```

입니다.

이번 상황:

```text
doWrite = false
doRead  = true
```

이므로:

```text
count: 4 → 3
```

이어야 합니다.

따라서 충분히 업데이트된 뒤라면:

```text
full = (count == 4)
     = false
```

가 되어야 합니다.

즉 우리가 지금 보고 있는:

```text
full=true
readData=0x41
```

역시 **sampling 직후 너무 빨리 관찰한 결과일 가능성이 매우 높습니다.**

라고 볼 필요가 없습니다.

그리고 이전 FIFO 테스트에서:

후 바로 결과를 확인했을 때 `write` 결과가 정상적으로 보였던 것은 테스트 구조와 signal update가 그 상황에서는 충분히 진행되었기 때문이고, 이번처럼 **readPtr/count라는 sequential state의 변경 결과를 즉시 관찰하는 경우에는 한 번 더 simulation event를 진행시키는 것이 안전**합니다.

입니다.

그리고 assertion:

```scala
      writeOne(0x42)

      writeOne(0x44)

        dut.io.full.toBoolean,
        "FIFO must be full after four writes"

        dut.io.readData.toBigInt == 0x41,

      )

      dut.io.writeData #= 0x45

      dut.clockDomain.waitFallingEdge()

      dut.io.write #= false
      dut.io.read #= false
```

> **`waitFallingEdge()`가 "write while full"에서는 필요 없고 "full + read + write"에서는 필요한 이유는, 두 경우의 DUT 내부 상태 변화가 다르기 때문입니다.**

그리고 이것은 단순히 `write`가 아니라 **`readPtr`, `count` 같은 `Reg`의 값이 실제로 변경되느냐**와 관련이 있습니다.


이므로:

```text
doWrite = false
```

입니다.

그리고 `read`도 없으므로:

```text
doRead = false
```

입니다.

그래서 `waitFallingEdge()`가 없어도 테스트가 통과합니다.

# 6. 그래서 `waitFallingEdge()`가 이번에는 관찰에 영향을 줍니다

현재 코드:

```scala
dut.clockDomain.waitSampling()
dut.clockDomain.waitFallingEdge()

printStatus("After full read+write")
```

는 사실:

```text
             Rising Edge
                 ↑
                 │
          DUT가 READ 처리
                 │
                 ▼
       readPtr / count 변경
                 │
                 ▼
            Falling Edge
                 ↓
                 │
                 ▼
          결과 관찰
```

이라는 **관찰 시점 확보** 역할을 합니다.

반면:

```scala
dut.clockDomain.waitSampling()

printStatus(...)
```

는 simulation event ordering에 따라 **clocked state update와 그 결과를 조합논리로 전달하는 과정이 완전히 끝나기 전에 관찰할 가능성**이 있습니다.

SpinalSim이 event-driven simulation이기 때문에 이런 차이가 생깁니다. SpinalHDL 문서에서도 simulation event ordering 때문에 signal 값을 읽는 시점에 주의해야 하는 사례를 설명합니다.

---

# 7. 그런데 여기서 아주 중요한 정정

제가 앞에서 `waitFallingEdge()`를 설명하면서:

> "DUT의 sequential update가 진행된 뒤 Falling Edge에서 결과가 안정된다."

라고 단순화했는데, **정확한 핵심은 Falling Edge 자체가 반드시 필요한 것이 아닙니다.**

즉:

```scala
waitSampling()
waitFallingEdge()
```

가 유일한 정답은 아닙니다.

중요한 것은:

> **DUT의 상태 변경과 그에 따른 combinational propagation이 완료된 뒤 결과를 관찰할 수 있도록 simulation을 충분히 진행시키는 것**

입니다.

그래서 다른 방법도 있을 수 있습니다.

예를 들어:

```scala
dut.clockDomain.waitSampling(2)
```

처럼 다음 sampling event를 더 진행시키는 방법도 있습니다.

다만 우리가 지금 배우는 단계에서는 **"Rising에서 DUT를 동작시키고, Falling에서 결과를 관찰한다"**는 방식이 시간 관계를 눈으로 이해하기 쉬워서 유용합니다.

---

# 8. 그런데 사용자님의 실험에서 더 중요한 사실

사실 이 테스트를 통해 다음과 같은 아주 좋은 원칙을 발견했습니다.

## `waitFallingEdge()`의 필요성은 signal의 종류로 결정되는 게 아닙니다.

예를 들어:

> "`read`에는 필요하고 `write`에는 필요하다."

가 아닙니다.

정확히는:

> **"해당 sampling edge에서 DUT의 상태가 변경되고, 그 변경된 상태를 바로 관찰하려는가?"**

가 중요합니다.

---

# 9. 세 가지 상황을 정리하면

### ① 상태 변화 없음

```text
FULL + WRITE
```

```text
doWrite = false
doRead  = false
```

```text
count   : 4 → 4
readPtr : 0 → 0
```

따라서:

```scala

printStatus()
```

만으로도 우리가 원하는 값이 보입니다.

---

### ② 상태 변화 있음

```text
FULL + READ + WRITE
```

```text
doWrite = false
doRead  = true
```

```text
count   : 4 → 3
readPtr : 0 → 1
```

그리고 `readData`도:

```text
A → B
```

로 바뀌어야 합니다.

따라서 **상태 업데이트 후 결과를 관찰할 수 있도록 추가적인 simulation synchronization이 필요**합니다.

현재 테스트에서는:

```scala
waitFallingEdge()
```

를 사용한 것입니다.

---

### ③ 다음 sampling에서 입력을 다시 바꿈

예를 들어:

```scala
dut.io.write #= false
dut.io.write #= true
dut.clockDomain.waitSampling()
```

이면 중간의 `false`는 DUT가 관찰하지 않습니다.

이것은 앞서 사용자님이 정확하게 지적하셨던 문제입니다.

---

# 10. 이걸 FIFO 관점에서 한 문장으로 표현하면

이번 두 테스트의 차이는:

```text
FULL + WRITE
     ↓
DUT가 "거부"
     ↓
상태 변화 없음
     ↓
waitSampling() 직후 관찰해도 기존 값과 동일


FULL + READ + WRITE
     ↓
DUT가 "READ 수행"
     ↓
readPtr / count 변화
     ↓
readData / full도 변화
     ↓
변경된 상태를 관찰할 synchronization 필요
```

입니다.

---

# 11. 그래서 지금 아주 좋은 다음 실험이 있습니다

이제 `waitFallingEdge()`가 정말 **"관찰을 늦추는 역할"**인지 직접 증명해볼 수 있습니다.

다음 두 코드를 비교해보세요.

### 실험 A

```scala

printStatus("Immediately after sampling")
```

### 실험 B

```scala
dut.clockDomain.waitSampling()

```

그리고 둘 다:

```text
FULL + READ + WRITE
```

직후에 실행합니다.

그러면 우리가 지금 이야기한 **SpinalSim의 event ordering과 state update가 실제 waveform에서 어떻게 나타나는지** 확인할 수 있습니다.

이 실험을 한 번 해보면 다음 단계인 `simPublic()`으로 `readPtr`, `writePtr`, `count`를 GTKWave에 띄우는 것이 훨씬 의미 있어집니다.

# 좋아. 다음 단계: FIFO 내부 상태를 파형으로 직접 확인하자

지금까지 `SimpleFifo`의 **동작 자체**는 확인했으니, 이제 한 단계 더 들어가서

> **"왜 이 시점에 `full`이 바뀌고, `readData`가 바뀌는가?"**

를 GTKWave에서 직접 확인해보자.

이번 단계에서는 **FIFO 내부의 `readPtr`, `writePtr`, `count`를 waveform에 노출**시키는 것부터 시작하자.

---

# 1. 먼저 FIFO에 `simPublic()` 추가

현재 FIFO에서 이 부분이 있지.

```scala
val writePtr =
  Reg(UInt(ptrWidth bits)) init(0)

val readPtr =
  Reg(UInt(ptrWidth bits)) init(0)

val count =
  Reg(UInt(countWidth bits)) init(0)
```

여기에 `simPublic()`을 붙인다.

```scala
val writePtr =
  Reg(UInt(ptrWidth bits)) init(0)
writePtr.simPublic()

val readPtr =
  Reg(UInt(ptrWidth bits)) init(0)
readPtr.simPublic()

val count =
  Reg(UInt(countWidth bits)) init(0)
count.simPublic()
```

그러면 시뮬레이션에서 내부 레지스터를 waveform으로 볼 수 있다.

---

# 2. 전체 FIFO는 이렇게

SpinalHDL **v1.15.0 / Release 34** 기준으로 다음처럼 사용하면 된다.

```scala
import spinal.core._

case class SimpleFifo(
    dataWidth: Int,
    depth: Int
) extends Component {

  require(depth >= 2)
  require(dataWidth >= 1)

  val io = new Bundle {
    val write     = in Bool()
    val writeData = in Bits(dataWidth bits)

    val read      = in Bool()
    val readData  = out Bits(dataWidth bits)

    val full      = out Bool()
    val empty     = out Bool()
  }

  // -------------------------
  // Memory
  // -------------------------

  val mem = Vec(
    Reg(Bits(dataWidth bits)) init(0),
    depth
  )

  // -------------------------
  // Pointer
  // -------------------------

  val ptrWidth =
    log2Up(depth)

  val writePtr =
    Reg(UInt(ptrWidth bits)) init(0)

  val readPtr =
    Reg(UInt(ptrWidth bits)) init(0)

  // Simulation에서 내부 상태 확인
  writePtr.simPublic()
  readPtr.simPublic()

  // -------------------------
  // Occupancy counter
  // -------------------------

  val countWidth =
    log2Up(depth + 1)

  val count =
    Reg(UInt(countWidth bits)) init(0)

  // Simulation에서 내부 상태 확인
  count.simPublic()

  // -------------------------
  // Status
  // -------------------------

  io.empty := count === 0
  io.full  := count === depth

  // FIFO head
  io.readData := mem(readPtr)

  // -------------------------
  // Actual operations
  // -------------------------

  val doWrite =
    io.write && !io.full

  val doRead =
    io.read && !io.empty

  // -------------------------
  // Write
  // -------------------------

  when(doWrite) {

    mem(writePtr) := io.writeData

    when(writePtr === depth - 1) {
      writePtr := 0
    } otherwise {
      writePtr := writePtr + 1
    }
  }

  // -------------------------
  // Read
  // -------------------------

  when(doRead) {

    when(readPtr === depth - 1) {
      readPtr := 0
    } otherwise {
      readPtr := readPtr + 1
    }
  }

  // -------------------------
  // Count
  // -------------------------

  when(doWrite && !doRead) {

    count := count + 1

  } elsewhen(!doWrite && doRead) {

    count := count - 1
  }
}
```

# 3. 이제 waveform에서 뭘 볼까?

이번에는 다음 신호를 집중해서 보면 된다.

| 신호 | 의미 |
|---|---|
| `io_write` | 쓰기 요청 |
| `io_writeData` | 쓸 데이터 |
| `io_read` | 읽기 요청 |
| `io_readData` | FIFO의 현재 head |
| `io_full` | FIFO가 가득 참 |
| `io_empty` | FIFO가 비어 있음 |
| `writePtr` | 다음 write 위치 |
| `readPtr` | 현재 FIFO head 위치 |
| `count` | FIFO에 들어있는 데이터 개수 |

특히 중요한 건 이 3개다.

```text

readPtr
count
```

```text

readPtr  = 0
```

```text
│       │

├───────┤
│       │

    writePtr
```

가 된다.

그러면:

# 6. C, D까지 넣으면

결과는:

```text
┌───────┐
│   A   │ ← readPtr = 0
├───────┤
│   B   │
├───────┤

├───────┤
```

## `writePtr`가 0으로 돌아온다.


가 된다.

# 8. 이게 바로 우리가 방금 겪었던 문제다

앞에서 봤던 상황을 다시 보면:

```text
FULL + READ + WRITE
```

현재:

```text
count = 4
```

이므로:

```scala
io.full == true
```

이다.

우리 FIFO 정책에서는:

```scala
val doWrite =
  io.write && !io.full
```

이므로

```text
doWrite = false
```

이다.

반면:

```scala
val doRead =
  io.read && !io.empty
```

이므로

```text
doRead = true
```

이다.

결국 실제 동작은:

```text
WRITE 요청   → 거부
READ 요청    → 실행
```

이다.

따라서:

```text
count:    4 → 3
readPtr:  0 → 1
writePtr: 0 → 0
```

가 되어야 한다.

그리고:

```text

readData: A → B
```

가 된다.

# 9. 이번 단계에서 가장 중요한 관찰

GTKWave에서 다음과 같이 보면 아주 좋다.

```text
clock
io_write
io_read
io_writeData

writePtr
readPtr
count

io_full
io_empty
io_readData
```

그리고 **clock의 rising edge를 기준으로** 관찰한다.

예를 들어:

```text
        ↑       ↑       ↑       ↑
clock   ┌─┐     ┌─┐     ┌─┐     ┌─┐
        │ │     │ │     │ │     │ │
────────┘ └─────┘ └─────┘ └─────┘ └──

write   ────████──────────────
read    ────────────────████──

count   0    1       2       3
```

이런 식으로 **입력 → clock edge → 내부 상태 변화 → 출력 변화**의 관계를 보는 것이 핵심이다.

# 10. 다음 실험은 이것으로 가자

이번에는 테스트를 조금 확장해서 **pointer wrap-around를 실제로 검증**하자.

Depth = 4에서:

```text
1. A write
2. B write
3. C write
4. D write

5. A read
6. B read

7. E write
8. F write
```

이렇게 해보면 pointer가 실제로 순환한다.

예상 상태:

| 단계 | 동작 | writePtr | readPtr | count | head |
|---|---|---:|---:|---:|---|
| 초기 | - | 0 | 0 | 0 | - |
| 1 | A write | 1 | 0 | 1 | A |
| 2 | B write | 2 | 0 | 2 | A |
| 3 | C write | 3 | 0 | 3 | A |
| 4 | D write | 0 | 0 | 4 | A |
| 5 | A read | 0 | 1 | 3 | B |
| 6 | B read | 0 | 2 | 2 | C |
| 7 | E write | 1 | 2 | 3 | C |
| 8 | F write | 2 | 2 | 4 | C |

여기서 아주 재미있는 부분이 나온다.

**메모리 위치 0과 1을 다시 사용한다.**

즉 FIFO는 메모리를:

```text
A B C D
```

로 한 번 사용하고 끝나는 것이 아니라,

```text
A B C D
    ↓
E F
```

처럼 **원형으로 재사용**한다.

이것이 FIFO의 핵심 구조 중 하나다.

---

# 8. 이게 바로 우리가 방금 겪었던 문제다

앞에서 봤던 상황을 다시 보면:

```text
FULL + READ + WRITE
```

현재:

```text
count = 4
```

이므로:

```scala
io.full == true
```

이다.

우리 FIFO 정책에서는:

```scala
val doWrite =
  io.write && !io.full
```

이므로

```text
doWrite = false
```

이다.

반면:

```scala
val doRead =
  io.read && !io.empty
```

이므로

```text
doRead = true
```

이다.

결국 실제 동작은:

```text
WRITE 요청   → 거부
READ 요청    → 실행
```

이다.

따라서:

```text
count:    4 → 3
readPtr:  0 → 1
writePtr: 0 → 0
```

가 되어야 한다.

그리고:

```text
full:     true → false
readData: A → B
```

가 된다.

---

# 9. 이번 단계에서 가장 중요한 관찰

GTKWave에서 다음과 같이 보면 아주 좋다.

```text
clock
io_write
io_read
io_writeData

writePtr
readPtr
count

io_full
io_empty
io_readData
```

그리고 **clock의 rising edge를 기준으로** 관찰한다.

예를 들어:

```text
        ↑       ↑       ↑       ↑
clock   ┌─┐     ┌─┐     ┌─┐     ┌─┐
        │ │     │ │     │ │     │ │
────────┘ └─────┘ └─────┘ └─────┘ └──

write   ────████──────────────
read    ────────────────████──

count   0    1       2       3
```

이런 식으로 **입력 → clock edge → 내부 상태 변화 → 출력 변화**의 관계를 보는 것이 핵심이다.

# 10. 다음 실험은 이것으로 가자

이번에는 테스트를 조금 확장해서 **pointer wrap-around를 실제로 검증**하자.

Depth = 4에서:

```text
1. A write
2. B write
3. C write
4. D write

5. A read
6. B read

7. E write
8. F write
```

이렇게 해보면 pointer가 실제로 순환한다.

예상 상태:

| 단계 | 동작 | writePtr | readPtr | count | head |
|---|---|---:|---:|---:|---|
| 초기 | - | 0 | 0 | 0 | - |
| 1 | A write | 1 | 0 | 1 | A |
| 2 | B write | 2 | 0 | 2 | A |
| 3 | C write | 3 | 0 | 3 | A |
| 4 | D write | 0 | 0 | 4 | A |
| 5 | A read | 0 | 1 | 3 | B |
| 6 | B read | 0 | 2 | 2 | C |
| 7 | E write | 1 | 2 | 3 | C |
| 8 | F write | 2 | 2 | 4 | C |

여기서 아주 재미있는 부분이 나온다.

**메모리 위치 0과 1을 다시 사용한다.**

즉 FIFO는 메모리를:

```text
A B C D
```

로 한 번 사용하고 끝나는 것이 아니라,

```text
A B C D
    ↓
E F
```

처럼 **원형으로 재사용**한다.

이것이 FIFO의 핵심 구조 중 하나다.
