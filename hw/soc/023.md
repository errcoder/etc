## 1. 먼저 Error Response의 동작을 정의하겠습니다

현재 메모리 맵은 다음과 같습니다.

| 주소 범위                     | 장치       | 처리       |
| ------------------------- | -------- | -------- |
| `0x00000000 ~ 0x000003FF` | Data RAM | 정상 접근    |
| 그 외 주소                    | Unmapped | Error 처리 |

이번 단계에서는 Unmapped 주소에 대한 Load 요청을 우선 처리하겠습니다.

정상 RAM Load와 Unmapped Load의 동작은 다음과 같습니다.

정상 RAM Load

1. CPU가 Load 명령을 전송합니다.
2. Decoder가 RAM 주소임을 확인하고 RAM으로 전달합니다.
3. RAM이 읽은 데이터를 응답합니다.
4. Decoder가 데이터를 CPU에 전달하고 `error = 0`을 반환합니다.

Unmapped Load

1. CPU가 Load 명령을 전송합니다.
2. Decoder가 RAM 주소가 아님을 확인합니다.
3. Decoder가 요청을 수락하고 내부적으로 Error Response를 예약합니다.
4. 다음 Clock Cycle에 `ready = 1`, `error = 1`, `data = 0`을 CPU에 반환합니다.

여기서 `DBusSimpleRsp.ready`는 CPU가 응답을 받을 수 있다는 뜻이 아니라 응답 데이터가 유효하다는 표시입니다. 기존에 확인했던 VexRiscv 소스와 동일한 의미입니다.


## 2. 중요한 VexRiscv 설정도 확인했습니다

이번 단계에서 놓치면 안 되는 부분이 있습니다.

현재 사용 중인 VexRiscv의 `DBusSimplePlugin`은 다음과 같이 정의되어 있습니다.

```
class DBusSimplePlugin(
  catchAddressMisaligned: Boolean = false,
  catchAccessFault: Boolean = false,
  ...
)
```

즉, `catchAccessFault`의 기본값은 `false`입니다.

또한 정확히 사용 중인 commit의 소스를 확인한 결과, `catchAccessFault`가 활성화되어 있을 때 `rsp.ready && rsp.error`인 Load에 대해 Load Access Fault 예외 코드 5를 발생시킵니다.
Store Access Fault는 이 코드 경로에서 처리하지 않습니다.


따라서 두 가지를 구분해서 진행하겠습니다.

1. Decoder가 Unmapped Load에 Error Response를 반환하는 기능.
2. CPU가 그 Error Response를 실제 RISC-V 예외로 처리하는 기능.

이번에는 우선 첫 번째 기능을 구현하고 검증하겠습니다. Store Access Fault는 별도의 후속 작업으로 다루는 것이 정확합니다.

## 2. DBusDecoder.scala 전체 교체

이번에는 Unmapped Load를 수락한 후 한 Clock Cycle 뒤에 Error Response를 발생시키도록 구현합니다.

```
package myvexsoc

import spinal.core._
import vexriscv.plugin._

class DBusDecoder extends Component {

  val io = new Bundle {
    val cpu = slave(DBusSimpleBus())
    val ram = master(DBusSimpleBus())
  }

  // RAM address map:
  // 0x00000000 ~ 0x000003FF
  val ramHit =
    io.cpu.cmd.address < U(0x00000400L, 32 bits)

  // RAM command forwarding
  io.ram.cmd.valid := io.cpu.cmd.valid && ramHit
  io.ram.cmd.payload := io.cpu.cmd.payload

  // Command acceptance:
  // - RAM access       : RAM decides ready
  // - Unmapped Load    : accept immediately
  // - Unmapped Store   : do not accept
  io.cpu.cmd.ready := Mux(
    ramHit,
    io.ram.cmd.ready,
    !io.cpu.cmd.wr
  )

  // Detect an accepted Unmapped Load
  val unmappedLoadFire =
    io.cpu.cmd.fire && !ramHit && !io.cpu.cmd.wr

  // Generate Error Response one cycle later
  val errorPending =
    RegNext(unmappedLoadFire) init (False)

  // Response routing
  // Unmapped Load Error Response has priority.
  io.cpu.rsp.ready :=
    errorPending || io.ram.rsp.ready

  io.cpu.rsp.data :=
    Mux(
      errorPending,
      B(0, 32 bits),
      io.ram.rsp.data
    )

  io.cpu.rsp.error :=
    errorPending || io.ram.rsp.error
}
```

### 동작 원리

`errorPending`이 핵심입니다.

```
val errorPending =
  RegNext(unmappedLoadFire) init (False)
```

Unmapped Load 요청이 수락된 Clock Edge에서 `unmappedLoadFire`가 참이 되고, 다음 Clock Cycle에 `errorPending`이 참이 됩니다.

그동안 CPU에는 다음 응답이 전달됩니다.

| 신호          | 값 | 의미        |
| ----------- | - | --------- |
| `rsp.ready` | 1 | 응답 유효     |
| `rsp.error` | 1 | 접근 오류     |
| `rsp.data`  | 0 | 오류 응답 데이터 |

여기서는 CPU가 한 번에 하나의 Load 요청만 outstanding 상태로 유지한다는 현재 `DBusSimplePlugin`의 사용 조건을 전제로 합니다.

## 3. InstructionRom.scala 전체 교체

이번에는 CPU가 RAM에 정상 Store를 한 번 수행한 다음, RAM 주소 범위 밖인 `0x20000000`에서 Load를 시도하도록 프로그램을 구성합니다.

그리고 Load 다음에 실행될 Store를 하나 배치합니다. CPU가 Access Fault 예외를 정상적으로 처리한다면 이 Store는 실행되지 않아야 합니다.

```
package myvexsoc

import spinal.core._
import spinal.lib._
import vexriscv.plugin._

class InstructionRom extends Component {

  val io = new Bundle {
    val cmd = slave(Stream(IBusSimpleCmd()))
    val rsp = master(Flow(IBusSimpleRsp()))
  }

  // Instructions
  val ADDI_X1_X0_1 = B"x00100093"
  val SW_X1_0_X0   = B"x00102023"

  val LUI_X4_20000 = B"x20000237"
  val LW_X3_0_X4   = B"x00022183"

  val SW_X3_8_X0   = B"x00302423"

  val JAL_X0_0     = B"x0000006F"
  val NOP          = B"x00000013"

  io.cmd.ready := True

  val instruction = Bits(32 bits)
  instruction := NOP

  switch(io.cmd.pc) {

    // RAM[0] = 1
    is(U"32'h80000000") {
      instruction := ADDI_X1_X0_1
    }

    is(U"32'h80000004") {
      instruction := SW_X1_0_X0
    }

    // x4 = 0x20000000
    is(U"32'h80000008") {
      instruction := LUI_X4_20000
    }

    // Load from unmapped address 0x20000000
    is(U"32'h8000000C") {
      instruction := LW_X3_0_X4
    }

    // This Store must not execute after Load Access Fault
    is(U"32'h80000010") {
      instruction := SW_X3_8_X0
    }

    // Infinite loop if execution reaches here
    is(U"32'h80000014") {
      instruction := JAL_X0_0
    }
  }

  // One-cycle instruction response
  io.rsp.valid := RegNext(io.cmd.fire) init (False)

  io.rsp.inst :=
    RegNextWhen(instruction, io.cmd.fire) init (NOP)

  io.rsp.error := False
}
```

### 프로그램의 의도

| PC           | 명령어              | 기대 동작           |
| ------------ | ---------------- | --------------- |
| `0x80000000` | `ADDI x1,x0,1`   | x1 = 1          |
| `0x80000004` | `SW x1,0(x0)`    | RAM[0] = 1      |
| `0x80000008` | `LUI x4,0x20000` | x4 = 0x20000000 |
| `0x8000000C` | `LW x3,0(x4)`    | Unmapped Load   |
| `0x80000010` | `SW x3,8(x0)`    | 실행되면 안 됨        |
| `0x80000014` | `JAL x0,0`       | 무한 루프           |

## 5. VexRiscvTopSim.scala 전체 코드

이번 테스트에서는 다음 사항을 확인합니다.

1. RAM Store가 정상적으로 수락되는가?
2. Unmapped Load가 수락되는가?
3. 다음 Cycle에 Error Response가 발생하는가?
4. Error Response의 `data`가 0인가?
5. CPU가 Load Access Fault를 처리하여 후속 Store를 실행하지 않는가?

초기 `waitSampling(5)`는 넣지 않았습니다. Clock 생성 후 곧바로 Falling Edge 관찰을 시작합니다.

```
package myvexsoc

import spinal.core.sim._
import vexriscv.plugin._

import scala.collection.mutable

object VexRiscvTopSim extends App {

  SimConfig.withWave
    .compile(new VexRiscvTop)
    .doSim { dut =>

      println("========================================")
      println(" VexRiscv Unmapped Load Error Test")
      println("========================================")

      dut.clockDomain.forkStimulus(period = 10)

      val dbusPlugin = dut.system.cpu.plugins
        .collectFirst {
          case p: DBusSimplePlugin => p
        }
        .getOrElse {
          throw new Exception("DBusSimplePlugin not found")
        }

      val dbus = dbusPlugin.dBus

      val stores = mutable.Map.empty[Long, Long]

      var storeCount = 0
      var loadCount = 0
      var errorResponseCount = 0

      var loadPending = false
      var pendingLoadAddress = 0L

      for (cycle <- 1 to 100) {

        dut.clockDomain.waitFallingEdge()

        // --------------------------------
        // 1. Observe Load response
        // --------------------------------

        val rspValid = dbus.rsp.ready.toBoolean

        if (rspValid) {

          assert(
            loadPending,
            s"Unexpected Load response at cycle $cycle"
          )

          val rspError = dbus.rsp.error.toBoolean
          val rspData = dbus.rsp.data.toLong

          println(
            f"Cycle $cycle%3d : LOAD RSP " +
              f"addr=0x$pendingLoadAddress%08X " +
              f"data=0x$rspData%08X error=$rspError"
          )

          assert(
            pendingLoadAddress == 0x20000000L,
            f"Unexpected response address: 0x$pendingLoadAddress%08X"
          )

          assert(
            rspError,
            "Expected Error Response for Unmapped Load"
          )

          assert(
            rspData == 0L,
            f"Expected error data 0x00000000, got 0x$rspData%08X"
          )

          errorResponseCount += 1
          loadPending = false
        }

        // --------------------------------
        // 2. Observe DBus command
        // --------------------------------

        val cmdValid = dbus.cmd.valid.toBoolean
        val cmdReady = dbus.cmd.ready.toBoolean

        if (cmdValid && cmdReady) {

          val wr = dbus.cmd.wr.toBoolean
          val address = dbus.cmd.address.toLong
          val data = dbus.cmd.payload.data.toLong
          val mask = dbus.cmd.mask.toInt

          if (wr) {

            storeCount += 1
            stores(address) = data

            println(
              f"Cycle $cycle%3d : STORE " +
                f"addr=0x$address%08X " +
                f"data=0x$data%08X mask=0x$mask%X"
            )

          } else {

            loadCount += 1
            loadPending = true
            pendingLoadAddress = address

            println(
              f"Cycle $cycle%3d : LOAD addr=0x$address%08X"
            )

          }
        }
      }

      // --------------------------------
      // 3. Final checks
      // --------------------------------

      println()
      println("========================================")
      println(" Unmapped Load Error Test Result")
      println("========================================")

      assert(
        !loadPending,
        "Load response is still pending"
      )

      assert(
        storeCount == 1,
        s"Expected 1 Store, observed $storeCount"
      )

      assert(
        loadCount == 1,
        s"Expected 1 Load, observed $loadCount"
      )

      assert(
        errorResponseCount == 1,
        s"Expected 1 Error Response, observed $errorResponseCount"
      )

      assert(
        stores.getOrElse(0x00000000L, -1L) == 1L,
        "RAM[0] Store verification failed"
      )

      assert(
        !stores.contains(0x00000008L),
        "Store after Load Access Fault was executed!"
      )

      println("[PASS] RAM[0] = 0x00000001")
      println("[PASS] Unmapped Load address = 0x20000000")
      println("[PASS] Error Response received")
      println("[PASS] Error Response data = 0x00000000")
      println("[PASS] Error Response count = 1")
      println("[PASS] Store after Load Access Fault was not executed")

      println("========================================")
      println(" Unmapped Load Error Test finished")
      println("========================================")
    }
}
```

This warning means that your VexRiscv processor is configured without an illegal instruction exception handler, 
which will cause software like Rust to crash or behave unpredictably if it encounters an unsupported instruction.

In a standard RISC-V processor, when the CPU encounters an instruction it doesn't recognize (or one that isn't enabled in its hardware configuration), 
it throws an "illegal instruction" exception. 

The operating system or runtime environment catches this exception to gracefully handle it—often by emulating the missing instruction in software.

### Why Rust Breaks Without It

• Panic and Enums: The Rust compiler (rustc) frequently uses the RISC-V illegal instruction opcode (such as unimp or 0x00000000) as a trap. 
For example, if your code encounters an explicit panic!(), an unreachable code block, or a corrupted enum state, 
Rust intentionally executes an illegal instruction to halt the program safely.
• No Exception Catching: Because your hardware lacks the "illegal instruction catch support," the CPU cannot jump to an exception handler 
when Rust deliberately trips this trap. Instead of a clean panic message or a controlled halt, 
the processor will likely lock up, enter an infinite loop, or execute random memory.
• Feature Detection: Rust binaries or standard libraries sometimes try to probe if certain instruction extensions (like atomic A or compressed C instructions) 
are supported. Without hardware catch support, this probe will immediately freeze the core instead of returning a manageable error.

### How to Fix It

Depending on whether you want to change your hardware or your software, you have two paths:

### Option 1: Update the VexRiscv Hardware Configuration (Recommended)

If you are generating the VexRiscv core yourself (via SpinalHDL), you need to enable the illegal instruction exception in your CPU plugin configuration.
• Look for your CsrPlugin config.
• Ensure that illegalInstruction or exception support is explicitly enabled.

### Option 2: Adjust your Rust Compilation (Software Workaround)

If you cannot change the hardware, you must ensure Rust never generates instructions the CPU doesn't explicitly support:
• Check your target features: Make sure your Rust compilation target precisely matches your VexRiscv extensions (e.g., riscv32im-unknown-none-elf). Do not compile for riscv32imc if your hardware lacks compressed instruction support.
• Custom panic handler: Ensure your #[panic_handler] in no-std Rust uses a looping mechanism or a hardware-supported breakpoint/abort register rather than relying on an illegal instruction to stop the core.

To help narrow down the best solution:
• Are you generating the VexRiscv core yourself, or using a pre-compiled bitstream?
• What ISA extensions (e.g., I, M, A, C) are enabled on your VexRiscv hardware?
