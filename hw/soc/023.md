## 1. 먼저 Error Response의 동작을 정의하겠습니다

현재 메모리 맵은 다음과 같습니다.

| 주소 범위                     | 장치       | 처리       |
| ------------------------- | -------- | -------- |
| `0x00000000 ~ 0x000003FF` | Data RAM | 정상 접근    |
| 그 외 주소                    | Unmapped | Error 처리 |

이번 단계에서는 Unmapped 주소에 대한 Load 요청을 우선 처리하겠습니다.

정상 RAM Load와 Unmapped Load의 동작은 다음과 같습니다.

정상 RAM Load

1. CPU가 Load 명령을 전송합니다.
2. Decoder가 RAM 주소임을 확인하고 RAM으로 전달합니다.
3. RAM이 읽은 데이터를 응답합니다.
4. Decoder가 데이터를 CPU에 전달하고 `error = 0`을 반환합니다.

Unmapped Load

1. CPU가 Load 명령을 전송합니다.
2. Decoder가 RAM 주소가 아님을 확인합니다.
3. Decoder가 요청을 수락하고 내부적으로 Error Response를 예약합니다.
4. 다음 Clock Cycle에 `ready = 1`, `error = 1`, `data = 0`을 CPU에 반환합니다.

여기서 `DBusSimpleRsp.ready`는 CPU가 응답을 받을 수 있다는 뜻이 아니라 응답 데이터가 유효하다는 표시입니다. 기존에 확인했던 VexRiscv 소스와 동일한 의미입니다.


## 2. 중요한 VexRiscv 설정도 확인했습니다

이번 단계에서 놓치면 안 되는 부분이 있습니다.

현재 사용 중인 VexRiscv의 `DBusSimplePlugin`은 다음과 같이 정의되어 있습니다.

```
class DBusSimplePlugin(
  catchAddressMisaligned: Boolean = false,
  catchAccessFault: Boolean = false,
  ...
)
```

즉, `catchAccessFault`의 기본값은 `false`입니다.

또한 정확히 사용 중인 commit의 소스를 확인한 결과, `catchAccessFault`가 활성화되어 있을 때 `rsp.ready && rsp.error`인 Load에 대해 Load Access Fault 예외 코드 5를 발생시킵니다.
Store Access Fault는 이 코드 경로에서 처리하지 않습니다.


따라서 두 가지를 구분해서 진행하겠습니다.

1. Decoder가 Unmapped Load에 Error Response를 반환하는 기능.
2. CPU가 그 Error Response를 실제 RISC-V 예외로 처리하는 기능.

이번에는 우선 첫 번째 기능을 구현하고 검증하겠습니다. Store Access Fault는 별도의 후속 작업으로 다루는 것이 정확합니다.
