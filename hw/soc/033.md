DBusDecoder가 "store unmapped-address" 를 수락한 사이클과 동일한 사이클에서 exceptionPort.valid := true 가
되면 그 다음, 어떤 경로(RTL sequential and/or combinational circuit)를 통해서 수락된 그 "store unmapped-address" 명령어의
바로 다음 명령어가 trap handler 시작 주소에 있는 명령어가 되는지 RTL 소스 코드 수준에서 설명해 줘.

---

질문의 핵심은 정확합니다. 단순히 `exceptionPort.valid := storeFault`가 같은 사이클에 참이 된다고 해서, 자동으로 다음 명령어의 PC가 `mtvec`로 바뀌는 것은 아닙니다.

실제로 다음 명령어가 Trap Handler의 첫 명령어가 되려면 VexRiscv 내부에서 다음 세 동작이 연결되어야 합니다.

1. Store 명령에 대한 예외가 Execute stage에서 인식되어야 합니다.
2. 예외가 발생한 Store 명령과 그보다 뒤에 있는 명령들이 파이프라인에서 제거(flush)되어야 합니다.
3. 예외 처리기가 다음 Instruction Fetch 주소를 `mtvec`로 변경해야 합니다.

이 세 동작이 어떤 조합회로와 순차회로를 통해 이루어지는지, 현재 사용 중인 VexRiscv 구조를 기준으로 구분해서 설명하겠습니다.

## 1. 사이클 N: Store 명령이 수락되는 순간

현재 DBusSimplePlugin의 명령 생성 코드는 다음과 같습니다.

`DBusSimplePlugin.scala`

```scala
val cmdStage = if(emitCmdInMemoryStage) memory else execute

dBus.cmd.valid :=
  arbitration.isValid &&
  input(MEMORY_ENABLE) &&
  !arbitration.isStuckByOthers &&
  !arbitration.isFlushed &&
  !skipCmd &&
  !cmdSent

dBus.cmd.wr := input(MEMORY_STORE)
```

현재 CPU 설정에서는 `emitCmdInMemoryStage`가 활성화되어 있지 않으므로 `cmdStage`는 Execute입니다. 주소는 다음과 같이 만들어집니다.

```scala
dBus.cmd.address := input(SRC_ADD).asUInt
```

이제 Execute stage에 다음 명령이 있다고 가정하겠습니다.

```
sw x1, 0(x10)
```

그리고 유효 주소가 `0x20000000`이라고 가정합니다.

DBusDecoder에서 Unmapped Store를 받아들이도록 변경한 상태라면 다음 신호가 성립합니다.

```scala
io.cpu.cmd.ready := True

io.storeFault :=
  io.cpu.cmd.fire &&
  io.cpu.cmd.wr &&
  !ramHit &&
  !gpioHit
```

결과적으로 해당 사이클의 신호는 다음과 같습니다.

| 신호                 | 값            | 의미                   |
| ------------------ | ------------ | -------------------- |
| `dBus.cmd.valid`   | 1            | Execute의 Store 명령 유효 |
| `dBus.cmd.wr`      | 1            | Store 명령             |
| `dBus.cmd.address` | `0x20000000` | 접근 주소                |
| `dBus.cmd.ready`   | 1            | DBusDecoder가 명령 수락   |
| `dBus.cmd.fire`    | 1            | 실제 handshake         |
| `storeFault`       | 1            | Unmapped Store 감지    |

그리고 신규 플러그인의 다음 코드가 실행됩니다.

```scala
exceptionPort.valid := storeFault
exceptionPort.code  := 7
exceptionPort.badAddr := dbusPlugin.dBus.cmd.address
```

따라서 같은 사이클에 다음 예외 정보가 CsrPlugin에 전달됩니다.

```scala
exceptionPort.valid   = 1
exceptionPort.code    = 7
exceptionPort.badAddr = 0x20000000
```

여기까지는 모두 조합회로(combinational logic) 입니다.

아직 `mtvec`로 PC가 바뀐 것은 아닙니다.

## 2. 사이클 N: CsrPlugin의 예외 감지와 파이프라인 Flush

이제 중요한 부분입니다.

`CsrPlugin.scala`의 예외 포트 등록 코드를 보겠습니다.

```scala
override def newExceptionPort(
  stage: Stage,
  priority: Int = 0,
  codeWidth: Int = 4
) = {
  val interface = Flow(ExceptionCause(codeWidth))
  exceptionPortsInfos +=
    ExceptionPortInfo(interface, stage, priority, codeWidth)
  interface
}
```

우리가 신규 플러그인에서 다음과 같이 등록했으므로,

```scala
exceptionService.newExceptionPort(pipeline.execute)
```

이 예외 포트는 Execute stage에 소속됩니다.

CsrPlugin의 실제 예외 처리 코드 중 핵심은 다음입니다.

```scala
for(portInfo <- sortedByStage;
    port = portInfo.port;
    stage = portInfo.stage;
    stageId = indexOf(portInfo.stage)) {

  when(port.valid) {
    stage.arbitration.flushNext := True
    stage.arbitration.removeIt := True

    exceptionValids(stageId) := True
    exceptionContext := port.payload
  }
}
```

`port.valid = 1`이므로 Execute stage에서 다음 두 신호가 활성화됩니다.

```scala
execute.arbitration.flushNext := True
execute.arbitration.removeIt := True
```

두 신호의 의미가 다릅니다.

- `removeIt`: Execute stage의 현재 명령을 정상적인 파이프라인 명령으로 취급하지 않도록 제거합니다.
- `flushNext`: 이보다 앞선 stage에 있는 더 젊은 명령들을 제거하도록 합니다.

### 실제 Flush가 만들어지는 RTL

`Pipeline.scala`에는 다음 코드가 있습니다.

```scala
stage.arbitration.isFlushed :=
  stages.drop(stageIndex + 1)
    .map(_.arbitration.flushNext).orR ||
  stages.drop(stageIndex)
    .map(_.arbitration.flushIt).orR

if(!unremovableStages.contains(stage))
  stage.arbitration.removeIt setWhen
    stage.arbitration.isFlushed
```

파이프라인의 stage 순서가 다음과 같다고 생각하면 됩니다.

```
Decode → Execute → Memory → WriteBack
```

Execute에서 `flushNext = 1`이 발생하면:

```
Decode     : isFlushed = 1 → removeIt
Execute    : removeIt = 1
Memory     : 이 예외 때문에 직접 flush되지 않음
WriteBack  : 이 예외 때문에 직접 flush되지 않음
```

즉, Store 명령과 그 뒤에 실행되려고 했던 젊은 명령들은 제거되고, 이미 Store보다 앞서 실행 중이던 오래된 명령들은 보존됩니다.

그리고 Fetcher에도 Flush가 전달됩니다. Fetcher의 코드에서:

```scala
val externalFlush =
  stages.map(_.arbitration.flushNext).orR
```

Fetch 응답 파이프라인도 이 신호를 이용해 잘못된 경로에서 가져온 명령어를 제거합니다.

### 이 시점에서 Store의 PC는 어떻게 보존되는가?

여기서 매우 중요한 세부 사항이 있습니다.

예외 발생 명령은 `removeIt` 때문에 정상적인 유효 명령으로 다음 stage에 전달되지 않습니다. 그러나 PC 등의 stage 데이터 전달은 `isValid` 전달과 별도로 동작합니다.

`Pipeline.scala`의 stage 데이터 연결 부분은 다음과 같습니다.

```scala
inputDefault :=
  RegNextWhen(
    stageBefore.output(key),
    !stage.arbitration.isStuck
  )
```

즉, PC 데이터의 전달 조건은 `!stage.arbitration.isStuck`이며, `removeIt` 자체가 데이터 전달을 막는 조건은 아닙니다.

이것이 중요한 이유는 CsrPlugin이 예외 명령의 PC를 마지막 stage에서 캡처할 수 있도록 파이프라인 데이터 경로를 유지하기 때문입니다.

## 3. 사이클 N 이후: 예외 정보가 파이프라인을 따라 이동

CsrPlugin은 예외가 발생한 stage의 예외 정보를 그 자리에서 곧바로 Trap 처리하지 않습니다.

대신 다음 코드를 사용합니다.

```scala
for(stageId <- firstStageIndexWithExceptionPort
    until stages.length;
    stage = stages(stageId)) {

  val previousStage =
    if(stageId == firstStageIndexWithExceptionPort)
      stage
    else
      stages(stageId - 1)

  when(!stage.arbitration.isStuck) {
    exceptionValidsRegs(stageId) :=
      if(stageId != firstStageIndexWithExceptionPort)
        exceptionValids(stageId - 1) &&
        !previousStage.arbitration.isStuck
      else
        False
  } otherwise {
    if(stage != stages.last)
      exceptionValidsRegs(stageId) :=
        exceptionValids(stageId)
    else
      exceptionValidsRegs(stageId) := False
  }
}
```

이것은 예외 발생을 나타내는 별도의 valid 파이프라인입니다.

현재 Store Access Fault가 Execute stage에서 발생했으므로 예외 정보가 다음과 같이 이동합니다.

```
Execute → Memory → WriteBack
```

실제 stage가 정지하면 예외 valid도 함께 유지됩니다.

동시에 예외 주소와 원인 코드는 다음 레지스터에 저장됩니다.

```scala
val exceptionContext =
  Reg(ExceptionCause(codeWidth))
```

예외가 처음 발생한 사이클에:

```scala
exceptionContext := port.payload
```

이 실행되므로 `code=7`, `badAddr=0x20000000`이 보존됩니다.

그리고 CsrPlugin은 마지막 stage의 PC가 예외 처리 중 변경되지 않도록 다음 코드를 사용합니다.

```scala
stages.last.dontSample
  .getOrElseUpdate(PC, ArrayBuffer[Bool]()) +=
  exceptionValids.last
```

따라서 예외 valid가 마지막 stage에 도달했을 때, 그 stage의 PC 데이터는 예외를 발생시킨 Store 명령의 PC를 유지할 수 있습니다.

## 4. 마지막 stage: 실제 Trap 진입 신호 생성

CsrPlugin에는 다음 코드가 있습니다.

```scala
val exception =
  if(exceptionPortCtrl != null)
    exceptionPortCtrl.exceptionValids.last &&
    allowException
  else
    False

val hadException =
  RegNext(exception) init(False)
```

이 부분을 정확하게 구분해야 합니다.

- `exception`: 마지막 stage에서 예외 valid가 확인되는 조합 신호
- `hadException`: 그 예외 신호를 클록 에지에서 샘플링한 순차 신호

즉, 예외가 마지막 stage에 도달한 다음 클록 에지에서 `hadException`이 1이 됩니다.

그다음 실제 Trap 진입 코드가 실행됩니다.

```scala
when(hadException || interruptJump) {

  trapEvent := True

  fetcher.haltIt()

  jumpInterface.valid := True

  jumpInterface.payload :=
    xtvec.base @@ U"00"

  lastStage.arbitration.flushNext := True

  ...
}
```

여기서 세 가지가 핵심입니다.

1. `fetcher.haltIt()`은 Trap 주소로 전환하는 동안 새로운 Fetch를 정지시킵니다.
2. `jumpInterface.valid := True`는 PC 변경 요청을 발생시킵니다.
3. `jumpInterface.payload`는 Trap Handler 시작 주소를 전달합니다.

이제 `mtvec`가 어떻게 주소로 만들어지는지 보겠습니다.

현재 설정:

```scala
CsrPluginConfig
  .smallest(BigInt("80000120", 16))
```

CsrPlugin은 초기화할 때 다음과 같이 설정합니다.

```scala
val mtvec = Reg(Xtvec()).allowUnsetRegToAvoidLatch

if(mtvecInit != null)
  mtvec.mode init(mtvecInit & 0x3)

if(mtvecInit != null)
  mtvec.base init(mtvecInit / 4)
```

그리고 Trap 주소를 만들 때:

```scala
jumpInterface.payload :=
  xtvec.base @@ U"00"
```

따라서 현재 설정에서 Trap 주소는 다음과 같습니다.

$$ \text{mtvec.base} = 0x80000120 / 4 $$

$$ \text{Trap PC} = \text{mtvec.base} \times 4                  = 0x80000120 $$


이 시점에서 CsrPlugin은 CSR도 갱신합니다.

```scala
mstatus.MIE  := False
mstatus.MPIE := mstatus.MIE
mstatus.MPP  := privilege

mcause.interrupt := !hadException
mcause.exceptionCode := trapCause

mepc := mepcCaptureStage.input(PC)

mtval := exceptionPortCtrl.exceptionContext.badAddr
```

따라서 이번 Store Access Fault라면 기대값은 다음과 같습니다.

| CSR      | 기대값                   |
| -------- | --------------------- |
| `mcause` | `7`                   |
| `mepc`   | Unmapped Store 명령의 PC |
| `mtval`  | `0x20000000`          |


## 5. 마지막 연결: Fetch PC가 Trap 주소로 바뀌는 경로

이제 질문의 가장 중요한 부분입니다.

CsrPlugin이 만든 `jumpInterface`는 `JumpService`를 통해 Fetcher에 등록되어 있습니다.

Fetcher의 `createJumpInterface()`는 다음과 같습니다.

```scala
override def createJumpInterface(
  stage: Stage,
  priority: Int = 0
): Flow[UInt] = {

  val interface = Flow(UInt(32 bits))

  jumpInfos += JumpInfo(interface, stage, priority)

  interface
}
```

Fetcher는 등록된 Jump 요청들을 우선순위에 따라 선택합니다.

```scala
val pcLoad = Flow(UInt(32 bits))

pcLoad.valid :=
  jumpInfos.map(_.interface.valid).orR

pcLoad.payload :=
  MuxOH(
    OHMasking.first(valids.asBits),
    pcs
  )
```

그다음 실제 Fetch PC 레지스터를 갱신하는 부분입니다.

```scala
val pcReg =
  Reg(UInt(32 bits)) init(resetVector)

val correction = False

val pc = pcReg + (inc ## B"00").asUInt

when(jump.pcLoad.valid) {
  correction := True
  pc := jump.pcLoad.payload
  flushed := True
}

when(booted &&
     (output.ready || correction || pcRegPropagate)) {
  pcReg := pc
}

output.valid := !fetcherHalt && booted
output.payload := pc
```

여기서 조합회로와 순차회로의 역할이 분명하게 나뉩니다.

조합회로 경로

`CsrPlugin.jumpInterface.valid`

`Fetcher.jump.pcLoad.valid`

`fetchPc.correction = True`

`fetchPc.pc = 0x80000120`

순차회로 경로

클록 상승 에지

`fetchPc.pcReg := 0x80000120`

Fetch 재개

`IBus CMD PC = 0x80000120`

Trap Handler 첫 명령어 Fetch

특히 다음 코드가 중요합니다.

```scala
when(jump.pcLoad.valid) {
  correction := True
  pc := jump.pcLoad.payload
}

when(booted &&
     (output.ready || correction || pcRegPropagate)) {
  pcReg := pc
}
```

`correction`이 조합회로에서 참이 되면 Fetch PC 레지스터는 다음 클록 에지에서 Trap 주소를 저장합니다.

그리고 `fetcherHalt`가 해제되어 Fetch가 재개되면 해당 주소가 Instruction Bus로 전달됩니다.

## 6. 전체 동작을 시간 순서로 정리

지금까지 분석한 내용을 한 표로 합치면 다음과 같습니다.

| 시점                | Store 명령             | 예외 처리                                   | Fetch                   |
| ----------------- | -------------------- | --------------------------------------- | ----------------------- |
| N                 | Execute에서 Store 실행   | `storeFault=1`, `exceptionPort.valid=1` | 정지 시작                   |
| N 클록 에지           | Store 제거             | 예외 정보 레지스터에 저장                          | 잘못된 Fetch 명령 제거         |
| N+1 이후            | Store 정상 실행 경로에서 제거됨 | Exception valid가 Memory/WB로 이동          | 정지 유지                   |
| 마지막 stage 도달      | 예외 명령의 PC 데이터 유지     | `exception=1`                           | 정지 유지                   |
| 다음 클록 에지          | —                    | `hadException=1`                        | Trap redirect 준비        |
| Trap redirect 사이클 | —                    | `mcause`, `mepc`, `mtval` 갱신            | `jumpInterface.valid=1` |
| redirect 클록 에지    | —                    | Trap 상태 저장                              | `pcReg=0x80000120`      |
| 이후                | —                    | Trap Handler 실행 준비 완료                   | `0x80000120` Fetch      |

여기서 꼭 구분해야 할 점은 Unmapped Store를 수락한 바로 다음 클록에 Trap Handler 명령이 Fetch되는 것은 아니라는 사실입니다.

예외 정보가 파이프라인을 따라 이동하고, 마지막 stage에서 Trap 진입 조건이 성립한 후 Fetch PC가 변경됩니다. 그동안 Fetch는 정지하고 잘못된 경로의 명령은 제거됩니다.

## 7. 현재 구현에서 추가로 주의할 점

이 분석을 통해 앞서 제시한 `StoreAccessFaultPlugin`의 구조적 의도는 설명할 수 있지만, 실제 RTL이 올바르게 동작한다고 확정하려면 아직 시뮬레이션 검증이 필요합니다.

특히 다음 세 가지를 파형으로 확인해야 합니다.

1. `storeFault`와 `execute.arbitration.removeIt`가 동일 사이클에 1이 되는가?
2. `exceptionValids`가 Execute에서 Memory, WriteBack으로 이동하는가?
3. `hadException`이 1이 된 뒤 `jumpInterface.valid`와 Fetch PC가 `0x80000120`으로 변경되는가?

제가 가장 중요하게 보는 파형 신호는 다음입니다.

```scala
dBus.cmd.valid
dBus.cmd.ready
dBus.cmd.wr
dBus.cmd.address

storeFault

execute.arbitration.removeIt
execute.arbitration.flushNext

exceptionPort.valid
exceptionValids.execute
exceptionValids.memory
exceptionValids.writeBack

hadException

jumpInterface.valid
jumpInterface.payload

fetchPc.pcReg
instructionRom.io.cmd.valid
instructionRom.io.cmd.pc
```

결론: Store 명령의 handshake와 `exceptionPort.valid`는 같은 사이클에 발생하지만, Trap Handler의 첫 명령어가 Fetch되는 것은 그 이후입니다. 연결 경로는 `ExceptionPort → CsrPlugin 예외 파이프라인 및 Flush → hadException → JumpService → Fetcher PC correction → pcReg`입니다. 이 경로는 단순한 `RegNext(storeFault)` 한 개가 아니라, VexRiscv의 기존 예외 전달·파이프라인 제어·Fetch PC 갱신 구조를 모두 이용합니다.
