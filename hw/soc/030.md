현재 로그의 제목이 `VexRiscv Trap Error Path Verification`인 것으로 보아, 방금 실행한 것은 기존 Trap 테스트입니다. 이 테스트는 정상 통과했으므로 회귀 테스트 기준으로 보관하겠습니다.

### 2. GPIO 테스트 프로그램 실행

앞서 제시한 GPIO 테스트용 `InstructionRom`과 `VexRiscvTopSim`으로 교체합니다.

테스트 프로그램의 실행 순서는 다음과 같습니다.

| 순서 | CPU 명령                 | 검증 내용             |
| -- | ---------------------- | ----------------- |
| 1  | GPIO_OUT에 `0x5A` Store | GPIO 출력 레지스터 쓰기   |
| 2  | GPIO_OUT Load          | 출력 레지스터 읽기        |
| 3  | RAM[0]에 결과 Store       | 읽은 값 확인           |
| 4  | GPIO_OE에 `1` Store     | 출력 Enable 설정      |
| 5  | GPIO_IN Load           | 외부 입력 읽기          |
| 6  | RAM[1]에 결과 Store       | 입력값 확인            |
| 7  | RAM[3]에 `0x33` Store   | 예약 주소 테스트용 기준값    |
| 8  | RAM[3] Load            | RAM 응답 라우팅 확인     |
| 9  | GPIO 예약 주소 Load        | Error Response 확인 |

### 3. 기대 결과

기대값

| 항목          | 기대값          |
| ----------- | ------------ |
| `gpioOut`   | `0x0000005A` |
| `gpioOe`    | `0x00000001` |
| RAM[0]      | `0x0000005A` |
| RAM[1]      | `0xA5C369F0` |
| RAM[3]      | `0x00000033` |
| RAM[4]      | `0x00000033` |
| Load 응답 횟수  | 3            |
| Error 응답 횟수 | 0            |

참고로 여기서 GPIO 예약 주소 Load는 이전 테스트 프로그램에서 `0x0000000C`가 아니라 RAM 주소 `0x0000000C`를 대상으로 하고 있으므로, 앞서 제시한 테스트 프로그램의 주소 배치를 다시 확인해야 합니다. GPIO 예약 주소 `0x1000000C`를 테스트하려면 별도의 Load 명령이 필요합니다. 이 부분은 실제 테스트 전에 수정해야 합니다.

먼저 중요한 설계 조건이 있습니다.

- 현재 `mtvec`는 `0x80000020`입니다.
- 따라서 GPIO 테스트 프로그램이 `0x80000020`을 일반 코드로 사용하면 안 됩니다.
- 메인 프로그램은 `0x8000001C`에서 `0x80000040`으로 점프하게 하겠습니다.
- `0x80000020`에는 Trap Handler를 배치하고, 예약 GPIO 주소 Load가 발생하면 이곳으로 진입하는지 확인하겠습니다.

## 1. GPIO 통합 테스트 프로그램 구성

테스트 주소는 다음과 같습니다.

| 주소                           | 용도                    |
| ---------------------------- | --------------------- |
| `0x10000000`                 | GPIO_OUT              |
| `0x10000004`                 | GPIO_IN               |
| `0x10000008`                 | GPIO_OE               |
| `0x1000000C`                 | Reserved (Load Error) |
| `0x00000000` \~ `0x00000010` | RAM 테스트 영역            |

테스트 순서는 다음과 같습니다.

1. GPIO_OUT에 `0x5A` 쓰기 및 읽기
2. 읽은 값을 RAM[0]에 저장
3. GPIO_OE에 `1` 쓰기 및 읽기
4. 읽은 값을 RAM[1]에 저장
5. 외부 GPIO 입력 `0xA5C369F0` 읽기
6. 읽은 값을 RAM[2]에 저장
7. RAM[3]에 `0x33` 쓰기 및 읽기
8. 읽은 값을 RAM[4]에 저장
9. GPIO 예약 주소 `0x1000000C` Load
10. Trap Handler 진입 및 반복 실행 확인

## 2. InstructionRom.scala

기존 파일을 다음 코드로 교체하세요.

GPIO CPU 통합 테스트용 ROM — SpinalHDL 1.13.0 프로젝트 기준

```scala
package myvexsoc

import spinal.core._
import spinal.lib._
import vexriscv.plugin._

class InstructionRom extends Component {
  val io = new Bundle {
    val cmd = slave(Stream(IBusSimpleCmd()))
    val rsp = master(Flow(IBusSimpleRsp()))
  }

  // ----------------------------------------------------------------
  // RISC-V instructions
  // ----------------------------------------------------------------

  // Main program: 0x80000000 ~ 0x8000001C
  val LUI_X10_10000 = B"x10000537" // LUI  x10, 0x10000
  val ADDI_X1_X0_5A = B"x05A00093" // ADDI x1, x0, 0x5A
  val SW_X1_0_X10   = B"x00152023" // SW   x1, 0(x10)
  val LW_X2_0_X10   = B"x00052103" // LW   x2, 0(x10)
  val SW_X2_0_X0    = B"x00202023" // SW   x2, 0(x0)
  val ADDI_X3_X0_1  = B"x00100193" // ADDI x3, x0, 1
  val SW_X3_8_X10   = B"x00352423" // SW   x3, 8(x10)
  val JAL_X0_40     = B"x0240006F" // JAL  x0, 0x80000040

  // Trap handler: mtvec = 0x80000020
  val JAL_X0_0      = B"x0000006F" // JAL x0, 0

  // GPIO/RAM test: 0x80000040 ~
  val LW_X4_8_X10   = B"x00852203" // LW   x4, 8(x10)
  val SW_X4_4_X0    = B"x00402223" // SW   x4, 4(x0)

  val LW_X5_4_X10   = B"x00452283" // LW   x5, 4(x10)
  val SW_X5_8_X0    = B"x00502423" // SW   x5, 8(x0)

  val ADDI_X6_X0_33 = B"x03300313" // ADDI x6, x0, 0x33
  val SW_X6_12_X0   = B"x00602623" // SW   x6, 12(x0)

  val LW_X7_12_X0   = B"x00C02383" // LW   x7, 12(x0)
  val SW_X7_16_X0   = B"x00702823" // SW   x7, 16(x0)

  val LW_X8_12_X10  = B"x00C52403" // LW   x8, 12(x10)

  val NOP = B"x00000013"

  // ----------------------------------------------------------------
  // Instruction ROM
  // ----------------------------------------------------------------

  io.cmd.ready := True

  val instruction = Bits(32 bits)
  instruction := NOP

  switch(io.cmd.pc) {

    // Main program
    is(U"32'h80000000") { instruction := LUI_X10_10000 }
    is(U"32'h80000004") { instruction := ADDI_X1_X0_5A }
    is(U"32'h80000008") { instruction := SW_X1_0_X10 }
    is(U"32'h8000000C") { instruction := LW_X2_0_X10 }
    is(U"32'h80000010") { instruction := SW_X2_0_X0 }
    is(U"32'h80000014") { instruction := ADDI_X3_X0_1 }
    is(U"32'h80000018") { instruction := SW_X3_8_X10 }
    is(U"32'h8000001C") { instruction := JAL_X0_40 }

    // Trap handler
    is(U"32'h80000020") { instruction := JAL_X0_0 }
    is(U"32'h80000024") { instruction := NOP }

    // GPIO/RAM test program
    is(U"32'h80000040") { instruction := LW_X4_8_X10 }
    is(U"32'h80000044") { instruction := SW_X4_4_X0 }

    is(U"32'h80000048") { instruction := LW_X5_4_X10 }
    is(U"32'h8000004C") { instruction := SW_X5_8_X0 }

    is(U"32'h80000050") { instruction := ADDI_X6_X0_33 }
    is(U"32'h80000054") { instruction := SW_X6_12_X0 }

    is(U"32'h80000058") { instruction := LW_X7_12_X0 }
    is(U"32'h8000005C") { instruction := SW_X7_16_X0 }

    // Reserved GPIO register access: must generate Load Access Fault
    is(U"32'h80000060") { instruction := LW_X8_12_X10 }

    // Should not reach this instruction if Trap works
    is(U"32'h80000064") { instruction := JAL_X0_0 }
  }

  // One-cycle instruction response
  io.rsp.valid := RegNext(io.cmd.fire) init (False)
  io.rsp.inst := RegNextWhen(instruction, io.cmd.fire) init (NOP)
  io.rsp.error := False
}
```

### 명령어 배치 검토

| PC           | 명령       | 목적                   |
| ------------ | -------- | -------------------- |
| `0x80000000` | LUI x10  | GPIO Base Address 설정 |
| `0x80000008` | SW       | GPIO_OUT 쓰기          |
| `0x8000000C` | LW       | GPIO_OUT 읽기          |
| `0x80000018` | SW       | GPIO_OE 쓰기           |
| `0x8000001C` | JAL      | 테스트 코드로 이동           |
| `0x80000020` | JAL x0,0 | Trap Handler         |
| `0x80000040` | LW       | GPIO_OE 읽기           |
| `0x80000048` | LW       | GPIO_IN 읽기           |
| `0x80000058` | LW       | RAM 읽기               |
| `0x80000060` | LW       | GPIO 예약 주소 접근        |

명령어 인코딩은 RISC-V I/S/U/J 형식의 필드 배치를 기준으로 계산했습니다. 특히 `JAL x0, 0x80000040`의 상대 오프셋은 `+0x24`입니다.

## 3. VexRiscvTopSim.scala

다음은 CPU 통합 테스트벤치입니다.

기존 Trap 테스트벤치의 모니터링 방식처럼 Falling Edge에서 DBus 명령과 응답을 관찰합니다. `DBusSimpleRsp.ready`는 응답 valid 신호라는 점도 반영했습니다.

```scala
package myvexsoc

import spinal.core._
import spinal.core.sim._
import vexriscv.plugin._

import scala.collection.mutable

object VexRiscvTopSim extends App {

  // ------------------------------------------------------------
  // Test configuration
  // ------------------------------------------------------------

  val GPIO_OUT_ADDR = BigInt("10000000", 16)
  val GPIO_IN_ADDR  = BigInt("10000004", 16)
  val GPIO_OE_ADDR  = BigInt("10000008", 16)
  val GPIO_RESERVED = BigInt("1000000C", 16)

  val RAM0 = BigInt("00000000", 16)
  val RAM1 = BigInt("00000004", 16)
  val RAM2 = BigInt("00000008", 16)
  val RAM3 = BigInt("0000000C", 16)
  val RAM4 = BigInt("00000010", 16)

  val GPIO_OUT_EXPECTED = BigInt("0000005A", 16)
  val GPIO_OE_EXPECTED  = BigInt("00000001", 16)
  val GPIO_IN_EXPECTED  = BigInt("A5C369F0", 16)
  val RAM3_EXPECTED     = BigInt("00000033", 16)

  val TRAP_PC = BigInt("80000020", 16)
  val MAX_CYCLES = 300

  def hex(value: BigInt, width: Int = 8): String = {
    "0x" + value.toString(16).toUpperCase.reverse.padTo(width, '0').reverse
  }

  // ------------------------------------------------------------
  // Simulation
  // ------------------------------------------------------------

  SimConfig.withWave.compile(new VexRiscvTop).doSim { dut =>

    dut.clockDomain.forkStimulus(period = 10)

    // External GPIO input
    dut.io.gpioIn #= GPIO_IN_EXPECTED

    val dbusPlugin =
      dut.system.cpu.plugins
        .collectFirst { case p: DBusSimplePlugin => p }
        .get

    val rom = dut.system.instructionRom

    // ----------------------------------------------------------
    // Scoreboard / monitor state
    // ----------------------------------------------------------

    val stores = mutable.Map.empty[BigInt, BigInt]
    val loadAddresses = mutable.ArrayBuffer.empty[BigInt]
    val responseAddresses = mutable.ArrayBuffer.empty[BigInt]
    val pendingLoads = mutable.Queue.empty[BigInt]

    var storeCount = 0
    var loadCount = 0
    var responseCount = 0
    var errorResponseCount = 0
    var trapFetchCount = 0

    println()
    println("========================================")
    println(" VexRiscv GPIO Integration Verification")
    println("========================================")

    // ----------------------------------------------------------
    // Main monitor loop
    // ----------------------------------------------------------

    for (cycle <- 0 until MAX_CYCLES) {

      dut.clockDomain.waitFallingEdge()

      // --------------------------------------------------------
      // 1. DBus response monitor
      //
      // DBusSimpleRsp.ready means response-valid.
      // --------------------------------------------------------

      val rspValid = dbusPlugin.dBus.rsp.ready.toBoolean

      if (rspValid) {

        assert(
          pendingLoads.nonEmpty,
          s"Unexpected DBus response at cycle $cycle"
        )

        val responseAddress = pendingLoads.dequeue()
        val responseData = dbusPlugin.dBus.rsp.data.toBigInt
        val responseError = dbusPlugin.dBus.rsp.error.toBoolean

        responseCount += 1
        responseAddresses += responseAddress

        if (responseError) {
          errorResponseCount += 1

          println(
            s"Cycle $cycle : LOAD RSP addr=${hex(responseAddress)} " +
              s"data=${hex(responseData)} error=true"
          )
        } else {
          println(
            s"Cycle $cycle : LOAD RSP addr=${hex(responseAddress)} " +
              s"data=${hex(responseData)} error=false"
          )
        }
      }

      // --------------------------------------------------------
      // 2. DBus command monitor
      // --------------------------------------------------------

      val cmdValid = dbusPlugin.dBus.cmd.valid.toBoolean
      val cmdReady = dbusPlugin.dBus.cmd.ready.toBoolean

      if (cmdValid && cmdReady) {

        val address = dbusPlugin.dBus.cmd.address.toBigInt
        val write = dbusPlugin.dBus.cmd.wr.toBoolean
        val data = dbusPlugin.dBus.cmd.data.toBigInt
        val mask = dbusPlugin.dBus.cmd.mask.toBigInt

        if (write) {

          storeCount += 1
          stores(address) = data

          println(
            s"Cycle $cycle : STORE addr=${hex(address)} " +
              s"data=${hex(data)} mask=${hex(mask, 1)}"
          )

        } else {

          loadCount += 1
          loadAddresses += address
          pendingLoads.enqueue(address)

          println(
            s"Cycle $cycle : LOAD addr=${hex(address)}"
          )
        }
      }

      // --------------------------------------------------------
      // 3. Instruction fetch monitor
      // --------------------------------------------------------

      val fetchValid = rom.io.cmd.valid.toBoolean
      val fetchReady = rom.io.cmd.ready.toBoolean

      if (fetchValid && fetchReady) {

        val pc = rom.io.cmd.pc.toBigInt

        if (pc == TRAP_PC) {
          trapFetchCount += 1
        }

        if (pc == TRAP_PC || pc == BigInt("80000060", 16)) {
          println(s"Cycle $cycle : FETCH PC=${hex(pc)}")
        }
      }
    }

    // ------------------------------------------------------------
    // Final checks
    // ------------------------------------------------------------

    println()
    println("========================================")
    println(" GPIO Integration Verification Result")
    println("========================================")

    // GPIO external outputs
    assert(
      dut.io.gpioOut.toBigInt == GPIO_OUT_EXPECTED,
      s"GPIO_OUT mismatch: ${hex(dut.io.gpioOut.toBigInt)}"
    )
    println(s"[PASS] GPIO_OUT = ${hex(dut.io.gpioOut.toBigInt)}")

    assert(
      dut.io.gpioOe.toBigInt == GPIO_OE_EXPECTED,
      s"GPIO_OE mismatch: ${hex(dut.io.gpioOe.toBigInt)}"
    )
    println(s"[PASS] GPIO_OE = ${hex(dut.io.gpioOe.toBigInt)}")

    // RAM write results
    assert(stores.get(RAM0).contains(GPIO_OUT_EXPECTED))
    println(s"[PASS] RAM[0] = ${hex(stores(RAM0))}")

    assert(stores.get(RAM1).contains(GPIO_OE_EXPECTED))
    println(s"[PASS] RAM[1] = ${hex(stores(RAM1))}")

    assert(stores.get(RAM2).contains(GPIO_IN_EXPECTED))
    println(s"[PASS] RAM[2] = ${hex(stores(RAM2))}")

    assert(stores.get(RAM3).contains(RAM3_EXPECTED))
    println(s"[PASS] RAM[3] = ${hex(stores(RAM3))}")

    assert(stores.get(RAM4).contains(RAM3_EXPECTED))
    println(s"[PASS] RAM[4] = ${hex(stores(RAM4))}")

    // Load command sequence
    val expectedLoads = Seq(
      GPIO_OUT_ADDR,
      GPIO_OE_ADDR,
      GPIO_IN_ADDR,
      RAM3,
      GPIO_RESERVED
    )

    assert(
      loadAddresses.toSeq == expectedLoads,
      s"Load address sequence mismatch: ${loadAddresses.map(hex(_)).mkString(", ")}"
    )
    println("[PASS] Load address sequence")

    // Response sequence and error response
    assert(responseAddresses.toSeq == expectedLoads)
    assert(responseCount == 5)
    println(s"[PASS] Load response count = $responseCount")

    assert(errorResponseCount == 1)
    println(s"[PASS] Error response count = $errorResponseCount")

    assert(responseAddresses.last == GPIO_RESERVED)
    println("[PASS] GPIO reserved address error response")

    assert(pendingLoads.isEmpty)
    println("[PASS] No pending Load response")

    // Store count
    assert(storeCount == 7)
    println(s"[PASS] Store count = $storeCount")

    // Trap handler
    assert(
      trapFetchCount >= 2,
      s"Trap handler was not repeatedly fetched: $trapFetchCount"
    )
    println(s"[PASS] Trap handler repeated ($trapFetchCount fetches)")

    println()
    println("========================================")
    println(" [PASS] GPIO INTEGRATION SIMULATION PASS")
    println("========================================")
  }
}
```

## 4. 실행 전에 확인할 사항

이번 테스트에서 기대하는 최종 결과는 다음과 같습니다.

| 검증 항목        | 기대 결과        |
| ------------ | ------------ |
| GPIO_OUT     | `0x0000005A` |
| GPIO_OE      | `0x00000001` |
| RAM[0]       | `0x0000005A` |
| RAM[1]       | `0x00000001` |
| RAM[2]       | `0xA5C369F0` |
| RAM[3]       | `0x00000033` |
| RAM[4]       | `0x00000033` |
| Store 명령     | 7회           |
| Load 명령      | 5회           |
| Load 응답      | 5회           |
| Error 응답     | 1회           |
| Trap Handler | 반복 실행        |

주의: 위 코드는 현재까지 확인된 인터페이스와 명령어 인코딩을 바탕으로 작성한 테스트 초안입니다. 제가 여기서 사용자의 로컬 프로젝트를 직접 컴파일하거나 시뮬레이션할 수는 없으므로, 실행 성공을 미리 단정하지 않겠습니다.

먼저 컴파일을 진행하고, 컴파일이 성공하면 시뮬레이션을 실행해 주세요. 특히 `DBusDecoder`의 `loadOwner` 및 `errorPending` 타이밍과 GPIO 에러 응답이 CPU Trap으로 이어지는지를 로그로 확인하겠습니다.

이번에는 실패하더라도 여러 부분을 한꺼번에 수정하지 않고, 실제 명령 수락 시점 → 응답 발생 시점 → Trap 진입 시점 순서로 원인을 확인하겠습니다.

---

---

VexRiscv CPU 는 DBusSimpleRsp 로부터 error = true 신호를 받으면 무조건 
program count 에 U"32'h80000020" 값을 넣어 trap handler 로 점프하게 설계되어 있는가?

---

아닙니다. `DBusSimpleRsp.error = true`를 받으면 무조건 PC에 `0x80000020`을 넣는 구조는 아닙니다.

정확하게는 다음 세 단계로 동작합니다.

1. `DBusSimplePlugin`이 Load 응답의 에러를 감지합니다.
2. `ExceptionService`에 예외를 발생시킵니다.
3. `CsrPlugin`이 예외를 처리하면서 `mtvec`에 설정된 Trap Handler 주소로 제어를 이동시킵니다.

따라서 `0x80000020`은 DBusSimplePlugin에 고정된 주소가 아닙니다. 현재 프로젝트의 CSR 설정에서 `mtvec` 초기값으로 지정한 주소입니다.

## 1. DBusSimplePlugin에서 실제로 하는 일

사용 중인 VexRiscv 커밋 `baf7dc82f855eddaf5b0a20a6802c526f127e38`의 `DBusSimplePlugin.scala`를 확인하면 다음 코드가 있습니다.

```scala
if(catchAccessFault) {
  when(dBus.rsp.ready && dBus.rsp.error && !input(MEMORY_STORE)) {
    memoryExceptionPort.valid := True
    memoryExceptionPort.code := 5
  }
}
```

여기서 중요한 조건은 세 가지입니다.

| 조건                 | 의미                           |
| ------------------ | ---------------------------- |
| `catchAccessFault` | Access Fault 처리가 활성화되어 있어야 함 |
| `dBus.rsp.ready`   | Load 응답이 유효해야 함              |
| `dBus.rsp.error`   | 응답에 에러가 표시되어야 함              |
| `!MEMORY_STORE`    | Store가 아니라 Load여야 함          |

조건이 충족되면 `ExceptionService`에 예외를 전달합니다. 이때 예외 코드 `5`는 Load Access Fault입니다.

즉, DBusSimplePlugin 자체가 PC를 `0x80000020`으로 변경하는 것은 아닙니다.

## 2. CsrPlugin에서 Trap 처리

`DBusSimplePlugin`이 전달한 예외는 `CsrPlugin`이 처리합니다.

이때 CSR의 역할은 다음과 같습니다.

| CSR      | 역할                    |
| -------- | --------------------- |
| `mepc`   | 예외가 발생한 명령어의 PC 저장    |
| `mcause` | 예외 원인 저장              |
| `mtval`  | 예외와 관련된 주소 저장         |
| `mtvec`  | Trap Handler 진입 주소 지정 |

현재 프로젝트의 설정은 다음과 같습니다.

```scala
new CsrPlugin(
  CsrPluginConfig.smallest(BigInt("80000020", 16)).copy(
    mepcAccess = CsrAccess.READ_WRITE,
    mbadaddrAccess = CsrAccess.READ_ONLY
  )
)
```

`CsrPlugin.scala`에서는 `mtvec`의 초기값을 다음과 같이 설정합니다.

```scala
if(mtvecInit != null) mtvec.mode init(mtvecInit & 0x3)
if(mtvecInit != null) mtvec.base init(mtvecInit / 4)
```

따라서 현재 설정에서는:

- `mtvec.mode = 0` (Direct Mode)
- `mtvec.base = 0x20000008`
- 실제 Trap 주소 = `0x80000020`

입니다.

## 3. 전체 동작 흐름

```
DBusSimpleRsp: `ready = true`, `error = true`
  |
  v
DBusSimplePlugin: Load Access Fault 감지, `memoryExceptionPort.valid = true`, `code = 5`
  |
  v
ExceptionService → CsrPlugin: `mepc`, `mcause`, `mtval` 갱신
  |
  v
JumpService / PC Redirect: `mtvec`에 지정된 Trap 주소로 이동
  |
  v
# 0x80000020: Trap Handler 실행
```

## 4. 따라서 질문에 대한 정확한 답변

현재 프로젝트에서는 정상적인 Load Access Fault가 발생하면 `0x80000020`으로 Trap 진입합니다. 하지만 `error=true`만으로 무조건 그렇게 되는 것은 아닙니다.

예를 들어:

- `catchAccessFault = false`이면 DBus 응답 에러를 이 경로에서 Trap으로 변환하지 않습니다.
- `rsp.ready = false`이면 아직 유효한 응답이 아니므로 에러를 처리하지 않습니다.
- Store 응답 에러는 위 코드의 `!MEMORY_STORE` 조건 때문에 이 경로에서 Load Access Fault로 처리되지 않습니다.
- 소프트웨어가 `mtvec`를 변경하면 Trap 진입 주소도 달라질 수 있습니다.

이 구분은 GPIO 설계에서 중요합니다. GPIO Peripheral이나 DBusDecoder가 담당하는 일은 에러 응답을 올바르게 반환하는 것이고, Trap 진입과 PC 변경은 VexRiscv의 ExceptionService와 CsrPlugin이 담당합니다.

다음에는 `ExceptionService`가 예외를 전달하고 `CsrPlugin`이 실제 PC Redirect를 발생시키는 부분을 소스 코드에서 추적하면 CPU의 Trap 처리 구조를 더 정확하게 이해할 수 있습니다.

## 1. 왜 Cycle 20에 0x80000020을 Fetch했을까?

테스트 프로그램의 해당 부분을 보겠습니다.

```
// PC = 0x80000018
SW x3, 8(x10)

// PC = 0x8000001C
JAL x0, 0x80000040

// PC = 0x80000020
JAL x0, 0
```

`JAL x0, 0x80000040`은 현재 PC에서 `0x24`만큼 이동합니다.

\\[ 0x8000001C + 0x24 = 0x80000040 \\]

그런데 VexRiscv는 명령어를 Fetch하고 실행하는 파이프라인 구조입니다.

`BranchPlugin(earlyBranch = false)` 설정에서는 분기 결정이 Fetch 단계보다 뒤에서 이루어질 수 있습니다.

따라서 다음과 같은 일이 가능합니다.

1. CPU가 `0x8000001C`의 JAL 명령을 Fetch합니다.
2. 다음 순차 주소인 `0x80000020`도 Fetch 요청합니다.
3. JAL의 분기 결과가 확정됩니다.
4. 기존 순차 경로를 취소하고 `0x80000040`으로 이동합니다.

즉, Fetch 요청이 발생했다는 사실만으로 해당 명령어가 실제 실행되었다고 판단하면 안 됩니다.

## 2. 로그로 실제 실행 여부 확인

여기서 결정적인 증거가 있습니다.

```
Cycle 20 : FETCH PC=0x80000020
Cycle 21 : STORE addr=0x10000008 data=0x00000001
```

`0x80000020`에는 다음 명령어가 있습니다.

```
val JAL_X0_0 = B"x0000006F" // JAL x0, 0
```

이 명령어가 실제 실행되었다면 CPU는 자기 자신에게 계속 점프해야 합니다.

그런데 Cycle 21 이후에도 GPIO_OE Store, GPIO_IN Load 등 후속 프로그램이 정상적으로 실행됩니다.

따라서 Cycle 20의 Fetch는 실제 Trap Handler 실행이 아니라 분기 처리 과정에서 발생한 순차 Fetch라고 판단할 수 있습니다.

## 3. 실제 Trap 진입은 Cycle 54

이 부분을 보겠습니다.

```
Cycle 50 : LOAD addr=0x1000000C
Cycle 51 : LOAD RSP addr=0x1000000C data=0x00000000 error=true
Cycle 54 : FETCH PC=0x80000020
Cycle 58 : FETCH PC=0x80000020
Cycle 62 : FETCH PC=0x80000020
```

이번에는 상황이 다릅니다.

- Cycle 50: GPIO 예약 주소 Load 요청
- Cycle 51: `error=true` 응답
- Cycle 54: Trap Handler 주소 Fetch
- 이후 4-cycle 간격으로 같은 주소 반복 Fetch

이것이 의도한 Trap 동작입니다.

Trap Handler의 명령어가 다음과 같이 무한 루프이기 때문입니다.

```
JAL x0, 0
```

## 5. 다음에 꼭 알아둘 개념

이번에 확인한 것은 CPU 파이프라인을 이해하는 데 중요한 차이입니다.

| 관찰 대상               | 의미              |
| ------------------- | --------------- |
| Instruction Fetch   | 명령어를 가져오기 위한 요청 |
| Instruction Decode  | 명령어 해석          |
| Instruction Execute | 명령어 실행          |
| Commit / Retirement | 명령어의 최종 완료      |

따라서 앞으로 CPU 시뮬레이션에서 PC만 관찰하지 말고, 필요하면 분기 취소(Flush), 명령어 유효 상태, 예외 발생 시점도 함께 관찰해야 합니다.

- GPIO_IN 읽기
