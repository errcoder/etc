SpinalHDL의 대표적인 RISC-V SoC 템플릿인 `Murax.scala`는 VexRiscv CPU 코어와 온칩 메모리(BRAM), 그리고 필수 페리페럴을 하나의 FPGA 친화적인 SoC로 통합하여 정의하는 파일입니다.

이 파일은 크게 설정을 담당하는 클래스와 하드웨어를 구현하는 컴포넌트 클래스로 나뉩니다. 각 단위별 기능과 역할을 상세히 설명해 드리겠습니다.

---

### 1. `MuraxConfig` (Case Class)

SoC의 전체적인 하드웨어 스펙과 구성을 정의하는 설정 클래스입니다. 사용자가 인스턴스화할 때 파라미터를 조절하여 SoC의 규모와 성능을 커스텀할 수 있습니다.

* **주요 필드 및 역할:**
* `coreFrequency`: 시스템 클럭 주파수 설정 (예: 50 MHz 등, 타이밍 계산 및 페리페럴 설정에 활용).
* `onChipRamSize`: 온칩 BRAM의 총 용량 (예: 8 KB 등).
* `onChipRamHexFile`: 시뮬레이션이나 합성 시 BRAM을 초기화할 펌웨어 파일 경로 (`.hex` 또는 `.bin` 연동).
* `pipelineDBus` / `pipelineMainBus`: CPU 데이터 버스 및 메인 버스의 파이프라인 스테이지 최적화 여부 설정.
* `vexRiscvConfig`: VexRiscv CPU 코어 내부의 플러그인 구성(RV32I/IM, 곱셈기, 배럴 시프터, 디버그 플러그인 등)을 정의하는 설정 객체.


* **기본값 제공 (`MuraxConfig.default`):** 일반적인 베어메탈 개발과 시뮬레이션에 바로 사용할 수 있는 표준 설정 프로파일을 제공합니다.

---

### 2. `Murax` (Component Class)

SpinalHDL의 `Component`를 상속받아 실제 하드웨어 회로(RTL)를 구축하는 **핵심 SoC 메인 클래스**입니다. `config` 파라미터를 전달받아 내부 버스와 주변장치를 조립합니다.

* **주요 구성 요소 및 역할:**
* **VexRiscv CPU 코어 인스턴스화:** `config.vexRiscvConfig`에 맞춰 RISC-V 32비트 프로세서 코어를 생성하고, 내부 인터럽트 및 디버그 라인을 SoC 버스와 연결합니다.
* **온칩 메모리(On-Chip RAM):** 주소 `0x00000000`번지에 매핑되는 BRAM 블록을 생성하고, CPU의 Instruction/Data 통합 버스와 연결합니다.
* **버스 브리지 및 APB3 디코더 (`Apb3Decoder`):** CPU의 내부 버스 요청을 받아 상위 주소 대역(`0xF0000000` 시작)의 접근을 각 주변장치로 라우팅해 주는 디코더 로직을 구성합니다.
* **내장 페리페럴(Peripherals) 통합:**
* **GPIO Controller:** 외부 핀 제어 및 LED/스위치 연동을 위한 범용 입출력 블록.
* **UART Controller:** 시리얼 통신 및 `printf` 디버깅 출력을 위한 통신 블록.
* **Timer:** 시스템 타이머 및 인터럽트 생성을 위한 타이머 블록.


* **인터럽트 컨트롤러 (Interrupt Controller):** 타이머, UART, GPIO 등에서 발생하는 인터럽트 신호를 모아서 VexRiscv CPU로 전달하는 중계 역할 수행.



---

### 3. 컴패니언 오브젝트 / Verilog 생성기 (`object Murax`)

파일 하단이나 별도 오브젝트로 존재하는 영역으로, 스칼라 코드를 실행하여 **실제 Verilog RTL 코드를 파일로 뱉어내는 엔트리 포인트(Entry Point)** 역할을 합니다.

* **주요 역할:**
* `SpinalVerilog(new Murax(MuraxConfig.default))` 구문을 포함하여, SBT 등을 통해 실행하면 `Murax.v` 파일이 자동으로 합성되도록 유도합니다.

Explain how the internal bus interconnects the CPU and APB peripherals in Murax.scala.

---

Murax SoC에서 VexRiscv CPU 코어와 APB3 주변장치들을 연결하는 내부 버스 인터커넥트(Interconnect) 구조는 **단순하면서도 효율적인 주소 디코딩 및 브리지(Bridge) 방식**으로 설계되어 있습니다.

Murax에는 복잡한 대형 버스 프로토콜(AXI 등) 대신, 가볍고 직관적인 SpinalHDL 표준 버스 컴포넌트들이 사용됩니다. 내부 버스가 CPU와 페리페럴을 연결하는 핵심 원리를 단계별로 설명해 드리겠습니다.

---

### 1. 전체 버스 연결 구조 요약

VexRiscv CPU가 메모리나 주변장치에 접근할 때 발행하는 **데이터 버스(Data Bus)** 요청은 주소(Address) 값의 상위 비트에 따라 크게 두 갈래로 나뉩니다.

```text
                  +-----------------------+
                  |   VexRiscv CPU Core   |
                  |     (Data Bus)        |
                  +-----------+-----------+
                              |
                     [ Address Decoding ]
                     /                  \
   (0x0000_0000)    /                    \    (0xF000_0000)
                   v                      v
        +-------------------+    +-------------------+
        |  On-Chip RAM      |    |    Apb3Bridge     |
        |  (Direct BRAM)    |    +---------+---------+
        +-------------------+              | (APB3 Protocol)
                                           v
                                 +-------------------+
                                 |    Apb3Decoder    |
                                 +----+----+----+----+
                                      |    |    |
                                      v    v    v
                                    [GPIO] [UART] [Timer]

```

---

### 2. 단계별 버스 상호작용 과정

#### ① CPU 데이터 버스 요청 (Data Bus Master)

* VexRiscv CPU는 명령어를 읽어오는 Instruction Bus 외에도, 데이터를 읽고 쓰는 **Data Bus**를 가집니다. CPU가 특정 주소(예: `0xF0010000`)에 쓰기 또는 읽기 명령을 내리면 버스 신호가 활성화됩니다.

#### ② 주소 영역 분기 (Address Decoding)

* 버스 컨트롤러(또는 내부 라우팅 로직)는 주소의 범위를 확인합니다.
* **온칩 메모리 영역 (`0x00000000` 대역):** RAM 컨트롤러로 직접 연결되어 한 클럭 내에 빠르게 데이터를 읽고 씁니다.
* **주변장치 영역 (`0xF0000000` 대역):** APB 버스 계열로 라우팅됩니다.



#### ③ 버스 프로토콜 변환: `Apb3Bridge`

* VexRiscv의 네이티브 메모리 액세스 신호는 표준 AMBA APB3 프로토콜과 형식이 다릅니다.
* 따라서 **`Apb3Bridge`** 컴포넌트가 중간에 위치하여, CPU의 읽기/쓰기 요청을 APB3 프로토콜 신호(`PSEL`, `PENABLE`, `PWRITE`, `PADDR`, `PWDATA`, `PRDATA`)로 실시간 변환해 줍니다.

#### ④ 다중 페리페럴 라우팅: `Apb3Decoder`

* `Apb3Bridge`를 통해 나온 단일 APB3 마스터 신호는 `Apb3Decoder`로 전달됩니다.
* 디코더는 각 페리페럴에 할당된 주소 범위(`SizeMapping`)를 기준으로 슬라이브 선택 신호(`PSEL`)를 골라줍니다.
* `0xF0000000` (GPIO 슬라이브 선택)
* `0xF0010000` (UART 슬라이브 선택)
* `0xF0020000` (Timer 슬라이브 선택)



---

### 3. SpinalHDL 코드로 보는 인터커넥트 정의 방식

Murax 소스코드(`Murax.scala`)를 보면 이 과정이 SpinalHDL의 버스 라이브러리를 통해 매우 간결하게 선언되어 있습니다.

```scala
// CPU 버스를 APB로 변환하는 브리지 생성
val bridgeToApb = Apb3Bridge(
  master = internalBus,
  mapping = sizeMapping
)

// APB 디코더를 통해 여러 페리페럴을 주소 매핑과 함께 연결
val apbDecoder = Apb3Decoder(
  master = bridgeToApb.io.apb,
  slaves = Array(
    io.gpioCtrl.apb  -> (0xF0000000, 4.kB),
    io.uartCtrl.apb  -> (0xF0010000, 4.kB),
    io.timer.apb     -> (0xF0020000, 4.kB)
  )
)

```

이와 같은 구조 덕분에 사용자가 새로운 커스텀 페리페럴(예: SPI, I2C 등)을 추가할 때도 `Apb3Decoder`의 `slaves` 배열에 빈 주소 대역만 등록해주면 CPU가 곧바로 해당 페리페럴을 제어할 수 있게 됩니다.

How do I add a custom APB3 peripheral to the Murax SoC and connect it to this internal bus interconnect?

---

Murax SoC에 사용자 정의 APB3 페리페럴(Custom Peripheral)을 추가하고 내부 버스 인터커넥트에 연결하는 과정은 **1) 페리페럴 하드웨어 컴포넌트 정의**, **2) Murax SoC 내부 `io` 및 `apbDecoder`에 등록**, **3) C 펌웨어에서 주소 매핑 연동**의 3단계로 진행됩니다.

---

### 1단계: 사용자 정의 APB3 페리페럴 컴포넌트 작성

SpinalHDL의 `Apb3SlaveFactory`를 사용하면 레지스터 맵을 매우 쉽게 구현할 수 있습니다. 예를 들어 간단한 32비트 출력 레지스터를 가진 커스텀 IP를 정의합니다.

```scala
import spinal.core._
import spinal.lib._
import spinal.lib.bus.amba3.apb._

class CustomPeripheral() extends Component {
  val io = new Bundle {
    val apb = slave(Apb3(addressWidth = 8, dataWidth = 32))
    val customPin = out Bool() // 외부로 나가는 커스텀 핀
  }

  // APB3 슬레이브 팩토리 생성
  val busCtrl = Apb3SlaveFactory(io.apb)
  
  // 0x00 번지에 매핑되는 32비트 레지스터 생성 (기본값 0)
  val reg = busCtrl.createReadWrite(UInt(32 bits), address = 0x00, doc = "Custom Control Register") init(0)

  io.customPin := reg(0) // 레지스터의 첫 번째 비트를 핀에 연결
}

```

---

### 2단계: Murax SoC 코드에 페리페럴 통합하기

`Murax.scala` 파일 내부로 들어가서, 방금 만든 커스텀 페리페럴을 인스턴스화하고 `Apb3Decoder`의 슬레이브 배열에 빈 주소 대역과 함께 추가합니다.

1. **IO Bundle 확장:** `Murax` 컴포넌트의 `io` Bundle에 커스텀 페리페럴의 APB 인터페이스를 추가합니다.
2. **Decoder 매핑 추가:** 기존 GPIO, UART, Timer가 등록되어 있던 `Apb3Decoder`의 `slaves` 배열에 새 주소 대역(예: `0xF0030000`)을 할당합니다.

```scala
// Murax 컴포넌트 내부 발췌
val customPeripheral = new CustomPeripheral()

// APB 디코더에 슬레이브 추가 (예: 0xF0030000 번지, 4KB 크기 할당)
val apbDecoder = Apb3Decoder(
  master = bridgeToApb.io.apb,
  slaves = Array(
    io.gpioCtrl.apb       -> (0xF0000000, 4.kB),
    io.uartCtrl.apb       -> (0xF0010000, 4.kB),
    io.timer.apb          -> (0xF0020000, 4.kB),
    customPeripheral.io.apb -> (0xF0030000, 4.kB) // <-- 커스텀 페리페럴 추가 완료!
  )
)

// 탑레벨 외부 포트와 연결
val customPin = out Bool()
customPin := customPeripheral.io.customPin

```

---

### 3단계: C 펌웨어에서 커스텀 페리페럴 제어하기

하드웨어가 합성되면, C 펌웨어 헤더 파일에 새 페리페럴의 베이스 주소(`0xF0030000`)를 정의하여 직접 레지스터 값을 조작할 수 있습니다.

```c
// firmware/uart.h 또는 커스텀 헤더 파일에 추가
#define CUSTOM_PERIPH_BASE  0xF0030000
#define CUSTOM_REG_CTRL     (*(volatile unsigned int *)(CUSTOM_PERIPH_BASE + 0x00))

// C 펌웨어 main 함수 예시
int main() {
    uart_init();
    uart_print("Custom Peripheral Test Start\r\n");

    while (1) {
        // 커스텀 레지스터에 값 쓰기 (첫 번째 비트 High)
        CUSTOM_REG_CTRL = 0x01;
        
        // 간단한 딜레이 후 Low로 변경
        for (volatile int i = 0; i < 500000; i++);
        
        CUSTOM_REG_CTRL = 0x00;
        for (volatile int i = 0; i < 500000; i++);
    }
    return 0;
}

```

* **Verification:** `sbt "runMain MuraxSim"`을 실행했을 때 `Apb3Decoder`가 `0xF0030000` 주소 요청을 정상적으로 디코딩하여 `CustomPeripheral`의 레지스터 값을 갱신하는지 파형이나 로그를 통해 확인할 수 있습니다.

How do I connect an interrupt request (IRQ) from this custom peripheral to the VexRiscv CPU in Murax?

---

Murax SoC(VexRiscv 코어 기반)에서 커스텀 페리페럴이 발생시키는 인터럽트 요청(IRQ)을 CPU에 전달하려면, **1) 페리페럴 내부 인터럽트 신호 생성**, **2) Murax SoC 내부에서 VexRiscv의 외부 인터럽트 라인(`externalInterrupt`)과 연결**, **3) C 펌웨어에서 인터럽트 활성화 및 ISR(Interrupt Service Routine) 작성**의 3단계를 거치면 됩니다.

---

### 1단계: 커스텀 페리페럴에 인터럽트 출력 추가하기

페리페럴 컴포넌트 내부에 인터럽트 핀(`interrupt`)을 선언하고, 특정 조건(예: 레지스터 설정이나 이벤트 발생)에 따라 이 핀을 `True`로 만들도록 구현합니다. 인터럽트는 보통 CPU가 인지한 뒤 소프트웨어로 클리어(Clear)할 수 있는 레지스터 구조를 갖추는 것이 일반적입니다.

```scala
import spinal.core._
import spinal.lib._
import spinal.lib.bus.amba3.apb._

class CustomPeripheralWithIrq() extends Component {
  val io = new Bundle {
    val apb = slave(Apb3(addressWidth = 8, dataWidth = 32))
    val interrupt = out Bool() // CPU로 향하는 IRQ 신호
  }

  val busCtrl = Apb3SlaveFactory(io.apb)
  
  // 컨트롤 및 상태/인터럽트 플래그 레지스터
  val controlReg = busCtrl.createReadWrite(UInt(32 bits), address = 0x00, doc = "Control") init(0)
  val irqStatus  = Reg(Bool()) init(False)

  // 인터럽트 발생 조건 (예: controlReg의 특정 비트가 1이 되거나 이벤트 발생 시)
  when(controlReg(1) && !irqStatus) {
    irqStatus := True
  }

  // 소프트웨어가 인터럽트를 클리어하기 위한 처리 (예: 0x04 번지에 쓰면 클리어)
  busCtrl.onWrite(address = 0x04) {
    irqStatus := False
  }

  // 외부 인터럽트 출력 핀 할당
  io.interrupt := irqStatus
}

```

---

### 2단계: Murax SoC (`Murax.scala`)에서 CPU 인터럽트 라인과 연결하기

VexRiscv 코어는 외부 인터럽트 신호(`externalInterrupt`) 입력을 지원합니다. 기존 페리페럴(Timer, UART, GPIO 등)의 인터럽트들과 함께 **OR 연산(Logical OR)** 등으로 묶어서 CPU의 인터럽트 포트에 전달해 주어야 합니다.

`Murax.scala` 내부에서 다음과 같이 연결합니다.

```scala
// 1. 커스텀 페리페럴 인스턴스화
val customPeripheral = new CustomPeripheralWithIrq()

// 2. APB 디코더에 매핑 추가 (예: 0xF0030000)
val apbDecoder = Apb3Decoder(
  master = bridgeToApb.io.apb,
  slaves = Array(
    io.gpioCtrl.apb         -> (0xF0000000, 4.kB),
    io.uartCtrl.apb         -> (0xF0010000, 4.kB),
    io.timer.apb            -> (0xF0020000, 4.kB),
    customPeripheral.io.apb -> (0xF0030000, 4.kB) // 추가
  )
)

// 3. CPU 외부 인터럽트 라인에 커스텀 페리페럴 IRQ 통합
// (기존 시스템의 인터럽트 신호들과 함께 OR 조합하여 VexRiscv externalInterrupt에 연결)
val allInterrupts = Bool()
// 예시: 타이머/UART 등 기존 인터럽트 + 커스텀 페리페럴 IRQ
allInterrupts := timerIrq | uartIrq | customPeripheral.io.interrupt

// VexRiscv 코어의 외부 인터럽트 포트에 바인딩
cpu.io.externalInterrupt := allInterrupts

```

### 3단계: C 펌웨어에서 인터럽트 처리하기 (ISR)

하드웨어가 연결되면, C 펌웨어에서 RISC-V Machine Interrupt(MIE, MIP 레지스터)를 활성화하고, 인터럽트 발생 시 호출될 트랩 핸들러(Trap Handler)를 작성합니다.

```c
#define CUSTOM_PERIPH_BASE 0xF0030000
#define CUSTOM_REG_CTRL    (*(volatile unsigned int *)(CUSTOM_PERIPH_BASE + 0x00))
#define CUSTOM_REG_CLEAR   (*(volatile unsigned int *)(CUSTOM_PERIPH_BASE + 0x04))

// RISC-V 인터럽트 핸들러 (attribute interrupt 지정)
void __attribute__((interrupt)) trap_handler() {
    // 1. 커스텀 페리페럴 인터럽트 발생 확인 및 처리
    uart_print("Interrupt caught from Custom Peripheral!\r\n");

    // 2. 하드웨어 인터럽트 플래그 클리어 (0x04 번지에 쓰기)
    CUSTOM_REG_CLEAR = 0x01;
}

void enable_interrupts() {
    // RISC-V MIE(Machine Interrupt Enable) 레지스터에서 외부 인터럽트(MEIE) 허용
    __asm__ volatile("li t0, 0x800"); // MEIE bit (bit 11)
    __asm__ volatile("csrs mie, t0");
    // 글로벌 인터럽트 허용 (MSTATUS.MIE 비트 활성화)
    __asm__ volatile("csrs mstatus, 0x8"); 
}

int main() {
    uart_init();
    uart_print("System Booted. Enabling Interrupts...\r\n");

    enable_interrupts();

    // 커스텀 페리페럴에 인터럽트 유발 신호 전달 (Control Reg 비트 1 설정)
    CUSTOM_REG_CTRL = 0x02; 

    while (1) {
        // 메인 루프 작업 수행
    }
}

```

How do I set up the mtvec register in the startup assembly code so the CPU jumps to the trap handler on an interrupt?

---

RISC-V 아키텍처에서 인터럽트나 예외가 발생했을 때 CPU가 지정된 트랩 핸들러로 올바르게 점프하려면, 부팅 직후 어셈블리 스타트업 코드(`crt0.s`)에서 **`mtvec` (Machine Trap-Vector Base-Address) 레지스터**를 설정해 주어야 합니다.

---

### 1. `mtvec` 레지스터의 구조

`mtvec` 레지스터는 크게 두 가지 정보를 담고 있습니다:

* **Base Address (상위 비트들):** 트랩 핸들러 함수가 위치한 메모리 주소 (4바이트 정렬이므로 하위 2비트는 항상 0).
* **Mode (하위 2비트):**
* `00` (Direct Mode): 모든 인터럽트와 예외가 무조건 `mtvec`에 설정된 단일 주소로 점프합니다. (베어메탈 환경에서 가장 흔히 사용)
* `01` (Vectored Mode): 인터럽트 번호에 따라 각각 다른 벡터 주소로 분기합니다.



---

### 2. 스타트업 어셈블리 코드 (`crt0.s`) 구현 예시

프로젝트의 `crt0.s` 파일에 스택 포인터를 설정한 뒤, `la` (Load Address) 명령어로 트랩 핸들러의 주소를 가져와 `csrw` 명령어로 `mtvec` 레지스터에 기록하는 코드를 추가합니다.

```assembly
.global _start
.extern main
.extern trap_handler

_start:
    # 1. 스택 포인터(SP) 초기화 (온칩 RAM의 끝 주소 등 적절한 위치 지정)
    # Murax 온칩 메모리 크기에 맞춰 설정 (예: 8KB RAM인 경우 0x00002000)
    li sp, 0x00002000

    # 2. mtvec 레지스터 설정 (트랩 핸들러 주소 등록)
    la t0, trap_handler     # trap_handler 심볼의 주소를 t0에 로드
    # 하위 2비트를 00(Direct Mode)으로 맞추기 위해 주소를 그대로 혹은 조작하여 설정
    csrw mtvec, t0          # mtvec 레지스터에 t0 값 쓰기

    # 3. 메인 함수(main)로 점프
    call main

    # 4. 만약 main이 반환되면 무한 루프 대기
_infinite_loop:
    j _infinite_loop

```

---

### 3. 주요 어셈블리 명령어 설명

1. **`la t0, trap_handler`**
* 링크 시 결정되는 `trap_handler` 함수의 절대 주소를 레지스터 `t0`에 적재합니다. C 코드에서 `void __attribute__((interrupt)) trap_handler()`로 선언한 함수의 이름과 일치해야 합니다.


2. **`csrw mtvec, t0`**
* RISC-V의 CSR(Control and Status Register) 쓰기 명령어입니다. `t0`에 담긴 트랩 핸들러의 주소를 `mtvec` 레지스터에 저장하여, 향후 인터럽트 발생 시 CPU가 이 주소를 참조하도록 만듭니다.

How do I check the cause of the interrupt inside the trap handler using the mcause register in C?

---

RISC-V 아키텍처에서 인터럽트나 예외가 발생했을 때, 어떤 이유로 트랩이 발생했는지 확인하려면 `mcause` (Machine Cause) 제어/상태 레지스터(CSR)를 읽어와야 합니다.

핸들러 내부에서 인라인 어셈블리를 통해 `mcause` 값을 읽고, 최상위 비트(MSB)와 하위 코드값을 파싱하면 외부 인터럽트, 타이머, 예외 등을 정확히 구분할 수 있습니다.

---

### 1. `mcause` 레지스터의 구조

32비트 RISC-V 시스템에서 `mcause` 레지스터는 다음과 같이 구성되어 있습니다:

* **비트 31 (MSB, Interrupt Bit):**
* `1`이면 인터럽트(Interrupt)에 의해 발생한 것임을 의미합니다.
* `0`이면 명령어 오류, 0으로 나누기 등의 예외(Exception)에 의해 발생한 것임을 의미합니다.


* **비트 [30:0] (Exception Code):**
* 인터럽트 또는 예외의 세부 원인 번호(Cause Code)를 나타냅니다.
* *주요 외부 인터럽트 코드:* 기계 모드 외부 인터럽트(Machine External Interrupt)는 보통 코드 **`11`** (`0x8000000B`)입니다.



---

### 2. `mcause`를 활용한 C 트랩 핸들러 구현 예시

다음은 `trap_handler` 내부에서 `mcause` 값을 읽고, 비트 연산을 통해 원인을 분석하여 분기하는 C 코드 예시입니다.

```c
#include "uart.h"

// 커스텀 페리페럴 레지스터 정의 (이전 예시 연동)
#define CUSTOM_PERIPH_BASE 0xF0030000
#define CUSTOM_REG_CLEAR   (*(volatile unsigned int *)(CUSTOM_PERIPH_BASE + 0x04))

void __attribute__((interrupt)) trap_handler() {
    unsigned long mcause_val;

    // 1. mcause 레지스터 값 읽기 (인라인 어셈블리 csrr 명령어 사용)
    __asm__ volatile("csrr %0, mcause" : "=r"(mcause_val));

    // 2. 인터럽트 여부 확인 (비트 31이 1인지 확인)
    int is_interrupt = (mcause_val & 0x80000000) != 0;
    unsigned long cause_code = mcause_val & 0x7FFFFFFF;

    if (is_interrupt) {
        // 인터럽트인 경우
        switch (cause_code) {
            case 11: // Machine External Interrupt (External PLIC/Peripherals)
                uart_print("[Trap] External Interrupt caught (Cause 11)\r\n");
                
                // 커스텀 페리페럴 인터럽트 플래그 클리어
                CUSTOM_REG_CLEAR = 0x01;
                break;

            case 7:  // Machine Timer Interrupt
                uart_print("[Trap] Timer Interrupt caught (Cause 7)\r\n");
                break;

            default:
                uart_print("[Trap] Unknown Interrupt\r\n");
                break;
        }
    } else {
        // 예외(Exception)인 경우 (예: 잘못된 메모리 접근, 부적절한 명령어 등)
        uart_print("[Trap] Exception occurred!\r\n");
    }
}

```

---

### 3. 코드 핵심 포인트

1. **`csrr %0, mcause`**: RISC-V 특권 아키텍처 명령어인 `csrr`(Control and Status Register Read)을 사용하여 `mcause` 레지스터의 내용을 C 변수 `mcause_val`에 안전하게 복사합니다.
2. **`0x80000000` 마스킹**: 비트 31번 플래그를 분리해내어 이것이 하드웨어 인터럽트인지 소프트웨어 예외인지 판별합니다.
3. **원인별 분기 (`cause_code`)**: Murax 및 VexRiscv 코어 환경에서 외부 페리페럴(UART, 타이머, 커스텀 IP 등)은 대개 플랫폼 레벨 인터럽트 컨트롤러(PLIC)나 통합 인터럽트 라인을 거쳐 Cause 11 (External Interrupt)로 진입하게 됩니다.

Want me to show how to clear the interrupt pending bit properly in the VexRiscv PLIC or custom peripheral to prevent infinite interrupt loops?

---

An infinite interrupt loop happens when the CPU returns from the trap handler via `mret`, but the peripheral's interrupt signal is still asserted (`High`). The moment global interrupts are re-enabled, the CPU instantly detects the active line and re-triggers the same trap.

To prevent this, you must clear the interrupt flag **at the peripheral hardware level** inside your C interrupt service routine (ISR) before exiting.

---

### Step-by-Step Fix to Prevent Infinite Loops

#### 1. Clear the Peripheral Flag *First* in the ISR

Always write to the peripheral's clear register at the very beginning of your trap handler. This forces the hardware IRQ wire to drop back to `Low` before the CPU executes `mret`.

```c
void __attribute__((interrupt)) trap_handler() {
    unsigned long mcause_val;
    __asm__ volatile("csrr %0, mcause" : "=r"(mcause_val));

    if ((mcause_val & 0x80000000) && ((mcause_val & 0x7FFFFFFF) == 11)) {
        
        // [CRITICAL STEP] Clear the peripheral interrupt flag immediately
        // Writing to this register toggles the hardware flip-flop and drops io.interrupt to Low
        CUSTOM_REG_CLEAR = 0x01; 

        // Now safely execute your service logic
        uart_print("[ISR] Peripheral interrupt serviced and cleared.\r\n");
    }
}

```

* **Verification:** Check your simulation waveform (`io.interrupt` or the CPU's `externalInterrupt` wire) to confirm the signal drops from `High` to `Low` immediately after `CUSTOM_REG_CLEAR` is written.

#### 2. Ensure Hardware Logic Properly Resets the Flag

In your SpinalHDL peripheral design (`CustomPeripheralWithIrq.scala`), make sure the interrupt register or flip-flop clears itself or responds correctly when the software write arrives:

```scala
// SpinalHDL peripheral example
val irqStatus = Reg(Bool()) init(False)

when(controlReg(1) && !irqStatus) {
  irqStatus := True
}

// When software writes to the clear address (0x04), reset the flag to False
busCtrl.onWrite(address = 0x04) {
  irqStatus := False
}

io.interrupt := irqStatus

```

* **Verification:** Ensure that `irqStatus` does not latch `True` permanently if the trigger condition is still active. If the source condition remains high, design the peripheral with an **edge-triggered** interrupt rather than a level-triggered one, or require software to explicitly clear it.

#### 3. Verify Log Output Stability

Run your SpinalSim testbench.

* **Failure Symptom:** The console spams `[ISR] Peripheral interrupt serviced...` millions of times per second without stopping.
* **Success Signal:** The log message prints **only once** (or exactly as many times as the event is triggered), and the CPU successfully returns to the main loop.

Want me to show how to implement an edge-triggered vs level-triggered interrupt design in SpinalHDL?

---

커스텀 페리페럴을 설계할 때 인터럽트의 작동 방식을 레벨 트리거(Level-Triggered)와 **엣지 트리거(Edge-Triggered)** 중 어떤 것으로 선택하느냐는 시스템의 안정성과 소프트웨어 구조에 큰 영향을 줍니다.

SpinalHDL에서 이 두 가지 방식을 각각 어떻게 구현하는지 명확한 코드 예시와 함께 살펴보겠습니다.

---

### 1. 레벨 트리거 (Level-Triggered Interrupt)

* **동작 방식:** 인터럽트 조건이 참인 동안(예: 레지스터 플래그가 `High` 상태인 동안) 인터럽트 핀이 계속 `High`를 유지합니다.
* **특징:** 소프트웨어가 ISR 내부에서 명시적으로 플래그를 클리어(`Clear`)해주지 않으면, CPU가 트랩에서 복귀하자마자 다시 인터럽트가 걸려 **무한 루프**에 빠지기 쉽습니다. 하지만 이벤트를 놓치지 않고 안정적으로 감지할 수 있습니다.

#### SpinalHDL 구현 예시 (`LevelTriggeredPeripheral.scala`)

```scala
import spinal.core._
import spinal.lib._
import spinal.lib.bus.amba3.apb._

class LevelTriggeredPeripheral() extends Component {
  val io = new Bundle {
    val apb = slave(Apb3(addressWidth = 8, dataWidth = 32))
    val interrupt = out Bool()
  }

  val busCtrl = Apb3SlaveFactory(io.apb)
  
  val statusReg = Reg(Bool()) init(False)

  // 외부 조건 발생 시 상태 플래그 세팅
  when(ConditionMet()) {
    statusReg := True
  }

  // 소프트웨어가 0x04 번지에 쓰면 플래그 클리어
  busCtrl.onWrite(address = 0x04) {
    statusReg := False
  }

  // [Level-Triggered] 플래그가 High인 동안 인터럽트 핀도 계속 High 유지
  io.interrupt := statusReg
}

```

---

### 2. 엣지 트리거 (Edge-Triggered Interrupt)

* **동작 방식:** 조건이 만족되는 순간(**상태가 변하는 시점**, 예: `Low`에서 `High`로 넘어가는 Rising Edge) **딱 1클럭 동안만** 펄스(Pulse) 형태로 인터럽트 신호를 발생시킵니다.
* **특징:** 소프트웨어가 플래그를 늦게 클리어하더라도 하드웨어 핀 자체가 자동으로 `Low`로 내려가므로 무한 루프 위험이 적습니다. 단, 신호가 겹치거나 펄스 폭이 너무 짧으면 간헐적으로 이벤트를 놓칠 위험이 있어 상태 래치(Latch)와 조합해 사용하는 것이 좋습니다.

#### SpinalHDL 구현 예시 (`EdgeTriggeredPeripheral.scala`)

```scala
import spinal.core._
import spinal.lib._
import spinal.lib.bus.amba3.apb._

class EdgeTriggeredPeripheral() extends Component {
  val io = new Bundle {
    val apb = slave(Apb3(addressWidth = 8, dataWidth = 32))
    val interrupt = out Bool()
  }

  val busCtrl = Apb3SlaveFactory(io.apb)
  
  val rawTrigger = Reg(Bool()) init(False)
  // 이전 클럭의 상태를 저장할 딜레이(Register) 생성
  val rawTriggerD = RegNext(rawTrigger) init(False)

  // 조건 발생 로직
  when(ConditionMet()) {
    rawTrigger := True
  }.otherwise {
    rawTrigger := False // 예시를 위해 자동 리셋되는 조건이라 가정
  }

  // [Edge-Triggered] 이전에는 0이었고 현재 1이 되는 순간(Rising Edge)을 감지하여 1클럭 펄스 생성
  val risingEdge = rawTrigger && !rawTriggerD

  io.interrupt := risingEdge
}

```

---

### 요약 및 선택 가이드

| 구분 | 레벨 트리거 (Level-Triggered) | 엣지 트리거 (Edge-Triggered) |
| --- | --- | --- |
| **신호 유지** | 조건이 해제되거나 소프트웨어가 클리어할 때까지 지속 | 단 1클럭 동안만 펄스로 발생 |
| **무한 루프 위험** | 높음 (소프트웨어가 클리어하지 않으면 즉시 재발생) | 낮음 (신호가 자동으로 떨어짐) |
| **추천 용도** | 타이머, UART 수신 대기 등 지속적인 상태 확인이 필요한 경우 | 버튼 입력, 외부 센서 펄스 등 순간적인 이벤트 감지 |

---

Want me to show how to write a testbench in SpinalSim to verify both interrupt trigger behaviors?

---

SpinalHDL의 강력한 시뮬레이션 프레임워크인 **SpinalSim**을 사용하여, 앞서 설계한 커스텀 페리페럴의 인터럽트 발생(Assert)과 해제(Clear) 동작을 검증하는 테스트벤치(Testbench) 스크립트 작성 방법입니다.

이 테스트벤치는 APB3 버스를 통해 레지스터에 값을 써서 인터럽트 조건을 유발하고, `io.interrupt` 핀이 정상적으로 High로 올라가는지 확인한 뒤, 클리어 레지스터에 써서 다시 Low로 떨어지는지 검증합니다.

---

### SpinalSim 테스트벤치 구현 (`CustomPeripheralSim.scala`)

```scala
import spinal.core._
import spinal.core.sim._
import spinal.lib.bus.amba3.apb._

object CustomPeripheralSim {
  def main(args: Array[String]): Unit = {
    // 1. 시뮬레이션 설정 (파형(Waveform) 생성 활성화)
    SimConfig.withWave.compile {
      val dut = new CustomPeripheralWithIrq() // 검증할 커스텀 페리페럴 컴포넌트
      dut
    }.doSim { dut =>
      // 2. 클럭 도메인 시작 (20ns 주기 = 50 MHz)
      dut.clockDomain.forkStimulus(period = 20)

      println("--- Starting Interrupt Peripheral Simulation ---")

      // 초기 상태 검증 (인터럽트 핀이 Low여야 함)
      assert(dut.io.interrupt.toBoolean == false, "Error: Interrupt should be low initially!")

      // 3. APB 쓰기 시뮬레이션: 제어 레지스터(0x00)에 값 써서 인터럽트 유발
      dut.clockDomain.waitSampling()
      
      // APB3 마스터 신호 구동 (드라이브)
      dut.io.apb.PSEL.poke(True)
      dut.io.apb.PENABLE.poke(False)
      dut.io.apb.PWRITE.poke(True)
      dut.io.apb.PADDR.poke(0x00)   // Control Register 주소
      dut.io.apb.PWDATA.poke(0x02)  // 비트 1 설정 (인터럽트 조건 트리거)

      // APB 프로토콜 타이밍 맞추기 (Setup phase -> Access phase)
      dut.clockDomain.waitSampling()
      dut.io.apb.PENABLE.poke(True)

      dut.clockDomain.waitSampling()
      // 트랜잭션 종료
      dut.io.apb.PSEL.poke(False)
      dut.io.apb.PENABLE.poke(False)

      // 4. 인터럽트 핀이 High로 올라갔는지 검증
      dut.clockDomain.waitSampling(2) // 2클럭 대기
      assert(dut.io.interrupt.toBoolean == true, "Error: Interrupt signal failed to assert (High)!")
      println("[Sim Success] Interrupt line successfully asserted (High).")

      // 5. APB 쓰기 시뮬레이션: 클리어 레지스터(0x04)에 값 써서 인터럽트 해제
      dut.clockDomain.waitSampling()
      
      dut.io.apb.PSEL.poke(True)
      dut.io.apb.PENABLE.poke(False)
      dut.io.apb.PWRITE.poke(True)
      dut.io.apb.PADDR.poke(0x04)   // Clear Register 주소
      dut.io.apb.PWDATA.poke(0x01)  // 클리어그널 전달

      dut.clockDomain.waitSampling()
      dut.io.apb.PENABLE.poke(True)

      dut.clockDomain.waitSampling()
      dut.io.apb.PSEL.poke(False)
      dut.io.apb.PENABLE.poke(False)

      // 6. 인터럽트 핀이 Low로 떨어졌는지 검증
      dut.clockDomain.waitSampling(2)
      assert(dut.io.interrupt.toBoolean == false, "Error: Interrupt signal failed to clear (Low)! Infinite loop risk.")
      println("[Sim Success] Interrupt line successfully cleared (Low).")

      println("--- All Interrupt Tests Passed Successfully! ---")
    }
  }
}

```

### 테스트벤치 핵심 동작 설명

1. **`forkStimulus(period = 20)`**: 하드웨어를 구동할 가상 클럭과 리셋 신호를 자동으로 생성해 줍니다.
2. **`poke(...)`와 `waitSampling()**`: SpinalSim에서 제공하는 API로, 가상의 마스터(CPU 역할)가 되어 APB3 버스 규격에 맞춰 주소, 데이터, 제어 신호(`PSEL`, `PENABLE`, `PWRITE`)를 강제로 주입합니다.
3. **`assert(...)` 검증**: 하드웨어의 응답 신호(`dut.io.interrupt.toBoolean`)를 실시간으로 읽어와 기대값과 일치하는지 확인하고, 실패 시 시뮬레이션을 즉시 중단하여 버그를 잡아냅니다.

SpinalHDL 시뮬레이터(SpinalSim)가 생성한 파형 파일을 SBT 명령어로 빌드·실행하고, **GTKWave**를 통해 시각적으로 확인하는 방법입니다.

---

### 1단계: SBT를 통해 시뮬레이션 실행하기

터미널을 열고 프로젝트 루트 디렉토리에서 작성한 테스트벤치 객체명(`CustomPeripheralSim`)을 지정하여 SBT 실행 명령어를 입력합니다.

```bash
sbt "runMain CustomPeripheralSim"

```

* **동작 내용:**
* 스칼라 코드가 컴파일된 후 시뮬레이션이 백그라운드(또는 콘솔)에서 구동됩니다.
* 테스트벤치 내부의 `assert(...)` 문들이 모두 통과하면 콘솔에 성공 메시지가 출력됩니다.
* `SimConfig.withWave` 설정에 의해 시뮬레이션 동작 과정이 기록된 파형 파일(**VCD** 또는 **FST** 형식)이 디스크에 저장됩니다.



---

### 2단계: 생성된 파형 파일 위치 확인하기

SpinalSim은 기본적으로 프로젝트 루트 디렉토리 내에 **`workspace/`** 폴더를 만들고, 그 아래에 테스트벤치 클래스 이름으로 디렉토리를 생성하여 파형 파일을 저장합니다.

* **일반적인 경로 예시:**
```text
workspace/
└── CustomPeripheralSim/
    └── CustomPeripheralWithIrq.vcd (또는 .fst)

```



---

### 3단계: GTKWave로 파형 열기

설치된 GTKWave 프로그램을 실행하거나, 터미널 명령어를 통해 곧바로 파형 파일을 엽니다.

* **터미널 명령어 실행 (Linux / macOS / Windows Git Bash 등):**
```bash
gtkwave workspace/CustomPeripheralSim/CustomPeripheralWithIrq.vcd

```


* **GTKWave 화면에서 시그널 추가하기:**
1. GTKWave 창이 뜨면 왼쪽 상단의 **SST (Signals Search Tree)** 패널에서 테스트 중인 컴포넌트 구조(`dut`)를 펼칩니다.
2. `io_apb` (APB 버스 신호들)와 `io_interrupt`, `statusReg` 등의 내부 신호들을 선택합니다.
3. 하단의 **Append** 버튼을 누르거나 우측 메인 파형 화면으로 드래그 앤 드롭하면, 클럭에 따라 인터럽트 핀이 `0`에서 `1`로 치솟고 클리어 레지스터 입력 시 다시 `0`으로 내려가는 파형을 명확하게 확인할 수 있습니다.
