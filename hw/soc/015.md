다음 단계는 Instruction ROM의 명령어를 실제로 실행하고, CPU 레지스터에 결과가 반영되는지 확인하는 것입니다.

이번에는 IBus handshake 테스트를 확장하는 대신, 작은 RISC-V 프로그램을 실행하는 테스트로 넘어가겠습니다.

목표는 다음과 같습니다.

```
ADDI x1, x0, 1     // x1 = 1
ADDI x2, x1, 2     // x2 = 3
JAL  x0, 0         // 무한 루프

검증:
x1 == 1
x2 == 3
```

다만 레지스터 값을 읽는 방법은 `CpuConfig.smallest()`에 실제로 포함된 플러그인과 VexRiscv의 디버그 인터페이스를 확인한 뒤 정하겠습니다. 내부 신호를 임의로 접근하는 방식은 피하겠습니다.

먼저 한 단계를 바로잡겠습니다. 실제 명령어 실행으로 넘어가기 전에 IBus 응답 지연을 검증해야 합니다.

앞서 출력에서 중요한 점은 다음과 같습니다.

```
Cycle 1 : CMD fire=true  PC=0x80000010
          RSP valid=true inst=0x00000013

Cycle 2 : CMD fire=true  PC=0x80000004
          RSP valid=true inst=0x00000013
```

현재 ROM은 명령 요청과 응답을 같은 cycle에 발생시키고 있습니다.

그런데 우리가 사용하는 VexRiscv 커밋의 `IBusSimplePlugin`을 확인하면 다음과 같습니다.

```
val busLatencyMin: Int = 1
```

그리고 이 값은 내부 fetch 응답 단계 수와 응답 FIFO 구성에 사용됩니다. 따라서 외부 ROM도 최소 1-cycle 응답 지연을 지켜야 합니다.&#x20;

## 1. InstructionRom 응답을 1-cycle 지연으로 변경

현재 `InstructionRom.scala`에서 응답 부분만 다음처럼 변경하세요.

```
io.cmd.ready := True

val instruction = Bits(32 bits)
instruction := NOP

switch(io.cmd.pc) {
  is(U"32'h80000000") {
    instruction := ADDI_X1_X0_1
  }
  is(U"32'h80000004") {
    instruction := JAL_X0_0
  }
}

// 1-cycle response latency
io.rsp.valid := RegNext(io.cmd.fire) init(False)
io.rsp.inst  := RegNextWhen(instruction, io.cmd.fire) init(NOP)
io.rsp.error := False
```

핵심은 두 가지입니다.

- `rsp.valid`: 요청이 수락된 다음 cycle에 응답합니다.
- `rsp.inst`: 요청이 수락된 시점의 명령어를 저장해 다음 cycle에 전달합니다.

매 cycle 새로운 요청을 받을 수 있는 처리량은 그대로 유지합니다.

## 2. 이번 테스트의 목표

우선 ROM 명령어 내용은 변경하지 마세요.

현재 테스트를 다시 실행해서 다음을 확인하겠습니다.

1. CPU의 `cmd.fire`가 계속 발생하는가?
2. ROM의 `rsp.valid`가 요청보다 한 cycle 늦게 발생하는가?
3. 응답 명령어가 요청 당시 PC에 해당하는 명령어인가?
4. `JAL x0, 0` 실행 후 PC가 어떻게 변화하는가?

주의: 이제부터는 같은 로그 행의 `CMD PC`와 `RSP inst`가 서로 대응한다고 보면 안 됩니다. 응답은 이전 cycle의 요청에 대한 것이기 때문입니다.

이번 테스트가 통과하면 그다음에 다음 프로그램으로 바꾸겠습니다.

```
0x80000000 : ADDI x1, x0, 1
0x80000004 : ADDI x2, x1, 2
0x80000008 : JAL  x0, 0
```

아직 레지스터 실행 검증 코드는 추가하지 않겠습니다. 먼저 IBus의 요청·응답 정렬부터 확실하게 확인합시다.

파일을 확인했습니다. 현재 `InstructionRom.scala`에는 요청 수락 후 1 cycle 뒤에 응답을 내보내는 구조가 들어가 있습니다.

핵심은 이 두 줄입니다.

```
io.rsp.valid := RegNext(io.cmd.fire) init (False)
io.rsp.inst  := RegNextWhen(instruction, io.cmd.fire) init (NOP)
```

동작을 풀어 쓰면 다음과 같습니다.

- `io.cmd.fire`가 1인 cycle에 현재 PC에 해당하는 `instruction`을 레지스터에 저장합니다.
- 같은 요청의 `cmd.fire`도 한 cycle 지연시켜 다음 cycle에 `rsp.valid`로 출력합니다.
- 따라서 응답 명령어와 응답 valid가 함께 한 cycle 지연됩니다.

또한 `io.cmd.ready := True`이므로 ROM은 매 cycle 요청을 수락할 수 있습니다. 요청이 연속으로 들어오면 응답도 연속으로 나올 수 있으므로, 시뮬레이션 로그에서 CMD와 RSP가 동시에 계속 `true`로 보이는 것은 이 구조와 모순되지 않습니다.

### VexRiscv 쪽 설정과 대조한 결과

VexRiscv의 `IBusSimplePlugin` 소스에서 `busLatencyMin`은 단순한 주석용 값이 아닙니다. 이 값이 프런트엔드의 응답 버퍼 깊이와 명령어 요청·응답 경로 구성에 사용됩니다.

소스에는 다음 코드가 있습니다.

```
cmdToRspStageCount = busLatencyMin + ...
```

그리고 응답을 `iBus.rsp.toStream`으로 받아 버퍼에 넣습니다. 즉, `busLatencyMin = 1`은 CPU 프런트엔드가 최소 1-cycle 응답 지연을 전제로 구성된다는 해석과 부합합니다.&#x20;

### 다음 검증 단계

ROM 코드는 일단 변경하지 않아도 됩니다. 이제 필요한 것은 요청 PC와 응답 명령어의 대응 관계를 검증하는 것입니다.

시뮬레이션에서 다음 순서로 확인하면 됩니다.

1. `cmd.fire`가 발생하면 해당 PC를 테스트벤치 큐에 저장합니다.
2. `rsp.valid`가 발생하면 큐에서 가장 오래된 PC를 꺼냅니다.
3. 꺼낸 PC에 해당하는 기대 명령어와 `rsp.inst`를 비교합니다.
4. 불일치하면 즉시 FAIL 처리합니다.

이렇게 하면 CMD와 RSP가 매 cycle `true`인 상황에서도 실제 응답 지연과 명령어 대응 관계를 검증할 수 있습니다.

다음으로 현재 사용 중인 `VexRiscvTopSim.scala` 전체를 올려주세요. 기존 시뮬레이션의 reset 및 `waitSampling()` 흐름을 유지하면서 이 검증을 추가하겠습니다.

이제 기존 테스트 구조를 유지하면서 요청 PC와 응답 명령어를 FIFO 방식으로 대응시키겠습니다. `cmd.fire`가 발생한 PC를 큐에 넣고, `rsp.valid`가 발생할 때 가장 먼저 들어온 PC를 꺼내 해당 명령어와 비교하면 됩니다.

`top.scala`에서는 CPU와 ROM 연결 부분은 그대로 두고, `VexRiscvTopSim`만 교체하면 됩니다.

이번 검증에서는 `waitSampling()` 대신 `waitFallingEdge()`를 사용하겠습니다.

- Falling edge에서 현재 CMD를 관찰하고 PC를 큐에 저장합니다.
- 그다음 rising edge에서 해당 요청이 수락됩니다.
- 다음 falling edge에서 `RegNext`로 생성된 RSP를 관찰합니다.
- 응답 명령어와 큐에서 꺼낸 요청 PC를 비교합니다.

이렇게 하면 같은 cycle에 CMD와 RSP가 모두 `valid=true`여도 각각의 요청과 응답을 구분할 수 있습니다.

## 1. VexRiscvTopSim 교체 코드

기존 `object VexRiscvTopSim extends App` 전체를 다음 코드로 교체하세요.

```
object VexRiscvTopSim extends App {

  import scala.collection.mutable

  SimConfig.withWave
    .compile(new VexRiscvTop)
    .doSim { dut =>

      println("========================================")
      println(" VexRiscvTop IBus Request/Response Test")
      println("========================================")

      dut.clockDomain.forkStimulus(period = 10)
      dut.clockDomain.waitSampling(5)

      println("[INFO] Reset/clock startup complete")

      val rom = dut.system.instructionRom

      // 요청 PC를 저장하는 FIFO
      val pendingPc = mutable.Queue.empty[Long]

      var requestCount  = 0
      var responseCount = 0
      var firstObservation = true

      // 현재 ROM에 정의된 명령어 주소별 기대값
      def expectedInstruction(pc: Long): Long = {
        pc match {
          case 0x80000010L => 0x00100093L // ADDI x1, x0, 1
          case 0x80000004L => 0x0000006FL // JAL  x0, 0
          case _           => 0x00000013L // NOP
        }
      }

      // 응답 검증
      def checkResponse(cycle: Int): Unit = {

        val rspValid = rom.io.rsp.valid.toBoolean

        if (rspValid) {

          if (pendingPc.nonEmpty) {

            // 가장 먼저 요청한 PC
            val requestPc = pendingPc.dequeue()

            val rspInst  = rom.io.rsp.inst.toLong
            val rspError = rom.io.rsp.error.toBoolean

            val expected = expectedInstruction(requestPc)

            println(
              f"Cycle $cycle%2d : " +
                f"RSP pc=0x$requestPc%08X " +
                f"inst=0x$rspInst%08X " +
                f"expected=0x$expected%08X"
            )

            assert(
              !rspError,
              f"FAIL: ROM response error at PC 0x$requestPc%08X"
            )

            assert(
              rspInst == expected,
              f"FAIL: PC=0x$requestPc%08X " +
                f"expected=0x$expected%08X " +
                f"actual=0x$rspInst%08X"
            )

            responseCount += 1

          } else if (firstObservation) {

            // 모니터를 시작하기 전에 이미 발생한 응답
            println(
              "[INFO] Ignore one response already in flight before monitoring"
            )

          } else {

            assert(
              false,
              s"FAIL: Response without a tracked request at cycle $cycle"
            )
          }
        }
      }

      // 요청 관찰 및 PC 저장
      def captureCommand(cycle: Int): Unit = {

        val cmdValid = rom.io.cmd.valid.toBoolean
        val cmdReady = rom.io.cmd.ready.toBoolean

        if (cmdValid && cmdReady) {

          val cmdPc = rom.io.cmd.pc.toLong

          pendingPc.enqueue(cmdPc)
          requestCount += 1

          println(
            f"Cycle $cycle%2d : " +
              f"CMD fire PC=0x$cmdPc%08X"
          )
        }
      }

      // 요청/응답 추적
      for (cycle <- 1 to 50) {

        dut.clockDomain.waitFallingEdge()

        // 반드시 응답을 먼저 처리
        checkResponse(cycle)

        // 현재 요청을 FIFO에 저장
        captureCommand(cycle)

        firstObservation = false
      }

      // 마지막 요청의 응답까지 확인
      dut.clockDomain.waitFallingEdge()
      checkResponse(51)

      println()
      println("========================================")
      println(" IBus Request/Response Test Result")
      println("========================================")

      assert(
        requestCount > 0,
        "FAIL: No IBus command observed"
      )

      assert(
        responseCount == requestCount,
        s"FAIL: Request count=$requestCount, Response count=$responseCount"
      )

      assert(
        pendingPc.isEmpty,
        s"FAIL: Outstanding requests remain: ${pendingPc.size}"
      )

      println(s"[PASS] Requests  : $requestCount")
      println(s"[PASS] Responses : $responseCount")
      println("[PASS] All response instructions matched their request PCs")
      println("========================================")
      println(" IBus test finished")
      println("========================================")
    }
}
```

## 2. 이번 테스트에서 확인할 사항

현재 ROM의 명령어 주소는 다음과 같습니다.

Cycle  2 : CMD fire PC=0x80000004
Cycle  3 : RSP pc=0x80000004 inst=0x0000006F expected=0x0000006F

실제 PC 순서는 CPU 동작에 따라 달라질 수 있습니다.

## 2. 한 가지 알아둘 점

현재 ROM은 다음과 같은 프로그램을 반복해서 제공합니다.

```
0x80000004 : JAL x0, 0
0x80000008 : NOP
0x8000000C : NOP
0x80000010 : ADDI x1, x0, 1
```

이것은 현재 ROM의 응답 데이터 검증이지, CPU가 실제로 `ADDI`를 실행해 `x1 = 1`이 되었는지를 검증한 것은 아닙니다.

또한 현재 테스트는 `cmd.ready = true`인 무정지 연속 요청 조건입니다. 응답 정지나 요청 backpressure 상황은 아직 검증하지 않았습니다.
