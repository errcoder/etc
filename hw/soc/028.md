### 1. 첫 번째 시뮬레이션 실패 원인
먼저 이 오류를 구분해야 합니다.

AssertionError: Load response lasted longer than one cycle


이것은 GPIO 회로가 응답을 두 사이클 동안 출력했다는 뜻이 아닙니다. 테스트벤치가 응답을 관찰한 시점이 적절하지 않았던 것입니다.

GPIO의 응답 생성 코드는 다음과 같습니다.
```

```

시간 순서로 살펴보겠습니다.
```

상승 에지 N           Load 명령 수락       1

```

waitSampling()은 다음 클럭 상승 에지까지 기다림을 진행합니다. 

하지만 상승 에지 직후에는 시뮬레이터의 순차 논리 갱신과 신호 전파가 진행되는 스케줄링 단계가 있습니다.

따라서 상승 에지 직후에 바로 값을 읽으면 갱신 전 값을 관찰할 수 있습니다.

반면 waitFallingEdge()까지 진행하면 상승 에지에서 발생한 레지스터 갱신이 안정화된 뒤의 값을 확인할 수 있습니다.

### 2. 수정한 검증 코드가 올바른 이유
사용자가 수정한 코드는 다음과 같습니다.
```

  !dut.io.bus.rsp.ready.toBoolean,
  "Load response lasted longer than one cycle"
)
```

이 방법이 적절합니다.
- 첫 번째 하강 에지: 응답이 유효한지 확인
- 다음 하강 에지: 응답이 사라졌는지 확인
  
같은 클럭 위상의 하강 에지끼리 비교하므로 한 클럭 주기 동안 응답이 유지되었는지를 명확하게 검사합니다.

이번 실패는 GPIO 설계의 실패가 아니라 테스트벤치의 관찰 타이밍 문제였습니다. 제가 처음 제시한 검증 코드에서 이 점을 충분히 고려하지 못했습니다.

### 4. 다음 단계: DBusDecoder에 GPIO 통합
이제 독립적인 GPIO 주변장치 검증은 완료했습니다.

다음에는 기존에 검증했던 RAM과 Unmapped Load Error 기능을 유지하면서 GPIO를 DBusDecoder에 연결하겠습니다.

통합 후 주소별 동작은 다음과 같습니다.
```
주소                         장치         동작
0x00000000 ~ 0x000003FF      RAM         기존 동작
0x10000000 ~ 0x1000000F      GPIO        GPIO 레지스터 접근
그 외 주소                     Decoder    기존 Unmapped Load Error
```
여기서 가장 중요한 부분은 RAM과 GPIO의 Load 응답을 구분하여 CPU에 올바르게 전달하는 것입니다.

기존 RAM의 동기식 읽기 응답, GPIO의 한 사이클 응답, Unmapped Load Error 응답이 서로 섞이지 않도록 응답 소유자를 추적하는 구조를 만들겠습니다.

그리고 기존에 통과한 Trap, CSR, MRET 복구 동작은 그대로 보존하겠습니다.

이제 기존 `DBusDecoder`에 GPIO를 통합하겠습니다.

이번 변경의 핵심은 CPU가 주소를 내보내면 Decoder가 RAM과 GPIO 중 목적지를 선택하고, Load 응답이 돌아오면 그 응답을 발생시킨 장치의 데이터만 CPU에 전달하는 것입니다.

기존에 통과한 다음 기능은 유지합니다.

- RAM 주소 영역과 동기식 Load 응답
- GPIO 레지스터 접근
- Unmapped Load의 Error Response
- CPU의 Trap 및 MRET 동작

## 1. 통합 후 데이터 경로

VexRiscv CPU

DBusSimpleBus

DBusDecoder

주소 판별 및 응답 경로 선택

RAM

0x00000000 \~ 0x000003FF

GPIO

0x10000000 \~ 0x1000000F

Unmapped

그 외 주소

응답 경로를 선택하기 위해 Decoder 내부에 `loadOwner`라는 상태 레지스터를 두겠습니다.

| loadOwner | 의미                        |
| --------- | ------------------------- |
| `0`       | 현재 응답 대기 없음               |
| `1`       | RAM Load 응답 대기            |
| `2`       | GPIO Load 응답 대기           |
| `3`       | Unmapped Load Error 응답 대기 |

이 상태는 Store에는 설정하지 않습니다. Store는 현재 구조에서 응답을 기다리지 않기 때문입니다.

## 2. `DBusDecoder.scala` 전체 교체

기존 파일을 다음 코드로 교체하세요.

```scala
package myvexsoc

import spinal.core._
import vexriscv.plugin._

class DBusDecoder extends Component {

  val io = new Bundle {
    val cpu  = slave(DBusSimpleBus())
    val ram  = master(DBusSimpleBus())
    val gpio = master(DBusSimpleBus())
  }

  // ------------------------------------------------------------
  // Address decoding
  // ------------------------------------------------------------

  // RAM:
  // 0x00000000 ~ 0x000003FF
  val ramHit =
    io.cpu.cmd.address < U(0x00000400L, 32 bits)

  // GPIO:
  // 0x10000000 ~ 0x1000000F
  val gpioHit =
    io.cpu.cmd.address(31 downto 4) === U(0x01000000, 28 bits)

  // ------------------------------------------------------------
  // Command forwarding
  // ------------------------------------------------------------

  io.ram.cmd.valid := io.cpu.cmd.valid && ramHit
  io.ram.cmd.payload := io.cpu.cmd.payload

  io.gpio.cmd.valid := io.cpu.cmd.valid && gpioHit
  io.gpio.cmd.payload := io.cpu.cmd.payload

  // ------------------------------------------------------------
  // CPU command acceptance
  //
  // RAM/GPIO:
  //   Target peripheral controls ready.
  //
  // Unmapped Load:
  //   Accept immediately and generate an Error Response.
  //
  // Unmapped Store:
  //   Do not accept. Store Access Fault is not implemented.
  // ------------------------------------------------------------

  io.cpu.cmd.ready := Mux(
    ramHit,
    io.ram.cmd.ready,
    Mux(
      gpioHit,
      io.gpio.cmd.ready,
      !io.cpu.cmd.wr
    )
  )

  // ------------------------------------------------------------
  // Load command detection
  // ------------------------------------------------------------

  val loadFire =
    io.cpu.cmd.fire && !io.cpu.cmd.wr

  val unmappedLoadFire =
    loadFire && !ramHit && !gpioHit

  // ------------------------------------------------------------
  // Load response ownership
  // ------------------------------------------------------------

  val OWNER_NONE  = U(0, 2 bits)
  val OWNER_RAM   = U(1, 2 bits)
  val OWNER_GPIO  = U(2, 2 bits)
  val OWNER_ERROR = U(3, 2 bits)

  val loadOwner =
    Reg(UInt(2 bits)) init (OWNER_NONE)

  // Unmapped Load Error Response:
  // one cycle after the command is accepted.
  val errorPending =
    RegNext(unmappedLoadFire) init (False)

  // A newly accepted Load takes priority over clearing
  // the previous response owner.
  when(loadFire) {
    when(ramHit) {
      loadOwner := OWNER_RAM
    } elsewhen (gpioHit) {
      loadOwner := OWNER_GPIO
    } otherwise {
      loadOwner := OWNER_ERROR
    }
  } elsewhen (io.cpu.rsp.ready) {
    loadOwner := OWNER_NONE
  }

  // ------------------------------------------------------------
  // Response valid
  // ------------------------------------------------------------

  io.cpu.rsp.ready :=
    (loadOwner === OWNER_RAM && io.ram.rsp.ready) ||
    (loadOwner === OWNER_GPIO && io.gpio.rsp.ready) ||
    (loadOwner === OWNER_ERROR && errorPending)

  // ------------------------------------------------------------
  // Response data
  // ------------------------------------------------------------

  io.cpu.rsp.data :=
    Mux(
      loadOwner === OWNER_RAM,
      io.ram.rsp.data,
      Mux(
        loadOwner === OWNER_GPIO,
        io.gpio.rsp.data,
        B(0, 32 bits)
      )
    )

  // ------------------------------------------------------------
  // Response error
  // ------------------------------------------------------------

  io.cpu.rsp.error :=
    Mux(
      loadOwner === OWNER_RAM,
      io.ram.rsp.error,
      Mux(
        loadOwner === OWNER_GPIO,
        io.gpio.rsp.error,
        loadOwner === OWNER_ERROR && errorPending
      )
    )
}
```

  val gpioIn  = in Bits (32 bits)

  val gpioOe  = out Bits (32 bits)

## 4. 응답 소유자 추적이 필요한 이유

예를 들어 CPU가 다음 순서로 Load를 실행한다고 가정하겠습니다.

```
LW x1, 0(x0)          // RAM[0] 읽기
LW x2, 0x10000000     // GPIO_OUT 읽기
LW x3, 0x20000000     // Unmapped 주소 읽기
```

각각 응답을 만드는 장치가 다릅니다.

1. RAM은 `readSync()`를 통해 데이터를 반환합니다.
2. GPIO는 GPIO 레지스터 값을 반환합니다.
3. Unmapped 주소는 Decoder가 직접 Error Response를 생성합니다.

따라서 응답이 돌아왔을 때 Decoder는 어떤 장치의 응답인지 알아야 합니다.

이것이 `loadOwner`를 사용하는 이유입니다.

특히 CPU가 Load 응답을 기다리는 동안 다음 Load를 발행하지 않는다는 기존 DBusSimplePlugin의 동작을 이용합니다. 다만 새 Load 수락과 이전 응답 완료가 같은 사이클에 발생하는 경우에도 새 소유자 정보가 유지되도록 새 Load에 우선순위를 주었습니다.
