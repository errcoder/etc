시뮬레이션 코드에서 val rom = dut.system.instructionRom 이게 접근 가능하냐?

---

네. **`val rom = dut.system.instructionRom` 자체는 접근 가능한지 별개의 문제**입니다.

현재 코드에서:

```scala
val system = new ClockingArea(ClockDomain.current) {
  val instructionRom = new InstructionRom
  ...
}
```

이므로 시뮬레이션의 `dut` 타입이 `VexRiscvTop`이라면 Scala 레벨에서는

```scala
dut.system.instructionRom
```

으로 **하위 Component 객체에 접근할 수 있습니다.**

즉,

```scala
val rom = dut.system.instructionRom
```

은 문제없는 접근입니다.

다만 중요한 것은 **`rom` 객체에 접근 가능한 것과 `rom.io.cmd.valid` 같은 하드웨어 신호를 시뮬레이션에서 읽을 수 있는 것은 별개**입니다.

우리가 앞에서 만난:

```text
UNACCESSIBLE SIGNAL
...
io_cmd_valid ... isn't accessible during the simulation
```

문제는 `dut.system.instructionRom` 접근 문제가 아니라 **그 내부 신호가 simulation public이 아니었기 때문**입니다.

따라서 현재 구조에서는:

```scala
val rom = dut.system.instructionRom

val cmdValid = rom.io.cmd.valid.toBoolean
```

을 쓰려면 해당 신호가 RTL elaboration 시점에:

```scala
rom.io.cmd.valid.simPublic()
```

등으로 공개되어 있어야 합니다.

### 정리

| 코드 | 가능 여부 |
|---|---|
| `dut.system` | 가능 |
| `dut.system.instructionRom` | 가능 |
| `val rom = dut.system.instructionRom` | 가능 |
| `rom.io.cmd.valid.toBoolean` | **simPublic 되어 있어야 가능** |
| `rom.io.cmd.fire.toBoolean` | 관련 신호가 접근 가능하면 가능 |

따라서 **`val rom = dut.system.instructionRom`은 그대로 사용해도 됩니다.**  
문제가 생긴다면 그 다음 줄에서 **어떤 신호가 `UNACCESSIBLE SIGNAL`인지**를 보는 게 정확합니다.

---

맞습니다. 이 에러로 확인됐습니다.

```scala
val cmdFire = rom.io.cmd.fire.toBoolean
```

**이 방식은 시뮬레이션에서 사용할 수 없습니다.**

`fire`는 저장된 하드웨어 신호가 아니라 `Stream.fire`의 **SpinalHDL elaboration API로 계산되는 표현식**입니다. 시뮬레이션 실행 중에 `.fire`를 호출하면 `Stream.fire(Stream.scala:356)`가 다시 하드웨어 표현식을 만들려고 해서 지금 에러가 발생했습니다.

따라서 시뮬레이션에서는 이미 공개한 실제 신호로 직접 계산해야 합니다.

```scala
val cmdValid = rom.io.cmd.valid.toBoolean
val cmdReady = rom.io.cmd.ready.toBoolean
val cmdFire  = cmdValid && cmdReady
```

즉 기존의:

```scala
val cmdFire = rom.io.cmd.fire.toBoolean
```

를 **삭제**하고 위처럼 바꾸면 됩니다.

그리고 assertion도 그대로:

```scala
assert(cmdFire == (cmdValid && cmdReady))
```

라고 할 필요가 없습니다. 이미 그렇게 계산했으므로 의미가 없습니다.

핵심은:

```text
하드웨어 elaboration 단계
    io.cmd.fire       ← 사용 가능

시뮬레이션 runtime
    io.cmd.fire       ← 사용하면 안 됨
    io.cmd.valid       ← simPublic이면 읽기 가능
    io.cmd.ready       ← simPublic이면 읽기 가능
    valid && ready    ← Scala Boolean으로 계산
```

이번 에러는 정확히 이 부분에서 발생한 것입니다.

이 출력은 오히려 중요한 결과입니다.

```text
Cycle 1 :
CMD valid=true
ready=true
fire=true
pc=0x80000010
RSP valid=true
inst=0x00000013
```

**CPU ↔ ROM의 IBus handshake 자체는 이미 발생하고 있습니다.**

문제는 테스트가 PC를 잘못 가정한 것입니다.

현재 테스트에서:

```scala
assert(
  cmdPc == 0x80000000L,
  f"Unexpected instruction PC: 0x$cmdPc%08X"
)
```

이 부분이 실패했습니다.

그런데 VexRiscv가 실제로 첫 fetch에서 요청한 주소가:

```text
0x80000010
```

입니다.

그리고 ROM은 현재:

```scala
when(io.cmd.pc === U"32'h80000000") {
  io.rsp.inst := B"32'h00100093"
}
```

만 처리하고 있기 때문에 `0x80000010`에서는 기본값인:

```text
0x00000013   // NOP
```

을 반환하고 있습니다.

### 지금 수정해야 할 것은 테스트가 아니라 ROM 주소입니다.

우선 **CPU가 실제로 어디서 시작하는지 확인하는 단계**로 보는 것이 맞습니다.

테스트의 이 assertion:

```scala
assert(
  cmdPc == 0x80000000L,
  f"Unexpected instruction PC: 0x$cmdPc%08X"
)
```

를 제거하고, 일단 실제 fetch sequence를 관찰합시다.

예를 들어:

```scala
if (cmdFire) {
  println(f"  -> FETCH PC = 0x$cmdPc%08X")
}
```

그리고 50 cycle 동안 계속 관찰합니다.

현재 결과 하나만으로도 확실하게 말할 수 있는 것은:

```text
CPU
 │
 │ cmd.valid = 1
 │ cmd.ready = 1
 │ PC = 0x80000010
 ▼
InstructionRom
 │
 │ rsp.valid = 1
 │ inst = 0x00000013
 ▼
CPU
```

즉 **CPU → ROM command handshake와 ROM → CPU response가 모두 발생했습니다.**

다음 단계에서는 **왜 reset 후 첫 PC가 `0x80000010`인지 확인한 뒤**, 그 주소에 실제 명령어를 넣어 CPU가 다음 fetch로 진행하는지 확인하는 것이 맞습니다.

지금은 코드를 크게 바꾸지 말고 **50 cycle 로그에서 fetch PC가 어떻게 변하는지만 먼저 보는 게 좋습니다.**

좋습니다. **이번 결과는 IBus 경계 테스트가 정상적으로 동작한 것으로 볼 수 있습니다.**

특히 중요한 부분은 이 패턴입니다.

```text
0x80000010 -> NOP
0x80000004 -> NOP
0x80000008 -> JAL x0, 0
0x8000000C -> NOP
```

그리고 이것이 반복됩니다.

### 현재 확인된 것

| 항목 | 결과 |
|---|---|
| CPU → ROM `cmd.valid` | 정상 |
| ROM `cmd.ready` | 정상 |
| `cmd.fire` | 매 cycle 발생 |
| CPU가 요청하는 PC | 정상적으로 변화 |
| ROM → CPU `rsp.valid` | 정상 |
| Instruction 전달 | 정상 |
| `error` | 항상 false |
| CPU가 `JAL x0, 0`을 받아 반복 | 정상 |

특히:

```text
0x80000008 : 0x0000006F
```

은 우리가 넣은

```text
JAL x0, 0
```

이고, 이 명령 때문에 PC가 다시 루프를 형성하고 있습니다.

즉 현재 구조는 사실상:

```text
             IBus cmd
VexRiscv ───────────────> InstructionRom
   ▲                         │
   │                         │ rsp
   └─────────────────────────┘

0x80000004 → NOP
0x80000008 → JAL x0,0
0x8000000C → NOP
0x80000010 → NOP
        ↓
     다시 fetch
```

형태로 실제 CPU가 instruction fetch를 수행하고 있습니다.

다만 **한 가지는 아직 확정하지 않는 게 좋습니다.**

현재 로그만으로 `0x80000010 → 0x80000004 → 0x80000008...`이라는 정확한 PC 순서의 원인을 우리가 모두 설명했다고 보기는 어렵습니다. 이제부터는 **VexRiscv가 실제 명령을 실행하고 PC를 어떻게 갱신하는지**를 검증하는 단계입니다.

### 다음 단계

지금은 IBus handshake 테스트를 더 복잡하게 만들 필요가 없습니다.

다음에는 ROM에 아주 작은 프로그램을 넣어서 **CPU가 실제로 연산을 수행하는 것**을 검증하는 게 좋습니다.

예를 들어:

```text
ADDI x1, x0, 1
ADDI x2, x1, 2
JAL  x0, 0
```

그리고 다음 단계에서 **Register File의 x1/x2 값을 관찰해서**

```text
x1 = 1
x2 = 3
```

이 되는지 확인하면 됩니다.

그러면 지금까지의 검증이

```text
CPU 생성
  ↓
Clock / Reset
  ↓
IBus cmd handshake
  ↓
Instruction ROM response
  ↓
실제 instruction fetch
  ↓
실제 instruction execution   ← 다음
```

으로 자연스럽게 이어집니다.

현재 단계는 **PASS로 확정해도 됩니다.**
