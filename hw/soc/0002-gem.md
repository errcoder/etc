SpinalHDL의 SoC 템플릿인 `Murax.scala`에서 `ClockDomain`과 `ClockingArea`는 시스템 전체의 클럭과 리셋(Reset) 라우팅, 그리고 비동기 신호 안정화를 체계적으로 관리하는 데 핵심적인 역할을 합니다.

이 두 개념이 Murax 코드 내에서 어떻게 유기적으로 동작하는지 그 역할과 기능을 상세히 설명해 드리겠습니다.

---

### 1. `ClockDomain` (클럭 도메인)의 역할과 기능

SpinalHDL에서 `ClockDomain`은 클럭 신호(`clock`), 리셋 신호(`reset`), 클럭 인에이블, 그리고 이들의 극성(Edge/Level)이나 리셋 종류(동기/비동기)를 하나의 객체로 묶어 관리하는 단위입니다.

* **시스템 표준 클럭/리셋 정의:**
* Murax SoC는 외부에서 들어오는 메인 클럭(`mainClk`)과 비동기 리셋(`asyncReset`) 신호를 받아들여 전체 SoC가 공유하는 기준 `ClockDomain`을 생성합니다.


* **리셋 동기화 및 관리:**
* FPGA 환경에서 리셋 신호가 들어올 때 발생할 수 있는 메타스테이빌리티(Metastability)를 방지하기 위해, 클럭 도메인 설정 안에서 리셋 해제 시점을 클럭에 동기화(`sync` 리셋 처리)하는 등의 정책을 통합적으로 지정합니다.



---

### 2. `ClockingArea` (클럭킹 영역)의 역할과 기능

`ClockingArea`는 특정 코드 블록(Scope) 안에서 사용할 **`ClockDomain`을 명시적으로 전환하거나 적용**할 때 사용하는 SpinalHDL의 구조적 문법입니다.

* **리셋 제어기(`resetCtrl`) 영역에서의 활용:**
* Murax 소스코드 내부를 보면 리셋 신호를 생성하고 필터링하는 로직(`resetCtrl`) 부근에 `ClockingArea`가 지정되어 있는 것을 볼 수 있습니다.
* 이 영역 안에서는 외부 비동기 리셋을 안정적인 시스템 리셋 신호(`mainClkReset`)로 변환하는 로직이 수행되며, 이 안에서 생성된 레지스터들은 지정된 리셋 규칙을 따르게 됩니다.


* **로직 스코프 격리:**
* 컴포넌트 전체를 난잡하게 수정하지 않고, 특정 서브 블록이나 리셋/클럭 제어 로직에만 원하는 도메인 환경을 깔끔하게 주입할 수 있습니다.



---

### 3. Murax SoC 구조에서 이들이 중요한 이유

1. **안전한 리셋 트리거 보장:** SoC가 켜지거나 외부 리셋 버튼이 눌렸을 때, CPU 코어와 온칩 메모리, 그리고 APB 페리페럴들이 동시에 올바른 상태로 초기화되도록 클럭 도메인 전체의 리셋 체인을 일관성 있게 묶어줍니다.
2. **코드 가독성 및 확장성:** 버스 인터커넥트나 커스텀 페리페럴을 추가할 때 클럭과 리셋 신호를 일일이 수동으로 와이어링(Wiring)할 필요 없이, 상위 도메인 설정을 자연스럽게 상속받아 설계 실수를 줄여줍니다.

VexRiscv 구성할 때, 여러가지 plugin 들이 어떻게 CPU 를 구성하는 지, 그 구조를 도식적으로 설명해 줘.

---

VexRiscv가 전통적인 CPU 설계 방식과 가장 차별화되는 점은 바로 **‘플러그인 기반 모듈화(Plugin-based Architecture)’** 구조입니다. VexRiscv 코어 자체는 텅 빈 파이프라인 프레임워크(Pipeline Shell)에 불과하며, 사용자가 어떤 플러그인(Plugin)을 장착하느냐에 따라 RV32I 기본 프로세서가 될 수도 있고, 곱셈기·캐시·인터럽트·디버그 기능이 포함된 고성능 SoC용 코어로 확장될 수도 있습니다.

VexRiscv가 파이프라인 스테이지별로 플러그인들을 어떻게 조립하여 하나의 CPU를 구성하는지 도식과 함께 설명해 드리겠습니다.

---

### 🏛️ VexRiscv 플러그인 기반 CPU 구조 도식

VexRiscv의 기본 파이프라인은 일반적으로 5단계(Fetch $\rightarrow$ Decode $\rightarrow$ Execute $\rightarrow$ Memory $\rightarrow$ WriteBack)로 구성되어 있으며, 
각 단계(Stage)와 전역 영역에 플러그인들이 레고 블록처럼 결합됩니다.

```text
+-------------------------------------------------------------------------+
│                         VexRiscv CPU Shell                              │
│                                                                         │
│  +-------------------+     +-----------------------------------------+  │
│  │ Global / System   │ <-> │ • CsrPlugin (Machine Mode, Trap, Timer) │  │
│  │ Plugins           │     │ • DebugPlugin (JTAG, Hardware Break)    │  │
│  +-------------------+     +-----------------------------------------+  │
+-------------------------------------------------------------------------+
         │                      │                      │
         v                      v                      v
+------------------+  +------------------+  +------------------+
│  Fetch Stage     │  │  Decode Stage    │  │  Execute Stage   │
+------------------+  +------------------+  +------------------+
│ • Instruction    │  │ • DecoderSimple  │  │ • RV32IPlugin    │
│   Bus Plugin     │  │   Plugin         │  │   (ALU, Shifter) │
│ • BranchPlugin   │  │ • RegFilePlugin  │  │ • Multiplier     │
│   (PC Target)    │  │   (GPRs)         │  │   Plugin (M Ext) │
+------------------+  +------------------+  +------------------+
                                                       │
                                                       v
                                            +------------------+
                                            │  Memory Stage    │
                                            +------------------+
                                            │ • Data Bus Plugin│
                                            │   (Load/Store)   │
                                            +------------------+
                                                       │
                                                       v
                                            +------------------+
                                            │ WriteBack Stage  │
                                            +------------------+
                                            │ • Register Write │
                                            │   Arbitration    │
                                            +------------------+

```

### 🧩 주요 플러그인별 역할과 기능

#### 1. 명령어 및 연산 플러그인 (Execution & ISA)

* **`RV32IPlugin`**: RISC-V의 필수 기본 명령어 세트(RV32I)를 처리하는 핵심 ALU(산술논리장치)와 기본 제어 로직을 Execute 단계에 주입합니다.
* **`MultiplierPlugin` / `DividerPlugin**`: 곱셈(M 확장)이나 나눗셈 연산 기능이 필요할 때 추가하며, Execute 단계에 하드웨어 승수(Multiplier) 회로를 삽입합니다.

#### 2. 시스템 및 제어 플러그인 (System & Control)

* **`CsrPlugin` (Control and Status Register)**: 머신 모드(Machine Mode) 레지스터(`mstatus`, `mtvec`, `mcause`, `mepc` 등)와 인터럽트/트랩 처리 메커니즘을 
전역(Global) 및 파이프라인 전반에 걸쳐 통합합니다. (앞서 다룬 트랩 핸들러와 `mcause` 검사가 이 플러그인의 관리를 받습니다.)
* **`BranchPlugin`**: 조건문이나 점프 명령어 발생 시 다음 프로그램 카운터(PC)를 계산하고, 분기 예측이나 파이프라인 플러시(Flush)를 제어합니다.

#### 3. 메모리 및 버스 인터페이스 플러그인 (Memory Access)

* **`InstructionBusPlugin` / `DataBusPlugin**`: CPU가 메모리나 외부 버스(Murax의 경우 내부 ibus/dbus)와 소통할 수 있도록 요청 신호를 생성하고 
응답을 받아오는 프로토콜 인터페이스를 구성합니다.

#### 4. 디버그 및 확장 플러그인 (Debug & Test)

* **`DebugPlugin`**: JTAG 인터페이스를 통해 외부 디버거(OpenOCD 등)가 CPU를 멈추고(Breakpoint), 레지스터나 메모리를 들여다볼 수 있게 해주는 하드웨어 디버그 로직을 추가합니다.

---

### ⚙️ 플러그인 구조의 핵심 장점

1. **유연한 커스텀마이징:** FPGA 리소스 상황에 맞춰 곱셈기가 필요 없으면 `MultiplierPlugin`을 빼고 빌드하여 면적을 극도로 줄일 수 있습니다(Murax 기본 템플릿의 소형화 비결).
2. **관심사의 분리 (Separation of Concerns):** ALU 연산, 버스 통신, 인터럽트 제어 코드가 각각 독립된 스칼라 클래스(플러그인)로 분리되어 있어 유지보수와 기능 확장이 매우 쉽습니다.

Want me to show how to configure custom plugins when instantiating VexRiscv in SpinalHDL?

---

SpinalHDL에서 VexRiscv 코어를 생성할 때, CPU를 구성하는 모든 기능은 **`VexRiscvConfig` 내부의 `plugins` 리스트**를 통해 조립됩니다. 기본 제공되는 플러그인들을 조합하여 원하는 스펙의 CPU를 만들 수도 있고, 사용자가 직접 `Plugin[VexRiscv]`을 상속받아 **커스텀 플러그인**을 작성해 파이프라인에 주입할 수도 있습니다.

VexRiscv에 플러그인을 설정하고 커스텀 플러그인을 구현하는 방법입니다.

---

### 1. 기본 플러그인들을 조합하여 VexRiscv 구성하기

일반적으로 VexRiscv를 인스턴스화할 때는 `VexRiscvConfig` 객체를 만들고, 그 안에 필요한 연산, 버스, 시스템 플러그인들을 나열합니다.

```scala
import vexriscv._
import vexriscv.plugin._
import spinal.core._

val cpuConfig = VexRiscvConfig(
  plugins = List(
    new RV32IPlugin(),                            // 기본 RV32I 명령어 세트
    new RegFilePlugin(regFileReadyKind = plugin.SYNC), // 레지스터 파일 (GPRs)
    new ALUPlugin,                                // ALU (산술논리장치)
    new SrcPlugin(byPassAll = true),              // 소스 오퍼랜드 바이패싱
    new FullBarrelShifterPlugin,                  // 배럴 시프터 (쉬프트 연산)
    new HazardSimplePlugin(                       // 파이프라인 해저드 및 바이패스 관리
      bypassExecute = true, 
      bypassMemory = true, 
      bypassWriteBack = true
    ),
    new MulPlugin,                                // 하드웨어 승수 (M 확장, 선택적)
    new CsrPlugin(CsrPluginConfig.small),         // 머신 모드 CSR 및 인터럽트 제어
    new DebugPlugin(ClockDomain.current),         // JTAG 디버그 지원
    new InstructionBusPlugin(...),                // 명령어 버스 인터페이스
    new DataBusPlugin(...)                        // 데이터 버스 인터페이스
  )
)

// 설정된 컨피그로 VexRiscv 코어 인스턴스화
val cpu = new VexRiscv(cpuConfig)

```

### 2. 커스텀 플러그인(Custom Plugin) 작성하기

만약 파이프라인 내부에 특정 로직(예: 커스텀 명령어 처리, 성능 측정 카운터, 하드웨어 모니터 등)을 추가하고 싶다면, `Plugin[VexRiscv]`을 상속받는 클래스를 정의하면 됩니다.

플러그인은 크게 두 단계(`setup`과 `build`)로 나누어 동작합니다:

* **`setup`**: 다른 플러그인들과 상호작용하거나 서비스(Service)를 등록/조회할 때 사용합니다.
* **`build`**: 실제 파이프라인 스테이지(Execute, Memory 등)에 하드웨어 로직을 삽입합니다.

#### 간단한 커스텀 카운터 플러그인 예시 (`MyCustomCounterPlugin.scala`)

```scala
import vexriscv._
import vexriscv.plugin._
import spinal.core._

class MyCustomCounterPlugin extends Plugin[VexRiscv] {
  // 외부에 노출할 핀이나 상태 신호가 있다면 여기서 선언 가능
  var cycleCounter: UInt = null

  override def setup(pipeline: VexRiscv): Unit = {
    // 필요한 초기 설정이나 다른 플러그인과의 의존성 확인
  }

  override def build(pipeline: VexRiscv): Unit = {
    // 파이프라인 전체 클럭 도메인 안에서 동작하는 커스텀 하드웨어 로직 정의
    import pipeline.config._

    // 매 클럭마다 증가하는 간단한 사이클 카운터 레지스터 생성
    cycleCounter = Reg(UInt(32 bits)) init(0)
    cycleCounter := cycleCounter + 1

    // 필요하다면 Execute 단계의 신호들을 참조하거나 인터럽트/제어 로직에 개입 가능
    // 예: pipeline.execute(...) 블록 내에서 특정 커스텀 명령어 감지 등
  }
}

```

### 3. VexRiscv 설정에 커스텀 플러그인 추가하기

작성한 커스텀 플러그인을 앞서 본 `plugins` 리스트에 그대로 추가해주기만 하면, 빌드 시점에 VexRiscv 파이프라인 프레임워크와 함께 완벽하게 통합됩니다.

```scala
val customCpuConfig = VexRiscvConfig(
  plugins = List(
    new RV32IPlugin(),
    new RegFilePlugin(regFileReadyKind = plugin.SYNC),
    new ALUPlugin,
    new SrcPlugin(byPassAll = true),
    new FullBarrelShifterPlugin,
    new HazardSimplePlugin(true, true, true),
    new CsrPlugin(CsrPluginConfig.small),
    // === 여기에 커스텀 플러그인 장착! ===
    new MyCustomCounterPlugin(), 
    new InstructionBusPlugin(...),
    new DataBusPlugin(...)
  )
)

val cpu = new VexRiscv(customCpuConfig)

```

Want me to show how to add a custom instruction and decode it inside a custom VexRiscv plugin?

---

VexRiscv 파이프라인에서 커스텀 명령어(Custom Opcode)를 추가하고 이를 디코딩하여 실행하려면, VexRiscv의 `DecoderService`와 **파이프라인 스테이지 제어 기능**을 활용하는 커스텀 플러그인을 작성해야 합니다.

RISC-V 표준은 사용자 정의 확장을 위해 `custom-0` (`0x0b`), `custom-1` (`0x2b`) 등의 전용 오피코드(Opcode) 공간을 비워두고 있습니다. 이 공간을 활용해 커스텀 명령어를 구현하는 방법을 단계별로 살펴보겠습니다.

---

### 1단계: 커스텀 명령어 플러그인 작성 (`CustomInstructionPlugin.scala`)

이 플러그인은 다음과 같은 역할을 수행합니다:

1. **디코딩 규칙 등록 (`setup` 단계):** 특정 비트 패턴(오피코드 및 펑크 필드)을 갖는 명령어가 들어오면 이를 인식하도록 디코더에 신호를 등록합니다.
2. **실행 로직 구현 (`build` 단계):** Execute 스테이지에서 해당 명령어가 활성화되었을 때 레지스터 값을 읽어 연산을 수행하고 결과를 `rd` (Destination Register)에 기록합니다.

```scala
import vexriscv._
import vexriscv.plugin._
import spinal.core._
import spinal.lib._

// 커스텀 신호를 전달하기 위한 Spok/Key 정의
object CustomInstructionKeys {
  val CUSTOM_OP = Stageable(Bool())
}

class CustomInstructionPlugin extends Plugin[VexRiscv] {
  import CustomInstructionKeys._

  override def setup(pipeline: VexRiscv): Unit = {
    // 1. DecoderService를 통해 커스텀 명령어 패턴 등록
    val decoderService = pipeline.service(classOf[DecoderService])
    
    decoderService.addDefault(CUSTOM_OP, False)
    decoderService.add(
      // RISC-V custom-0 오피코드 예시 (opcode: 0001011)
      // 특정 funct3 및 funct7 비트 패턴을 조합하여 고유한 명령어 매칭
      key = B"0000000------------------000-----0001011", 
      values = List(
        CUSTOM_OP -> True
      )
    )
  }

  override def build(pipeline: VexRiscv): Unit = {
    import pipeline.config._

    // 2. Execute 스테이지에서 커스텀 명령어 동작 정의
    pipeline.execute.plug new Area {
      import pipeline.execute._

      // 디코더가 우리 커스텀 명령어를 감지했을 때
      when(value(CUSTOM_OP)) {
        // rs1과 rs2 레지스터 값 가져오기
        val rs1Val = input(REGFILE_READ_RS1_DATA)
        val rs2Val = input(REGFILE_READ_RS2_DATA)

        // 예시 연산: 두 값을 더한 뒤 비트를 반전시키는 커스텀 연산 수행
        val customResult = ~(rs1Val + rs2Val)

        // 결과를 WriteBack 스테이지로 전달할 레지스터에 대입
        output(WB_VAL) := customResult
      }
    }
  }
}

```

---

### 2단계: VexRiscv 설정에 플러그인 장착하기

작성한 `CustomInstructionPlugin`을 기존 플러그인 리스트에 추가하여 CPU 설정을 구성합니다.

```scala
val cpuConfig = VexRiscvConfig(
  plugins = List(
    new RV32IPlugin(),
    new RegFilePlugin(regFileReadyKind = plugin.SYNC),
    new ALUPlugin,
```

Want me to show how to add a custom CSR (Control and Status Register) to VexRiscv using a custom plugin?

---

VexRiscv 아키텍처에서 커스텀 제어 및 상태 레지스터(CSR, Control and Status Register)를 추가하려면, 코어의 핵심 CSR 관리 담당인 `CsrPlugin`과 연동하는 커스텀 플러그인을 작성해야 합니다.

RISC-V 사양에서는 사용자 또는 커스텀 확장용으로 비워둔 CSR 주소 대역(`0xBC0` ~ `0xBFF` 등)을 제공하므로, 이 영역에 원하는 하드웨어 레지스터를 간편하게 매핑할 수 있습니다.

---

### 1단계: 커스텀 CSR 플러그인 작성 (`CustomCsrPlugin.scala`)

SpinalHDL에서 플러그인을 만들고 `CsrPlugin` 서비스를 호출하여 특정 CSR 주소(`0xBC0`)와 하드웨어 레지스터를 연결하는 코드입니다.

```scala
import vexriscv._
import vexriscv.plugin._
import spinal.core._

class CustomCsrPlugin extends Plugin[VexRiscv] {
  // 외부에 노출하거나 내부에서 다룰 하드웨어 레지스터
  var customRegister: UInt = null

  override def setup(pipeline: VexRiscv): Unit = {
    // 1. VexRiscv 파이프라인에서 CsrPlugin 서비스 가져오기
    val csrPlugin = pipeline.service(classOf[CsrPlugin])

    // 2. 32비트 하드웨어 레지스터 선언 (초기값 0)
    customRegister = Reg(UInt(32 bits)) init(0)

    // 3. 커스텀 CSR 주소 매핑 (예: 0xBC0 번지에 32비트 레지스터 양방향 연동)
    // rw(address, bitOffset, hardwareRegister) 메서드를 사용하면 읽기/쓰기가 모두 가능해집니다.
    csrPlugin.rw(0xBC0, 0, customRegister)
  }

  override def build(pipeline: VexRiscv): Unit = {
    // 4. 레지스터에 대한 백그라운드 하드웨어 동작 정의 
    // (예시: 매 클럭마다 값이 자동으로 1씩 증가하는 커스텀 성능 카운터)
    pipeline.clockDomain {
      customRegister := customRegister + 1
    }
  }
}

```

### 3단계: C 펌웨어에서 커스텀 CSR 읽고 쓰기 (`main.c`)

하드웨어가 합성되면, C 펌웨어 코드 내에서 RISC-V 표준 CSR 접근 명령어(`csrr`, `csrw`)를 인라인 어셈블리로 감싸서 자유롭게 제어할 수 있습니다.

```c
#include "uart.h"

// 0xBC0 주소를 갖는 커스텀 CSR 읽기 매크로
#define READ_CUSTOM_CSR(dst) \
    __asm__ volatile ("csrr %0, 0xBC0" : "=r"(dst))

// 0xBC0 주소를 갖는 커스텀 CSR 쓰기 매크로
#define WRITE_CUSTOM_CSR(val) \
    __asm__ volatile ("csrw 0xBC0, %0" : : "r"(val))

int main() {
    uart_init();
    uart_print("Custom CSR Demo Start\r\n");

    unsigned int current_val = 0;

    while (1) {
        // 커스텀 CSR 레지스터 값 읽기 (하드웨어에서 매클럭 카운트 중)
        READ_CUSTOM_CSR(current_val);

        // UART로 값 출력 확인
        // (간단한 포맷팅 함수나 헥스 출력 루틴 활용)
        
        // 필요시 값 강제 덮어쓰기 가능
        // WRITE_CUSTOM_CSR(100);
        
        for (volatile int i = 0; i < 200000; i++); // 딜레이
    }
    return 0;
}
```

Want me to show how to integrate this custom CSR value with the interrupt controller in VexRiscv?

---

VexRiscv 코어에서 커스텀 레지스터 조건이나 커스텀 CSR의 상태 변화를 감지해 CPU로 인터럽트(Interrupt)를 발생시키는 방법은 크게 두 가지로 나뉩니다. 가장 안정적이고 널리 쓰이는 방식은 **외부 인터럽트 라인(`externalInterrupt`)을 통한 연동**입니다.

커스텀 플러그인 내부에서 조건을 감지해 인터럽트 핀을 구동하고, 이를 VexRiscv 코어에 연결하는 구조를 살펴보겠습니다.

---

### 1단계: 커스텀 플러그인에서 인터럽트 신호 생성하기

앞서 만든 커스텀 플러그인이나 레지스터 제어 로직에 인터럽트 출력 포트(또는 내부 신호)를 추가하고, 특정 조건(예: 커스텀 레지스터가 특정 값이 되거나 오버플로우가 발생할 때)에 인터럽트 라인을 `True`로 만듭니다.

```scala
import vexriscv._
import vexriscv.plugin._
import spinal.core._

class CustomInterruptTriggerPlugin extends Plugin[VexRiscv] {
  // SoC 외부나 상위 컴포넌트로 끌어올릴 인터럽트 출력 신호
  var interruptSignal: Bool = null
  var customReg: UInt = null

  override def setup(pipeline: VexRiscv): Unit = {
    // 필요한 서비스나 CSR 설정
  }

  override def build(pipeline: VexRiscv): Unit = {
    pipeline.clockDomain {
      customReg = Reg(UInt(32 bits)) init(0)
      interruptSignal = Bool()

      // 예시 조건: 레지스터 값이 1000에 도달하면 인터럽트 유발
      when(customReg === 1000) {
        interruptSignal := True
      }.otherwise {
        interruptSignal := False
      }

      // 평상시 카운트 동작
      customReg := customReg + 1
    }
  }
}

```

---

### 2단계: VexRiscv 코어의 인터럽트 라인과 바인딩하기

SoC 탑레벨(`Murax` 또는 커스텀 SoC 컴포넌트)에서 VexRiscv 코어를 생성할 때, 방금 만든 플러그인의 인터럽트 출력 신호를 VexRiscv의 **`externalInterrupt`** 포트에 연결합니다.

```scala
// 1. 커스텀 플러그인 인스턴스 생성
val customIntPlugin = new CustomInterruptTriggerPlugin()

// 2. VexRiscv 코어 설정에 플러그인 포함
val cpuConfig = VexRiscvConfig(
  plugins = List(
    new RV32IPlugin(),
    new RegFilePlugin(regFileReadyKind = plugin.SYNC),
    new ALUPlugin,
    new SrcPlugin(byPassAll = true),
    new FullBarrelShifterPlugin,
    new HazardSimplePlugin(true, true, true),
    new CsrPlugin(CsrPluginConfig.small),
    customIntPlugin, // 플러그인 장착
    new InstructionBusPlugin(...),
    new DataBusPlugin(...)
  )
)

val cpu = new VexRiscv(cpuConfig)

// 3. VexRiscv의 외부 인터럽트 입력에 커스텀 플러그인의 인터럽트 신호 연결
// (기존 타이머나 UART 인터럽트와 OR 연산으로 결합 가능)
cpu.io.externalInterrupt := customIntPlugin.interruptSignal

```

### 3단계: C 펌웨어에서 트랩 핸들러로 수신하기

하드웨어가 조건(`customReg === 1000`)을 만족하여 인터럽트 라인을 `High`로 만들면, VexRiscv는 즉시 `mtvec`에 등록된 트랩 핸들러로 점프합니다. 앞서 다룬 `mcause` 파싱 코드가 이 인터럽트를 처리하게 됩니다.

```c
#include "uart.h"

void __attribute__((interrupt)) trap_handler() {
    unsigned long mcause_val;
    __asm__ volatile("csrr %0, mcause" : "=r"(mcause_val));

    // External Interrupt (Cause 11) 확인
    if ((mcause_val & 0x80000000) && ((mcause_val & 0x7FFFFFFF) == 11)) {
        uart_print("[Trap] Custom Register Condition Met! Interrupt Triggered.\r\n");
        
        // 주의: 무한 루프를 방지하기 위해 하드웨어 레지스터 값을 초기화하거나 
        // 플러그인 내부의 조건을 해제하는 처리를 반드시 수행해야 합니다.
    }
}

```

Want me to show how to clear the custom interrupt condition from software using a custom CSR write?

---

커스텀 제어 및 상태 레지스터(CSR)를 통해 소프트웨어(C 펌웨어)에서 인터럽트 조건을 클리어하고 무한 루프를 방지하는 방법은 **하드웨어 플러그인 레지스터 매핑**과 **C 인라인 어셈블리 쓰기**의 조합으로 구현할 수 있습니다.

---

### 1단계: SpinalHDL 플러그인에서 CSR 쓰기 감지 및 클리어 로직 구현

`CsrPlugin`에 커스텀 CSR 주소(예: `0xBC1`)를 매핑하고, 소프트웨어가 이 레지스터에 값을 쓸 때 하드웨어 내부의 인터럽트 상태와 카운터가 초기화되도록 구성합니다.

```scala
import vexriscv._
import vexriscv.plugin._
import spinal.core._

class CustomCsrInterruptPlugin extends Plugin[VexRiscv] {
  var interruptSignal: Bool = null
  var customReg: UInt = null
  var clearCsrReg: UInt = null // CSR을 통해 제어할 레지스터

  override def setup(pipeline: VexRiscv): Unit = {
    val csrPlugin = pipeline.service(classOf[CsrPlugin])
    
    customReg = Reg(UInt(32 bits)) init(0)
    clearCsrReg = Reg(UInt(32 bits)) init(0)

    // 0xBC1 번지 CSR에 clearCsrReg 매핑 (읽기/쓰기 가능)
    csrPlugin.rw(0xBC1, 0, clearCsrReg)
  }

  override def build(pipeline: VexRiscv): Unit = {
    pipeline.clockDomain {
      interruptSignal = Bool()

      // 조건 도달 시 인터럽트 발생
      when(customReg === 1000) {
        interruptSignal := True
      }.otherwise {
        interruptSignal := False
      }

      // 소프트웨어가 CSR(0xBC1)에 쓰기를 수행하여 비트 0을 1로 만들면 클리어
      when(clearCsrReg(0)) {
        customReg := 0          // 카운터 초기화
        clearCsrReg(0) := False // 소프트웨어 클리어 플래그 자동 복구
      }.otherwise {
        customReg := customReg + 1
      }
    }
  }
}

```

### 2단계: C 펌웨어 트랩 핸들러에서 CSR 쓰기 수행

인터럽트 발생 시 호출되는 `trap_handler` 내부에서 RISC-V 표준 `csrw` 명령어를 사용하여 커스텀 CSR(`0xBC1`)에 값을 기록합니다. 이 쓰기 동작 즉시 하드웨어의 인터럽트 라인이 `Low`로 떨어지므로 무한 루프를 방지할 수 있습니다.

```c
#include "uart.h"

// 0xBC1 주소를 갖는 커스텀 CSR에 값을 쓰는 매크로
#define WRITE_CUSTOM_CSR_CLEAR(val) \
    __asm__ volatile ("csrw 0xBC1, %0" : : "r"(val))

void __attribute__((interrupt)) trap_handler() {
    unsigned long mcause_val;
    __asm__ volatile ("csrr %0, mcause" : "=r"(mcause_val));

    // External Interrupt (Cause 11) 확인
    if ((mcause_val & 0x80000000) && ((mcause_val & 0x7FFFFFFF) == 11)) {
        uart_print("[Trap] Interrupt caught! Clearing via custom CSR.\r\n");

        // [핵심] 커스텀 CSR(0xBC1)에 비트 1을 써서 하드웨어 인터럽트 조건 해제
        WRITE_CUSTOM_CSR_CLEAR(0x01);
    }
}

```

```ld
SECTIONS
{
    .text : {
        *(.text.init)   /* 스타트업 코드가 가장 먼저 오도록 배치 */
        *(.text)

        *(.rodata)
        *(.rodata.*)
    } > RAM

    .data : {
        *(.data)
        *(.data.*)
    } > RAM

    .bss : {
        . = ALIGN(4);
        _bss_start = .;
        *(.bss)
        *(.bss.*)
        *(.sbss)
        *(.sbss.*)
        _bss_end = .;
    } > RAM
}
```

### 3. 펌웨어 Makefile (`firmware/Makefile`)

RISC-V GCC 툴체인을 사용하여 어셈블리 및 C 파일을 컴파일하고, 시뮬레이션이나 FPGA에 주입할 수 있는 `.hex` 및 `.bin` 파일로 변환하는 메이크파일입니다.

```makefile
# RISC-V 툴체인 접두사 설정 (시스템 환경에 맞게 수정)
CROSS_COMPILE = riscv64-unknown-elf-
CC = $(CROSS_COMPILE)gcc
OBJCOPY = $(CROSS_COMPILE)objcopy
OBJDUMP = $(CROSS_COMPILE)objdump

# 컴파일 플래그 (RV32I, 32비트 ABI, 최적화 및 표준 라이브러리 제외)
CFLAGS = -march=rv32i -mabi=ilp32 -O3 -Wall -nostdlib -ffreestanding
LDFLAGS = -T linker.ld -nostdlib -lgcc

# 소스 파일 목록
SRCS = crt0.s main.c uart.c
OBJS = $(SRCS:.s=.o)
OBJS := $(OBJS:.c=.o)

all: firmware.hex firmware.bin firmware.lst

%.o: %.s
	$(CC) $(CFLAGS) -c $< -o $@

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

firmware.elf: $(OBJS)
	$(CC) $(CFLAGS) $(LDFLAGS) $^ -o $@

firmware.bin: firmware.elf
	$(OBJCOPY) -O binary $< $@

firmware.hex: firmware.elf
```

### Makefile에 자동 복사 타겟 추가하기

`firmware/Makefile` 파일을 수정하여 빌드가 완료된 직후 `firmware.hex` 파일을 SpinalHDL 프로젝트 루트(또는 시뮬레이션 리소스 디렉토리)로 자동 복사하도록 설정합니다.

```makefile

CC = $(CROSS_COMPILE)gcc
OBJCOPY = $(CROSS_COMPILE)objcopy
OBJDUMP = $(CROSS_COMPILE)objdump

LDFLAGS = -T linker.ld -nostdlib -lgcc

SRCS = crt0.s main.c uart.c
OBJS = $(SRCS:.s=.o)
OBJS := $(OBJS:.c=.o)

# [중요] SpinalHDL 시뮬레이션 또는 프로젝트 루트 디렉토리 경로 지정
# firmware 폴더 기준 상위 디렉토리(프로젝트 루트)로 설정 예시
TARGET_DIR = ..

all: firmware.hex firmware.bin firmware.lst copy

%.o: %.s
	$(CC) $(CFLAGS) -c $< -o $@

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

firmware.elf: $(OBJS)
	$(CC) $(CFLAGS) $(LDFLAGS) $^ -o $@

firmware.bin: firmware.elf
	$(OBJCOPY) -O binary $< $@

firmware.hex: firmware.elf
	$(OBJCOPY) -O ihex $< $@

firmware.lst: firmware.elf
	$(OBJDUMP) -d $< > $@

# [자동화 타겟] 컴파일된 hex 파일을 스칼라 프로젝트 루트로 복사
copy: firmware.hex
	cp firmware.hex $(TARGET_DIR)/firmware.hex
	@echo "=================================================="
	@echo " [Success] firmware.hex copied to $(TARGET_DIR)/"
	@echo "=================================================="

clean:
	rm -f *.o *.elf *.bin *.hex *.lst
	rm -f $(TARGET_DIR)/firmware.hex
```

Want me to show how to write an SBT task or workflow so that sbt run automatically triggers make inside the firmware directory?

---

SpinalHDL 프로젝트에서 시뮬레이션을 실행할 때마다 펌웨어를 수동으로 빌드할 필요 없이, **시뮬레이션 스크립트(Scala `main` 메서드)가 시작될 때 자동으로 `make` 명령어가 실행되도록 연동**하는 것이 가장 직관적이고 안정적입니다.

Scala의 내장 프로세스 라이브러리(`scala.sys.process._`)를 활용하면 SBT 실행 흐름 안에서 펌웨어 빌드를 완벽하게 자동화할 수 있습니다.

### 방법: 시뮬레이션 `main` 메서드에 펌웨어 빌드 자동화 추가하기

시뮬레이션을 구동하는 Scala 객체(`object MuraxSim`)의 `main` 함수 최상단에 `make` 실행 로직을 배치합니다. 이렇게 하면 `sbt "runMain MuraxSim"` 명령어를 입력하는 순간 펌웨어가 자동으로 컴파일되고 복사된 뒤 시뮬레이션이 곧바로 시작됩니다.

```scala
import spinal.core._
import spinal.core.sim._
import scala.sys.process._
import java.io.File

object MuraxSim {
  def main(args: Array[String]): Unit = {
    
    // 1. [자동화] firmware 디렉토리에서 make 실행
    println("==================================================")
    println(" [Auto-Build] Compiling C firmware via Makefile...")
    println("==================================================")
    
    // new File("firmware") 경로에서 "make" 명령어 실행 (! 연산자는 프로세스 실행 후 종료 코드를 반환)
    val exitCode = Process("make", new File("firmware")).!
    
    if (exitCode != 0) {
      throw new RuntimeException(f"Firmware compilation failed with exit code $exitCode!")
    }
    
    println("[Auto-Build] Firmware compiled and synced successfully.\n")

    // 2. SpinalSim 시뮬레이션 설정 및 실행
    SimConfig.withWave.compile {
      val dut = new Murax(MuraxConfig.default)
      dut
    }.doSim { dut =>
      dut.clockDomain.forkStimulus(period = 20)
      
      println("--- Starting SoC Simulation ---")
      
      // 시뮬레이션 러닝 루프
      for (i <- 0 until 1000) {
        dut.clockDomain.waitSampling()
      }
      
      println("--- Simulation Completed Successfully ---")
    }
  }
}

```

---

### 이 방식의 장점

1. **정밀한 타이밍 제어:** `sbt run` 전체가 아니라 **특정 시뮬레이션(`runMain MuraxSim`)이 실행될 때만** 펌웨어를 빌드하므로 불필요한 빌드 지연을 막을 수 있습니다.
2. **에러 핸들링:** C 코드에 문법 오류가 있어 `make`가 실패하면(`exitCode != 0`), 스칼라 프로그램이 즉시 예외(`RuntimeException`)를 던지며 멈추기 때문에 잘못된 펌웨어로 시뮬레이션이 돌거나 오작동하는 것을 원천 방지합니다.

Want me to show how to configure OpenOCD and GDB to debug this bare-metal VexRiscv SoC on an FPGA?

---

FPGA에 올려진 VexRiscv SoC를 실물 하드웨어 상태에서 디버깅하려면, VexRiscv 코어 내부의 **`DebugPlugin`**(JTAG 타겟 모듈)과 PC의 디버거를 연결해 주는 OpenOCD(Open On-Chip Debugger)와 **RISC-V GDB**를 연동해야 합니다.

실제 FPGA 보드(예: ECP5, Artix-7 등)와 JTAG 프로그래머(FTDI 칩셋 등)를 사용할 때의 설정 및 연동 방법입니다.

---

### 1단계: OpenOCD 설정 파일 작성 (`vexriscv.cfg`)

OpenOCD가 FPGA의 JTAG 핀 구조와 VexRiscv 코어의 ID를 인식할 수 있도록 설정 파일을 작성합니다. (사용 중인 JTAG 채널러 및 FPGA 보드 환경에 맞춰 어댑터 설정을 변경해야 합니다.)

```tcl
# 1. JTAG 어댑터 설정 (예: FTDI 기반 Digilent JTAG-HS2 또는 범용 FT2232H 사용 시)
adapter driver ftdi
ftdi_vid_pid 0x0403 0x6010

# JTAG 트랜스포트 및 클럭 속도 설정
transport select jtag
adapter speed 1000

# 2. 칩 및 TAP(Test Access Port) 정의
set _CHIPNAME riscv
jtag newtap $_CHIPNAME cpu -irlen 5 -expected-id 0x10001fff

# 3. RISC-V 타겟 등록
set _TARGETNAME $_CHIPNAME.cpu
target create $_TARGETNAME riscv -chain-position $_TARGETNAME

# 4. 워크아레아(Work Area) 설정 (메모리 로딩 및 플래시/브레이크포인트 지원용)
$_TARGETNAME configure -work-area-phys 0x00000000 -work-area-size 1024 -work-area-backup 1

```

### 2단계: OpenOCD 실행하기

작성한 설정 파일을 이용해 OpenOCD 데몬을 실행합니다. 이 프로그램은 PC와 FPGA JTAG 포트 간의 통신을 중계하며 GDB의 접속을 대기(`localhost:3333`)하게 됩니다.

```bash
openocd -f vexriscv.cfg

```

* **정상 연결 시 출력 메시지 예시:** OpenOCD가 정상적으로 켜지면서 `Info : Listening on port 3333 for gdb connections` 메시지가 표시됩니다.

### 3단계: RISC-V GDB로 디버깅 시작하기

새로운 터미널 창을 열고, 컴파일된 ELF 파일(`.elf`)과 함께 RISC-V GCC 툴체인에 포함된 GDB를 실행합니다.

```bash

```

GDB 프롬프트(`(gdb)`)가 뜨면 다음 순서대로 명령어를 입력하여 FPGA 보드와 연결합니다:

```gdb
# 1. OpenOCD가 열어둔 포트에 원격 연결
(gdb) target remote localhost:3333

# 2. CPU 코어 정지 (Halt)
(gdb) monitor halt

# 3. (선택) 펌웨어 이미지를 온칩 메모리에 플래싱/로드
(gdb) load

# 4. main 함수에 브레이크포인트 설정
(gdb) break main

# 5. 실행 재개
(gdb) continue

```

### 4단계: 핵심 GDB 디버깅 명령어 활용

Want me to show how to automate OpenOCD startup directly inside launch.json as a pre-launch task?

---

VS Code에서 GDB 디버깅 세션을 시작(`F5`)할 때 **OpenOCD**가 백그라운드에서 자동으로 실행되도록 하려면, 작업 설정 파일인 `tasks.json`에 백그라운드 서버 구동 태스크를 정의하고 `launch.json`에서 이를 `preLaunchTask`로 연결하면 됩니다.

### 단계별 설정 방법

1. **tasks.json 파일 생성 및 OpenOCD 태스크 정의:** .vscode/tasks.json.
프로젝트 루트의 `.vscode/` 폴더 안에 `tasks.json` 파일을 만들고 아래 코드를 작성합니다. OpenOCD가 포트 `3333`에서 대기하기 시작하는 것을 감지하기 위해 백그라운드 문제 매처(Problem Matcher)를 설정합니다.

```json
            "type": "shell",

            "problemMatcher": {
                "owner": "custom",
                "pattern": [
                    {
                        "regexp": "^.*Listening on port 3333 for gdb connections.*$",
                        "file": 1,
                        "location": 2,
                        "message": 3
                    }
                ],
                "background": {
                    "activeOnStart": true,
                    "beginsPattern": "^.*Starting OpenOCD.*$",
                    "endsPattern": "^.*Listening on port 3333 for gdb connections.*$"
                }
            },
            "presentation": {
                "reveal": "silent",
                "panel": "shared"
            }
        }
    ]
}

```

*Verification:* VS Code 터미널(Ctrl+Shift+B 또는 태스크 실행 메뉴)에서 `start-openocd`를 실행했을 때 에러 없이 백그라운드에서 대기 상태가 되는지 확인합니다.

### 1단계: `tasks.json`에 OpenOCD 종료 태스크 추가하기

기존에 작성한 `.vscode/tasks.json` 파일에 `stop-openocd` 태스크를 추가합니다. 운영체제에 맞는 프로세스 종료 명령어를 사용합니다.

* **Linux / macOS 환경 (`pkill` 사용):**

```json
{
    "version": "2.0.2",
    "tasks": [
        {
            "label": "start-openocd",
            "type": "shell",
            "command": "openocd -f vexriscv.cfg",
            "isBackground": true,
            "problemMatcher": {
                "owner": "custom",
                "pattern": [
                    {
                        "regexp": "^.*Listening on port 3333 for gdb connections.*$",
                        "file": 1,
                        "location": 2,
                        "message": 3
                    }
                ],
                "background": {
                    "activeOnStart": true,
                    "beginsPattern": "^.*Starting OpenOCD.*$",
                    "endsPattern": "^.*Listening on port 3333 for gdb connections.*$"
                }
            },
            "presentation": {
                "reveal": "silent",
                "panel": "shared"
            }
        },
        {
            "label": "stop-openocd",
            "type": "shell",
            "command": "pkill -f 'openocd -f vexriscv.cfg'",
            "presentation": {
                "reveal": "silent",
                "panel": "shared"
            },
            "problemMatcher": []
        }
    ]
}

```

### 2단계: `launch.json`에 `postDebugTask` 연결하기

`.vscode/launch.json` 파일의 디버그 설정 블록에 **`postDebugTask`** 속성을 추가하여, 디버깅 세션이 종료될 때 방금 만든 `stop-openocd` 태스크가 자동으로 실행되도록 지정합니다.

```json
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "VexRiscv FPGA Debug (GDB)",
            "type": "cppdbg",
            "request": "launch",
            "program": "${workspaceFolder}/firmware/firmware.elf",
            "miDebuggerPath": "riscv64-unknown-elf-gdb",
            "miDebuggerServerAddress": "localhost:3333",
            "stopAtEntry": true,
            "cwd": "${workspaceFolder}/firmware",
            "preLaunchTask": "start-openocd",
            "postDebugTask": "stop-openocd",
            "setupCommands": [
                {
                    "description": "Enable pretty-printing for gdb",
                    "text": "-enable-pretty-printing",
                    "ignoreForDebugging": true
                },
                {
                    "description": "Halt the CPU core",
                    "text": "monitor halt"
                },
                {
                    "description": "Load ELF image to target RAM",
                    "text": "load"
                }
            ]
        }
    ]
}

```

---

### 동작 확인

1. VS Code에서 `F5`를 눌러 디버깅을 시작하면 백그라운드에서 OpenOCD가 자동으로 켜지고 GDB가 연결됩니다.
2. 디버깅을 중지(`Shift + F5` 또는 빨간색 네모 중지 버튼)하면, `postDebugTask`가 트리거되어 OpenOCD 프로세스가 깔끔하게 종료됩니다.
