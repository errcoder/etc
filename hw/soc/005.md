좋습니다. 이번에는 앞선 오류를 기준으로 **업스트림 소스와 공식 integration 예제를 다시 대조한 뒤** 정리했습니다.

핵심은 두 가지입니다.

1. `IBusSimplePlugin.iBus`는 `setup()`에서 생성되므로 `new VexRiscv(...)` 직후에 접근하면 `null`입니다. 현재 업스트림 소스가 실제로 그렇게 구현되어 있습니다. [GitHub](https://github.com/SpinalHDL/VexRiscv/blob/master/src/main/scala/vexriscv/plugin/IBusSimplePlugin.scala?utm_source=chatgpt.com)
2. 따라서 `rework { ... }` 안에서 접근해야 합니다. 업스트림 `Linux.scala`도 이 방식으로 `plugin.iBus`와 `plugin.dBus`를 다룹니다. [GitHub](https://github.com/SpinalHDL/VexRiscv/blob/master/src/main/scala/vexriscv/demo/Linux.scala?utm_source=chatgpt.com)

그리고 더 중요한 점을 하나 발견했습니다.

**우리가 지금 만들려는 것은 CPU 내부 bus를 다시 외부 `master(...)`로 만드는 것이 아닙니다.**  
따라서 `plugin.iBus` 자체를 direction-less로 만든 뒤 ROM에 직접 연결하는 것이 가장 단순합니다.

## 최종 점검한 `VexRiscvTop.scala`

이 버전으로 교체하세요.

```scala
package myvexsoc

import spinal.core._
import vexriscv._
import vexriscv.plugin._

class VexRiscvTop extends Component {

  val io = new Bundle {
    // ------------------------------------------------------------------------
    // Debug signals
    // ------------------------------------------------------------------------

    val debugIbusValid = out Bool()
    val debugIbusReady = out Bool()
    val debugIbusPc    = out UInt(32 bits)

    val debugRspValid = out Bool()
    val debugRspInst  = out Bits(32 bits)

    val debugDmemValid = out Bool()
    val debugDmemWr    = out Bool()
    val debugDmemAddr  = out UInt(32 bits)
    val debugDmemData  = out Bits(32 bits)
  }

  // --------------------------------------------------------------------------
  // CPU configuration
  // --------------------------------------------------------------------------

  val cpuConfig = CpuConfig.smallest()

  val cpu = new VexRiscv(cpuConfig)

  // --------------------------------------------------------------------------
  // VexRiscv plugin buses
  //
  // iBus / dBus are created during plugin setup().
  // Therefore they must be accessed from rework(), after the CPU pipeline
  // has been elaborated.
  // --------------------------------------------------------------------------

  cpu.rework {

    var iBus: IBusSimpleBus = null
    var dBus: DBusSimpleBus = null

    cpuConfig.plugins.foreach {

      case plugin: IBusSimplePlugin =>
        plugin.iBus.setAsDirectionLess()
        iBus = plugin.iBus

      case plugin: DBusSimplePlugin =>
        plugin.dBus.setAsDirectionLess()
        dBus = plugin.dBus

      case _ =>
    }

    // These plugins are required by CpuConfig.smallest().
    assert(iBus != null)
    assert(dBus != null)

    // ------------------------------------------------------------------------
    // Instruction ROM
    // ------------------------------------------------------------------------

    val rom = new InstructionRom(
      baseAddress = 0x80000000L,
      wordCount   = 16
    )

    // CPU -> ROM

    rom.io.cmdValid := iBus.cmd.valid
    rom.io.cmdPc    := iBus.cmd.pc

    // ROM -> CPU

    iBus.cmd.ready := rom.io.cmdReady

    iBus.rsp.valid := rom.io.rspValid
    iBus.rsp.error := rom.io.rspError
    iBus.rsp.inst  := rom.io.rspInst

    // ------------------------------------------------------------------------
    // Data bus
    //
    // There is no RAM yet.
    // The CPU will receive zero data if it performs a load.
    // ------------------------------------------------------------------------

    dBus.cmd.ready := True

    dBus.rsp.error := False
    dBus.rsp.data  := B(0, 32 bits)

    // ------------------------------------------------------------------------
    // Debug outputs
    // ------------------------------------------------------------------------

    io.debugIbusValid := iBus.cmd.valid
    io.debugIbusReady := iBus.cmd.ready
    io.debugIbusPc    := iBus.cmd.pc

    io.debugRspValid := iBus.rsp.valid
    io.debugRspInst  := iBus.rsp.inst

    io.debugDmemValid := dBus.cmd.valid
    io.debugDmemWr    := dBus.cmd.wr
    io.debugDmemAddr  := dBus.cmd.address
    io.debugDmemData  := dBus.cmd.data
  }
}
```

### 왜 이번에는 이 방식인가?

현재 업스트림 `IBusSimplePlugin`은 다음과 같이 선언되어 있습니다.

```scala
var iBus : IBusSimpleBus = null
```

그리고 `setup()`에서:

```scala
iBus = master(IBusSimpleBus(this)).setName("iBus")
```

를 수행합니다. 즉 **CPU constructor가 끝나는 시점에는 `iBus`가 아직 null일 수 있습니다.** [GitHub](https://github.com/SpinalHDL/VexRiscv/blob/master/src/main/scala/vexriscv/plugin/IBusSimplePlugin.scala?utm_source=chatgpt.com)

반면 공식 VexRiscv integration 코드에서는 `rework` 안에서 plugin bus를 가져와 direction을 해제하는 패턴을 사용합니다. [GitHub](https://github.com/SpinalHDL/VexRiscv/blob/master/src/main/scala/vexriscv/demo/Linux.scala?utm_source=chatgpt.com)

따라서 이전의:

```scala
val iBus = iBusPlugin.iBus
iBus.setAsDirectionLess()
```

를 `new VexRiscv()` 바로 다음에 두었던 것이 잘못이었습니다.

## `InstructionRom.scala`도 한 가지 확인

현재 ROM의 핵심 동작은:

```text
CPU cmd
   │
   │ PC
   ▼
ROM
   │
   │ 1 cycle
   ▼
CPU rsp
```

입니다.

현재 `IBusSimplePlugin`의 기본 `busLatencyMin`도 `1`이고, 실제 plugin 내부에서 `iBus.rsp`를 response buffer로 처리합니다. 따라서 이번 ROM에서 1-cycle response를 사용하는 것은 의도적으로 맞춘 것입니다. [GitHub](https://github.com/SpinalHDL/VexRiscv/blob/master/src/main/scala/vexriscv/plugin/IBusSimplePlugin.scala?utm_source=chatgpt.com)

### 성공 시 우리가 확인할 핵심

우리가 기대하는 것은 대략:

```text
IBUS PC=0x80000000
RSP INST=0x00100093

IBUS PC=0x80000004
RSP INST=0x00200113

IBUS PC=0x80000008
RSP INST=0x002081B3

IBUS PC=0x8000000C
RSP INST=0x0000006F
```

이후에는 `JAL x0,0` 때문에:

```text
IBUS PC=0x8000000C
IBUS PC=0x8000000C
IBUS PC=0x8000000C
...
```

형태를 기대합니다.

**다만 이 출력이 반드시 정확히 저 cycle 순서로 나온다고 미리 단정하지는 않겠습니다.** VexRiscv의 fetch pipeline에는 내부 stage와 response buffering이 있으므로, 지금 단계에서는 먼저 실제 waveform/log를 확인하고 그 timing을 해석하는 것이 맞습니다. 현재 업스트림 `IBusSimplePlugin`의 실제 fetch/response 구조가 그렇게 되어 있습니다. [GitHub](https://github.com/SpinalHDL/VexRiscv/blob/master/src/main/scala/vexriscv/plugin/IBusSimplePlugin.scala?utm_source=chatgpt.com)

이번에는 제가 코드를 먼저 던지고 오류를 찾는 식으로 진행하지 않고,
 **현재 업스트림 API → plugin lifecycle → bus 방향 → simulation 접근 → response latency까지 확인한 상태에서** 제시했습니다.
