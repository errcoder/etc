좋습니다. GPIO 통합 테스트까지 PASS했으므로, 다음은 Load Access Fault와 Store Access Fault의 처리 차이를 확인하겠습니다.

여기서 먼저 중요한 설계 원칙을 구분해야 합니다.

- Load는 요청을 수락한 뒤 응답을 돌려받습니다. 따라서 `DBusSimpleRsp.error`로 실패를 알릴 수 있습니다.
- Store는 `DBusSimpleCmd` 요청이 수락되는 시점에 쓰기 작업이 완료되는 구조입니다. `DBusSimpleRsp`는 Store 완료 응답으로 사용되지 않습니다.

따라서 Unmapped Store에 대해 `cmd.ready := False`로 계속 막는 것은 에러 응답이 아닙니다. CPU가 해당 명령에서 영원히 대기하는 hang을 만들 수 있습니다.

좋습니다. 이번 단계에서는 먼저 VexRiscv의 실제 구현을 기준으로 두 예외가 어떻게 다른지 확인하고, 그다음 우리 SoC에 적합한 Store Access Fault 처리 방식을 결정하겠습니다.

핵심은 현재 `DBusSimplePlugin`은 Load Access Fault는 지원하지만, 일반적인 DBus 응답을 통한 Store Access Fault는 지원하지 않는다는 점입니다.

## 1. RISC-V 예외 코드부터 구분

RISC-V에서 두 예외는 서로 다른 Exception Code를 사용합니다.

| Exception Code | 예외                           | 발생 상황          |
| -------------- | ---------------------------- | -------------- |
| 4              | Load Address Misaligned      | Load 주소 정렬 오류  |
| 5              | Load Access Fault            | Load 접근 실패     |
| 6              | Store/AMO Address Misaligned | Store 주소 정렬 오류 |
| 7              | Store/AMO Access Fault       | Store 접근 실패    |

여기서 Code 5와 Code 7은 서로 다른 예외입니다.

## 2. 현재 DBusSimplePlugin의 실제 처리 방식

사용 중인 VexRiscv 소스의 `DBusSimplePlugin.scala`에서 핵심 부분은 다음과 같습니다.

```scala
if(catchAccessFault) {
  when(dBus.rsp.ready && dBus.rsp.error && !input(MEMORY_STORE)) {
    memoryExceptionPort.valid := True
    memoryExceptionPort.code := 5
  }
}
```

이 코드는 다음 조건에서만 예외를 발생시킵니다.

- 응답이 유효함: `dBus.rsp.ready`
- 응답에 에러가 있음: `dBus.rsp.error`
- 현재 명령이 Load임: `!MEMORY_STORE`

따라서 `DBusSimpleRsp.error = true`를 전달해도 Store Access Fault는 발생하지 않습니다.

반면 주소 정렬 오류는 별도로 처리합니다.

```scala
if(catchAddressMisaligned) {
  when(input(ALIGNEMENT_FAULT)) {
    memoryExceptionPort.code :=
      (input(MEMORY_STORE) ? U(6) | U(4)).resized

    memoryExceptionPort.valid := True
  }
}
```

여기서는 Store인지 Load인지에 따라 Code 6 또는 Code 4를 선택합니다.

즉, 현재 플러그인은 Store Address Misaligned는 처리하지만 Store Access Fault는 DBus 응답만으로 처리하지 않습니다.

## 3. 왜 DBusDecoder에서 바로 해결할 수 없는가?

현재 DBus 인터페이스를 보면 다음과 같습니다.

DBusSimpleBus

Command

`cmd.valid`, `cmd.ready`, `cmd.wr`, `cmd.address`, `cmd.data`, `cmd.mask`

Response

`rsp.ready`, `rsp.error`, `rsp.data`

DBusSimpleRsp.ready는 응답 valid이며, Store 완료 응답을 CPU가 기다리는 구조가 아닙니다.

현재 `DBusSimplePlugin`은 다음처럼 동작합니다.

- Load: 명령을 보내고 응답이 도착할 때까지 대기합니다.
- Store: 명령이 수락되면 Store 요청 처리를 진행합니다. 일반적인 Store 완료 응답을 기다리지 않습니다.

따라서 Unmapped Store에 대해 다음과 같이 처리하면 문제가 생깁니다.

```scala
io.cpu.cmd.ready := False
```

CPU는 Store 명령이 수락되기를 계속 기다립니다. 예외가 발생하지 않으므로 결국 CPU가 멈춥니다.

반대로 다음과 같이 처리해도 올바른 Access Fault는 아닙니다.

```scala
io.cpu.cmd.ready := True
```

이 경우 Store 요청이 수락된 것으로 처리되므로, 에러 없이 명령이 완료될 수 있습니다.

## 4. Store Access Fault 구현 방식

제가 권장하는 방식은 DBusSimplePlugin에 Store Access Fault를 전달할 수 있는 별도의 예외 경로를 추가하는 것입니다.

두 가지 접근 방법을 비교하겠습니다.

| 방식               | 구현                    | 평가                |
| ---------------- | --------------------- | ----------------- |
| DBusSimpleBus 확장 | Store 응답 프로토콜 추가      | CPU 플러그인 수정 범위가 큼 |
| 별도 Exception 입력  | Store 명령 수락 시점에 예외 발생 | 현재 구조에 더 적합       |

두 번째 방식을 사용하면 다음과 같은 흐름을 만들 수 있습니다.
```
CPU Store 명령
`address = 0x20000000`
  |
  v
DBusDecoder
Unmapped Store 감지
  |
  v
Store 명령 수락 + 별도 예외 신호
`Store Access Fault`
Exception Code = 7
  |
  v
ExceptionService → CsrPlugin
`mcause = 7`
`mepc` 저장 후 `mtvec`으로 이동
```
이 방식은 Store 요청을 무한 대기시키지 않으면서, CPU에 올바른 예외를 전달하는 설계입니다.

단, 여기서 주의할 점이 있습니다. `DBusDecoder`만 수정해서는 예외가 자동으로 발생하지 않습니다. 현재 `DBusSimplePlugin`의 `memoryExceptionPort`는 내부 구현이므로, CPU의 예외 처리 파이프라인에 Store Access Fault를 주입할 수 있도록 플러그인 쪽에도 변경이 필요합니다.

## 5. 다음 구현 단계

코드를 바로 수정하기 전에 다음 소스 구조를 먼저 확인하는 것이 안전합니다.

1. `ExceptionService.scala` — 예외 포트 생성과 전달 규칙
2. `CsrPlugin.scala` — Exception Code 7 처리 및 PC Redirect
3. `DBusSimplePlugin.scala` — Store 명령의 실행 단계와 예외 주입 가능 시점

이 세 부분을 확인한 뒤, 기존 Load Access Fault 경로를 유지하면서 Store Access Fault를 추가하겠습니다.

다음 구현 목표는 명확합니다.

- Unmapped Load → `mcause = 5`
- Unmapped Store → `mcause = 7`
- 두 경우 모두 `mepc`가 해당 Load/Store 명령의 PC를 가리킴
- 두 경우 모두 `mtvec`의 Trap Handler로 진입
- RAM과 GPIO의 정상 접근에는 영향이 없음

이번에는 특히 Store 명령의 파이프라인 단계와 ExceptionService의 포트 타이밍을 먼저 검증하고, 그 결과에 근거해서 코드를 작성하겠습니다.
