좋습니다. GPIO 통합 테스트까지 PASS했으므로, 다음은 Load Access Fault와 Store Access Fault의 처리 차이를 확인하겠습니다.

여기서 먼저 중요한 설계 원칙을 구분해야 합니다.

- Load는 요청을 수락한 뒤 응답을 돌려받습니다. 따라서 `DBusSimpleRsp.error`로 실패를 알릴 수 있습니다.
- Store는 `DBusSimpleCmd` 요청이 수락되는 시점에 쓰기 작업이 완료되는 구조입니다. `DBusSimpleRsp`는 Store 완료 응답으로 사용되지 않습니다.

따라서 Unmapped Store에 대해 `cmd.ready := False`로 계속 막는 것은 에러 응답이 아닙니다. CPU가 해당 명령에서 영원히 대기하는 hang을 만들 수 있습니다.

좋습니다. 이번 단계에서는 먼저 VexRiscv의 실제 구현을 기준으로 두 예외가 어떻게 다른지 확인하고, 그다음 우리 SoC에 적합한 Store Access Fault 처리 방식을 결정하겠습니다.

핵심은 현재 `DBusSimplePlugin`은 Load Access Fault는 지원하지만, 일반적인 DBus 응답을 통한 Store Access Fault는 지원하지 않는다는 점입니다.

## 1. RISC-V 예외 코드부터 구분

RISC-V에서 두 예외는 서로 다른 Exception Code를 사용합니다.

| Exception Code | 예외                           | 발생 상황          |
| -------------- | ---------------------------- | -------------- |
| 4              | Load Address Misaligned      | Load 주소 정렬 오류  |
| 5              | Load Access Fault            | Load 접근 실패     |
| 6              | Store/AMO Address Misaligned | Store 주소 정렬 오류 |
| 7              | Store/AMO Access Fault       | Store 접근 실패    |

여기서 Code 5와 Code 7은 서로 다른 예외입니다.

## 2. 현재 DBusSimplePlugin의 실제 처리 방식

사용 중인 VexRiscv 소스의 `DBusSimplePlugin.scala`에서 핵심 부분은 다음과 같습니다.

```scala
if(catchAccessFault) {
  when(dBus.rsp.ready && dBus.rsp.error && !input(MEMORY_STORE)) {
    memoryExceptionPort.valid := True
    memoryExceptionPort.code := 5
  }
}
```

이 코드는 다음 조건에서만 예외를 발생시킵니다.

- 응답이 유효함: `dBus.rsp.ready`
- 응답에 에러가 있음: `dBus.rsp.error`
- 현재 명령이 Load임: `!MEMORY_STORE`

따라서 `DBusSimpleRsp.error = true`를 전달해도 Store Access Fault는 발생하지 않습니다.

반면 주소 정렬 오류는 별도로 처리합니다.

```scala
if(catchAddressMisaligned) {
  when(input(ALIGNEMENT_FAULT)) {
    memoryExceptionPort.code :=
      (input(MEMORY_STORE) ? U(6) | U(4)).resized

    memoryExceptionPort.valid := True
  }
}
```

여기서는 Store인지 Load인지에 따라 Code 6 또는 Code 4를 선택합니다.

즉, 현재 플러그인은 Store Address Misaligned는 처리하지만 Store Access Fault는 DBus 응답만으로 처리하지 않습니다.

## 3. 왜 DBusDecoder에서 바로 해결할 수 없는가?

현재 DBus 인터페이스를 보면 다음과 같습니다.

DBusSimpleBus

Command

`cmd.valid`, `cmd.ready`, `cmd.wr`, `cmd.address`, `cmd.data`, `cmd.mask`

Response

`rsp.ready`, `rsp.error`, `rsp.data`

DBusSimpleRsp.ready는 응답 valid이며, Store 완료 응답을 CPU가 기다리는 구조가 아닙니다.

현재 `DBusSimplePlugin`은 다음처럼 동작합니다.

- Load: 명령을 보내고 응답이 도착할 때까지 대기합니다.
- Store: 명령이 수락되면 Store 요청 처리를 진행합니다. 일반적인 Store 완료 응답을 기다리지 않습니다.

따라서 Unmapped Store에 대해 다음과 같이 처리하면 문제가 생깁니다.

```scala
io.cpu.cmd.ready := False
```

CPU는 Store 명령이 수락되기를 계속 기다립니다. 예외가 발생하지 않으므로 결국 CPU가 멈춥니다.

반대로 다음과 같이 처리해도 올바른 Access Fault는 아닙니다.

```scala
io.cpu.cmd.ready := True
```

이 경우 Store 요청이 수락된 것으로 처리되므로, 에러 없이 명령이 완료될 수 있습니다.

## 4. Store Access Fault 구현 방식

제가 권장하는 방식은 DBusSimplePlugin에 Store Access Fault를 전달할 수 있는 별도의 예외 경로를 추가하는 것입니다.

두 가지 접근 방법을 비교하겠습니다.

| 방식               | 구현                    | 평가                |
| ---------------- | --------------------- | ----------------- |
| DBusSimpleBus 확장 | Store 응답 프로토콜 추가      | CPU 플러그인 수정 범위가 큼 |
| 별도 Exception 입력  | Store 명령 수락 시점에 예외 발생 | 현재 구조에 더 적합       |

두 번째 방식을 사용하면 다음과 같은 흐름을 만들 수 있습니다.
```
CPU Store 명령
`address = 0x20000000`
  |
  v
DBusDecoder
Unmapped Store 감지
  |
  v
Store 명령 수락 + 별도 예외 신호
`Store Access Fault`
Exception Code = 7
  |
  v
ExceptionService → CsrPlugin
`mcause = 7`
`mepc` 저장 후 `mtvec`으로 이동
```
이 방식은 Store 요청을 무한 대기시키지 않으면서, CPU에 올바른 예외를 전달하는 설계입니다.

단, 여기서 주의할 점이 있습니다. `DBusDecoder`만 수정해서는 예외가 자동으로 발생하지 않습니다. 현재 `DBusSimplePlugin`의 `memoryExceptionPort`는 내부 구현이므로, CPU의 예외 처리 파이프라인에 Store Access Fault를 주입할 수 있도록 플러그인 쪽에도 변경이 필요합니다.

## 5. 다음 구현 단계

코드를 바로 수정하기 전에 다음 소스 구조를 먼저 확인하는 것이 안전합니다.

1. `ExceptionService.scala` — 예외 포트 생성과 전달 규칙
2. `CsrPlugin.scala` — Exception Code 7 처리 및 PC Redirect
3. `DBusSimplePlugin.scala` — Store 명령의 실행 단계와 예외 주입 가능 시점

이 세 부분을 확인한 뒤, 기존 Load Access Fault 경로를 유지하면서 Store Access Fault를 추가하겠습니다.

다음 구현 목표는 명확합니다.

- Unmapped Load → `mcause = 5`
- Unmapped Store → `mcause = 7`

## 1. 현재 소스에서 확인된 사실

정확한 커밋의 `DBusSimplePlugin.scala`에서 다음 구조를 확인했습니다.

- 기본 설정에서는 DBus 명령을 Execute stage에서 발생시킵니다.
- 예외 포트(`memoryExceptionPort`)는 기본 설정에서 Memory stage에 생성됩니다.
- Memory stage에서 Load 응답 오류(`rsp.ready && rsp.error`)를 감지하면 예외 코드 `5`를 발생시킵니다.
- 반면 Store Access Fault에 해당하는 코드 `7`을 발생시키는 처리는 없습니다.

여기서 특히 중요한 부분은 `DBusSimplePlugin`이 Store 명령을 보낼 때입니다.

## 2. 예외 포트는 재사용할 수 있는 구조

`CsrPlugin`은 `ExceptionService`를 구현하고 있으며, `newExceptionPort(stage, priority, codeWidth)`를 호출하면 해당 stage에

현재 단계에서 유력한 설계는 다음과 같습니다.

1. DBusDecoder가 unmapped Store를 감지합니다.
2. 그 Store 명령은 CPU가 멈추지 않도록 적절히 받아들입니다.
3. 같은 명령이 Memory stage에 도달했을 때 Store Access Fault 신호를 전달합니다.
4. DBusSimplePlugin이 기존 `memoryExceptionPort`를 통해 예외 코드 `7`과 잘못된 주소를 전달합니다.

단, 2번과 3번의 신호를 어떤 방식으로 같은 명령에 정확히 정렬할지는 아직 확정하면 안 됩니다. 단순히 `RegNext(unmappedStoreFire)`를 추가하는 방식은

## 1. `Services.scala` 확인 결과

보내주신 파일의 핵심은 다음 부분입니다. 사용하신 `master` 링크와 별도로, 프로젝트에서 고정한 커밋 SHA의 파일도 확인했으며 해당 정의는 동일합니다.

```
case class ExceptionCause(codeWidth : Int) extends Bundle {
  val code = UInt(codeWidth bits)
  val badAddr = UInt(32 bits)

  def resizeCode(width : Int): ExceptionCause = {
    val ret = ExceptionCause(width)
    ret.badAddr := badAddr
    ret.code := code.resized
    ret
  }
}

trait ExceptionService {
  def newExceptionPort(
    stage : Stage,
    priority : Int = 0,
    codeWidth : Int = 4
  ) : Flow[ExceptionCause]

  def isExceptionPending(stage : Stage) : Bool
}
```

여기서 알아둘 점은 다음과 같습니다.

- `code`: 예외 번호입니다. Store Access Fault는 `7`입니다.
- `badAddr`: 접근에 실패한 주소입니다.
- `Flow[ExceptionCause]`: 예외 발생을 알리는 valid 신호와 예외 정보를 전달합니다.
- `newExceptionPort()`: CSR 플러그인에 예외 포트를 등록합니다.

## 2. 여기서 설계 방향이 조금 더 명확해졌습니다

앞서 별도의 예외 전달 경로를 만드는 방안도 이야기했지만, 정확한 `DBusSimplePlugin.scala`를 다시 살펴보니 기존 예외 포트를 그대로 재사용하는 방법이 더 간결합니다.

현재 설정은 다음과 같습니다.

```
new DBusSimplePlugin(
  catchAddressMisaligned = false,
  catchAccessFault = true
)
```

이 설정 때문에 `DBusSimplePlugin`은 이미 `memoryExceptionPort`를 생성합니다. 그리고 기본 파이프라인에서는 이 포트가 Memory stage에 연결됩니다.

현재 Load Access Fault 처리 부분은 다음과 같습니다.

```
if(catchAccessFault) {
  when(dBus.rsp.ready && dBus.rsp.error && !input(MEMORY_STORE)) {
    memoryExceptionPort.valid := True
    memoryExceptionPort.code := 5
  }
}
```

즉, 오류 응답이 들어와도 `MEMORY_STORE`가 참이면 예외를 발생시키지 않도록 되어 있습니다.

여기서 다음과 같은 확장 가능성을 발견했습니다.

```
if(catchAccessFault) {
  when(dBus.rsp.ready && dBus.rsp.error) {
    memoryExceptionPort.valid := True
    memoryExceptionPort.code :=
      (input(MEMORY_STORE) ? U(7) | U(5)).resized
  }
}
```

이것은 아직 적용할 최종 코드가 아니라, 기존 예외 포트를 재사용할 수 있는지 검토하기 위한 핵심 아이디어입니다.

## 3. DBusDecoder와 DBusSimplePlugin의 역할

이 방향이라면 각 모듈의 역할은 명확해집니다.

| 모듈               | 변경할 역할                                    |
| ---------------- | ----------------------------------------- |
| DBusDecoder      | Unmapped Load와 Store를 모두 감지하고 오류 응답 생성    |
| DBusSimplePlugin | 오류 응답이 Load인지 Store인지 구분해 예외 코드 5 또는 7 발생 |
| CsrPlugin        | 기존 방식으로 Trap 처리                           |
| Instruction ROM  | Trap handler에서 원인과 주소 확인                  |

특히 CsrPlugin은 예외가 발생한 stage에서 해당 명령을 제거하고, 예외 상태를 파이프라인 끝까지 전달합니다. Trap 진입 시 `mepc`에는 해당 명령의 PC를, `mtval`에는 예외 포트의 `badAddr`를 기록합니다. 따라서 CsrPlugin 자체를 수정할 필요는 없어 보입니다.

## 4. 단, 구현 전에 반드시 검증할 부분

한 가지 중요한 위험이 남아 있습니다.

Store는 Load와 달리 응답을 기다리며 Memory stage에 머물지 않습니다. 따라서 DBusDecoder가 Store 오류 응답을 한 사이클 발생시키더라도, 그 응답이 Memory stage에 있는 바로 그 Store 명령과 정확히 일치하는지 확인해야 합니다.

특히 다음 상황을 확인해야 합니다.

1. Store 명령이 DBusDecoder에서 handshake되는 사이클
2. Store 명령이 Execute에서 Memory로 이동하는 사이클
3. 오류 응답이 발생하는 사이클
4. Memory stage의 `MEMORY_STORE`, `PC`, `REGFILE_WRITE_DATA`가 해당 Store 명령의 정보인지
5. 예외 발생 시 Store가 실제로 RAM이나 GPIO에 기록되지 않는지

이 정렬이 확인되기 전에는 `RegNext(unmappedStoreFire)`만 추가해서는 안 됩니다.

다음 단계는 코드 수정이 아니라 이 사이클 정렬을 확인하는 것입니다. 기존 DBusSimplePlugin의 Load 오류 처리 방식과 Store의 명령 진행 방식을 기준으로, 한 사이클 단위의 타이밍 표를 먼저 만들겠습니다. 그 결과가 맞으면 DBusDecoder와 DBusSimplePlugin의 최소 수정만으로 구현할 수 있는지 확정하겠습니다.

소스 분석을 진행한 결과, Store Access Fault는 DBusSimple의 응답 채널을 이용하지 않고, Execute stage에서 별도의 예외 포트로 전달하는 방식이 가장 안전합니다.

이렇게 하면 VexRiscv 원본 `DBusSimplePlugin.scala`를 수정하지 않아도 됩니다. 앞서 검토했던 `RegNext(unmappedStoreFire)` 방식보다 파이프라인 정렬 측면에서도 유리합니다.

## 1. 먼저 확인된 파이프라인 타이밍

현재 설정은 `emitCmdInMemoryStage=false`이므로 DBus 명령은 Execute stage에서 발생하고, 기존 Load 응답 및 예외 처리는 Memory stage에서 수행됩니다.

Unmapped Store를 다음과 같이 처리하는 것을 제안합니다.

| 시점       | Execute stage     | Memory stage | DBusDecoder                |
| -------- | ----------------- | ------------ | -------------------------- |
| 사이클 N    | Unmapped Store 실행 | 이전 명령 처리     | Store handshake 및 fault 감지 |
| 사이클 N    | Store 예외 포트 valid | 이전 명령 처리     | `storeFault = 1`           |
| 클록 상승 에지 | Store 제거 처리       | 예외 전달 준비     | Store는 RAM/GPIO에 전달되지 않음   |
| 이후       | 잘못된 경로의 명령 제거     | 예외 상태 전달     | CPU가 Trap 진입               |

핵심은 Store가 Memory stage로 이동하기 전에 Execute stage에서 예외를 발생시키는 것입니다.

이렇게 해야 Store 오류를 확인하기 위해 한 사이클을 기다리는 동안 다음 Store가 이미 발행되는 상황을 피할 수 있습니다.

## 2. 왜 DBus 응답 채널을 사용하지 않는가?

기존 DBusSimplePlugin은 Memory stage에서 다음 조건으로 Load Access Fault를 감지합니다.

```
when(dBus.rsp.ready && dBus.rsp.error && !input(MEMORY_STORE)) {
  memoryExceptionPort.valid := True
  memoryExceptionPort.code := 5
}
```

여기서 Store 오류를 `rsp.ready/error`로 전달하면 문제가 생길 수 있습니다. 응답은 Memory stage에서 해석되지만, 오류를 발생시킨 Store는 Execute stage에 있을 수 있기 때문입니다. 그 순간 Memory stage의 다른 명령을 잘못된 Load 오류로 판단할 위험도 있습니다.

따라서 다음처럼 역할을 분리하겠습니다.

- Load Access Fault: 기존 DBusSimplePlugin 응답 경로 그대로 사용
- Store Access Fault: DBusDecoder의 별도 `storeFault` 신호를 Execute stage의 새 예외 포트로 전달

CsrPlugin은 같은 stage에 여러 예외 포트를 등록할 수 있고, 우선순위에 따라 이를 통합합니다. 따라서 새 예외 포트를 추가해도 기존 Load 예외 포트를 대체하거나 수정할 필요가 없습니다.

## 3. 구현할 구조

```
DBusSimplePlugin
- Execute stage에서 Store 명령 발행
   |
   v
DBusDecoder
- RAM/GPIO 주소면 해당 장치로 전달
- Unmapped Store면 명령을 받아들임
- `storeFault`를 같은 사이클에 발생
  |
  v
StoreAccessFaultPlugin (신규)
- Execute stage의 `storeFault` 감지
- `ExceptionService`에 예외 코드 7 전달
- `badAddr`에 Store 유효 주소 전달
  |
  v
기존 CsrPlugin
- Trap 진입 및 CSR 갱신
```

신규 플러그인은 기존 DBusSimplePlugin의 `MEMORY_ENABLE`, `MEMORY_STORE`와 Execute stage의 주소 정보를 이용합니다. 예외 포트는 `pipeline.execute`에 등록하고, `badAddr`는 DBusSimplePlugin이 실제 명령 주소를 계산할 때 사용하는 `SRC_ADD`를 이용하는 방향입니다.

## 4. DBusDecoder에서 바뀔 동작

현재 unmapped Store는 `cmd.ready = False`라서 CPU가 멈춥니다. 이 부분을 바꿉니다.

```
io.cpu.cmd.ready := Mux(
  ramHit,
  io.ram.cmd.ready,
  Mux(
    gpioHit,
    io.gpio.cmd.ready,
    True
  )
)
```

그리고 다음 신호를 추가합니다.

```
io.storeFault := io.cpu.cmd.fire &&
                 io.cpu.cmd.wr &&
                 !ramHit &&
                 !gpioHit
```

`storeFault`는 명령이 실제로 handshake된 바로 그 사이클에 발생합니다. 따라서 별도의 `RegNext`를 사용하지 않습니다.

중요한 점은 기존 Load 오류 응답 경로는 그대로 유지한다는 것입니다. RAM과 GPIO의 정상 Store도 기존처럼 동작해야 합니다.

## 5. 최종 검증 목표

| 테스트                  | 기대 결과                |
| -------------------- | -------------------- |
| 정상 RAM Store         | 정상 기록                |
| 정상 GPIO Store        | 정상 기록                |
| 정상 GPIO Load         | 정상 데이터               |
| Unmapped Load        | `mcause = 5`         |
| Unmapped Store       | `mcause = 7`         |
| Unmapped Store       | `mtval = 접근 주소`      |
| Unmapped Store       | `mepc = Store 명령 PC` |
| Unmapped Store 이후 명령 | 실행되지 않음              |
| Trap 진입              | `mtvec = 0x80000120` |

특히 Unmapped Store 다음에 RAM Store를 하나 배치해서, 잘못된 Store뿐 아니라 그 뒤의 명령도 예외 처리로 제거되는지 확인하겠습니다.

## 6. 실제 파일을 연결하기 위한 다음 단계

현재 로컬 파일과 정확히 맞는 완성 코드를 만들기 위해 다음 세 파일을 보내주세요.

기존 GPIO 통합 테스트와 Load Access Fault 테스트는 그대로 보존하겠습니다.
