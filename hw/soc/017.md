VexRiscv 명령어 실행 검증 PASS

좋습니다! 이번에는 단순한 IBus 연결을 넘어 CPU가 실제로 명령어를 실행하고 그 결과를 DBus로 전달하는 것까지 확인했습니다.

## 1. 실행 결과

| 검증 항목        | 결과           |
| ------------ | ------------ |
| ADDI 실행      | PASS         |
| x1 값 기록 및 읽기 | PASS         |
| SW 실행        | PASS         |
| Store 주소     | `0x00000000` |
| Store 데이터    | `0x00000001` |
| Store 횟수     | 5회           |

특히 이 로그가 핵심입니다.

```
Cycle  5 : STORE address=0x00000000 data=0x00000001
Cycle 15 : STORE address=0x00000000 data=0x00000001
Cycle 25 : STORE address=0x00000000 data=0x00000001
```

`ADDI x1, x0, 1`의 결과가 Register File에 기록되고, 이후 `SW x1, 0(x0)`가 해당 값을 읽어 DBus에 전달했다는 것을 확인했습니다.

## 2. 현재까지 완성된 구조

Instruction ROM

명령어 공급 · 1-cycle 응답

VexRiscv CPU

Fetch → Decode → Execute → Write Back

DBus

Store 요청 · 주소 0 · 데이터 1

각 경계 및 명령 실행 검증 완료

## 3. 다음 단계: 실제 RAM 연결

이제 DBus에 임시로 연결한 응답/Ready 신호 대신 실제 Data RAM을 연결하겠습니다.

다음 목표는 다음과 같습니다.

1. `ADDI x1, x0, 1`
2. `SW x1, 0(x0)` → RAM[0] = 1
3. `ADDI x2, x0, 2`
4. `SW x2, 4(x0)` → RAM[1] = 2
5. 시뮬레이션에서 RAM 내용을 확인

이를 통해 Instruction ROM과 Data RAM이 분리된 Harvard 구조의 간단한 VexRiscv SoC를 완성하게 됩니다.

다음 단계에서는 RAM의 동기식 읽기 지연, DBus 응답 타이밍, Store/Load 핸드셰이크를 실제 VexRiscv 인터페이스에 맞춰 확인하겠습니다.
