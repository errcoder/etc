좋습니다! 이번에는 단순한 IBus 연결을 넘어 CPU가 실제로 명령어를 실행하고 그 결과를 DBus로 전달하는 것까지 확인했습니다.

## 1. 실행 결과

| 검증 항목        | 결과           |
| ------------ | ------------ |
| ADDI 실행      | PASS         |
| x1 값 기록 및 읽기 | PASS         |
| SW 실행        | PASS         |
| Store 주소     | `0x00000000` |
| Store 데이터    | `0x00000001` |
| Store 횟수     | 5회           |

특히 이 로그가 핵심입니다.

```
Cycle  5 : STORE address=0x00000000 data=0x00000001
Cycle 15 : STORE address=0x00000000 data=0x00000001
Cycle 25 : STORE address=0x00000000 data=0x00000001
```

`ADDI x1, x0, 1`의 결과가 Register File에 기록되고, 이후 `SW x1, 0(x0)`가 해당 값을 읽어 DBus에 전달했다는 것을 확인했습니다.

## 3. 다음 단계: 실제 RAM 연결

다음 목표는 다음과 같습니다.

1. `ADDI x1, x0, 1`
2. `SW x1, 0(x0)` → RAM[0] = 1
3. `ADDI x2, x0, 2`
4. `SW x2, 4(x0)` → RAM[1] = 2
5. 시뮬레이션에서 RAM 내용을 확인

목표 프로그램은 다음과 같습니다.

| 주소           | 명령어              | 동작          |
| ------------ | ---------------- | ----------- |
| `0x80000000` | `ADDI x1, x0, 1` | x1 = 1      |
| `0x80000004` | `SW x1, 0(x0)`   | RAM[0] = 1  |
| `0x80000008` | `ADDI x2, x0, 2` | x2 = 2      |
| `0x8000000C` | `SW x2, 4(x0)`   | RAM[1] = 2  |
| `0x80000010` | `LW x3, 0(x0)`   | x3 = RAM[0] |
| `0x80000014` | `JAL x0, 0`      | 정지 반복       |

단, RAM을 연결하기 전에 DBus의 요청·응답 타이밍을 정확히 맞춰야 합니다. 특히 `DBusSimpleBus`는 명령 Stream과 응답 인터페이스가 분리되어 있으므로, Store와 Load를 같은 방식으로 처리하면 안 됩니다.

## 1. DBus 응답 규칙 확인

프로젝트에서 사용하는 VexRiscv 커밋 `baf7dc82...`의 `DBusSimplePlugin.scala`를 확인했습니다.

중요한 부분은 다음 코드입니다.

```
// Load 요청은 응답이 없으면 CPU가 대기
arbitration.haltItself setWhen(
  arbitration.isValid &&
  input(MEMORY_ENABLE) &&
  !input(MEMORY_STORE) &&
  (!dBus.rsp.ready || ...)
)
```

여기서 주의할 점이 있습니다.

| 신호               | 의미                  |
| ---------------- | ------------------- |
| `dBus.cmd.valid` | 메모리 요청 유효           |
| `dBus.cmd.ready` | 메모리가 요청 수락          |
| `dBus.cmd.wr`    | 1이면 Store, 0이면 Load |
| `dBus.rsp.ready` | Load 응답 데이터 유효      |
| `dBus.rsp.data`  | Load 응답 데이터         |
| `dBus.rsp.error` | 응답 오류               |

특히 `dBus.rsp.ready`는 일반적인 Stream의 ready와 다릅니다. 이 인터페이스에서는 CPU가 Load 응답을 기다리는 데 사용하는 응답 유효 신호입니다. Store는 별도의 응답을 기다리지 않습니다.

다음 두 파일의 현재 버전 전체를 올려주세요.

- `VexRiscvTop.scala`

확인 후 다음을 진행하겠습니다.

1. 현재 ROM의 실제 명령어 주소와 Reset Vector 확인
2. DBus 주소·데이터·byte mask 연결
3. Store 시 RAM 쓰기
4. Load 시 동기식 RAM 읽기와 응답 생성
5. RAM[0], RAM[1]의 최종 데이터 검증
